A.1 精通 EXPLAIN

全书大多用这样的写法分析执行计划：

EXPLAIN (analyze, costs off)
SELECT ...

analyze 让 Postgres 真正执行计划，显示实际耗时等统计；costs off 去掉每一步的估算代价和预计行数，让输出更紧凑。比如第 5 章的一条查询：

EXPLAIN (analyze, costs off)
SELECT count(*)
FROM pizzeria.order_items
WHERE pizza @> '{"type": "custom"}';

 Aggregate (actual time=1.501..1.502 rows=1 loops=1)
   -> Seq Scan on order_items (actual time=0.033..1.446 rows=563 loops=1)
         Filter: (pizza @> '{"type": "custom"}'::jsonb)
         Rows Removed by Filter: 2375
 Planning Time: 0.287 ms
 Execution Time: 1.551 ms

两个参数都去掉，就只有估算代价（costs 默认为 true），没有实际耗时（因为没执行）：

 Aggregate (cost=139.13..139.14 rows=1 width=8)
   -> Seq Scan on order_items (cost=0.00..137.72 rows=563 width=0)
         Filter: (pizza @> '{"type": "custom"}'::jsonb)

书里用 (analyze, costs off) 只是因为它足够说明问题，并不是最佳实践。优化一条慢查询时，更好的做法是保留估算代价、并加上内存缓冲区信息： 

EXPLAIN (analyze, buffers on)
SELECT count(*)
FROM pizzeria.order_items
WHERE pizza @> '{"type": "custom"}';

 Aggregate (cost=139.13..139.14 rows=1 width=8)
           (actual time=1.713..1.714 rows=1 loops=1)
   Buffers: shared hit=101
   -> Seq Scan on order_items (cost=0.00..137.72 rows=563 width=0)
                              (actual time=0.034..1.624 rows=563 loops=1)
         Filter: (pizza @> '{"type": "custom"}'::jsonb)
         Rows Removed by Filter: 2375
         Buffers: shared hit=101
 Planning Time: 0.378 ms
 Execution Time: 1.757 ms
  • 同时有估算和实际，就能看出 Postgres 估得准不准。规划阶段 Postgres 是按估算代价在多个计划里挑的；如果选中的计划估算和实际差得很远，可能是统计信息没跟上，也可能是查询本身需要优化。
  • Buffers 显示执行时有多少数据要从磁盘取。shared hit=101 表示处理的所有行都来自内存（缓存在 101 个缓冲区里），完全没碰磁盘。如果命中率低、大量时间花在磁盘 I/O 上，也许给数据库服务器加点内存就够了，用不着别的优化手段。
💡 Postgres 18 的变化

从 Postgres 18 开始，EXPLAIN ANALYZE 默认就包含缓冲区信息，不用再显式加 buffers on。

★ 一句话

熟练使用 EXPLAIN、读懂执行计划。在弄清 Postgres 做了什么、为什么这样执行之前，不要过早优化，也不要凭感觉猜。

A.2 知道何时使用索引

书里几乎每一章都有一节专门讲某种索引。为什么这么重视？因为一旦理解了索引怎么工作、什么时候用，你和数据库的关系就彻底变了：数据库不再是黑盒，你会更愿意深入它的内部。 在自己的应用里，决定是否建索引就是你的责任了。记住三个词：EXPLAIN、索引不足、过度索引。

EXPLAIN

规则很简单：建索引之前，先生成并看懂执行计划。不要猜，先分析。它可能告诉你根本不需要索引。

索引不足（underindexing）

查询慢只是因为缺了本该有的索引。说实话，这是个让人愉快的问题。如果执行计划显示一条慢查询在大数据集上全表扫描，别急着换一台 CPU 更多、内存更大的机器，先考虑加个索引。 更大的机器意味着高得多的成本，而在索引不足的情况下加个索引，成本往往可以忽略不计。比如找出所有自定义配方的披萨： 

 Aggregate (cost=139.13..139.14 rows=1 width=8) (actual time=1.516..1.518 rows=1 loops=1)
   Buffers: shared hit=101
   -> Seq Scan on order_items (cost=0.00..137.72 rows=563 width=0)
                              (actual time=0.037..1.454 rows=563 loops=1)
         Filter: (pizza @> '{"type": "custom"}'::jsonb)
         Rows Removed by Filter: 2375
         Buffers: shared hit=101
 Execution Time: 1.565 ms

全表扫描，不过数据都在内存里。应用经常按类型过滤披萨，订单量还会持续增长，建索引是合理的。先确认现有的索引：

SELECT indexname, indexdef
FROM pg_indexes
WHERE schemaname = 'pizzeria' AND tablename = 'order_items';
-- order_items_pkey | CREATE UNIQUE INDEX order_items_pkey
--                  | ON pizzeria.order_items USING btree (order_id, order_item_id)

只有 (order_id, order_item_id) 上的复合 B-tree，显然用不来按 JSON 结构过滤 —— 这就是表级的“索引不足”。第 5 章的解决办法是在 pizza 列上建 GIN：

CREATE INDEX idx_pizza_orders_gin
ON pizzeria.order_items USING GIN(pizza);

 Aggregate (cost=125.34..125.35 rows=1 width=8) (actual time=0.926..0.927 rows=1 loops=1)
   Buffers: shared hit=107
   -> Bitmap Heap Scan on order_items (cost=15.90..123.93 rows=563 width=0)
                                      (actual time=0.160..0.869 rows=563 loops=1)
         Recheck Cond: (pizza @> '{"type": "custom"}'::jsonb)
         Heap Blocks: exact=101
         -> Bitmap Index Scan on idx_pizza_orders_gin (cost=0.00..15.75 rows=563 width=0)
                                                      (actual time=0.126..0.126 rows=563 loops=1)
               Index Cond: (pizza @> '{"type": "custom"}'::jsonb)
               Buffers: shared hit=6
 Execution Time: 0.996 ms

过度索引（overindexing）

反过来，索引太多会弊大于利。索引对查询性能那么有效，很容易让人想给每一列都建一个，但这是有代价的：

  • 索引是一种数据结构，要占存储和内存。索引越多，需要的资源越多。
  • 每次往表里插入新记录，每个索引都要更新；修改记录时也可能要更新。表上索引一多，Postgres 就得把它们全部维护好，导致写入放大，拖慢 INSERT、UPDATE、DELETE。
  • 规划阶段也有开销：索引越多，Postgres 挑选最佳计划时要考虑的就越多。

所以要有索引策略：不要为了优化又一条查询就加一个新索引，而是分析一张表上常见查询的执行计划，看能否用有限的几个索引让它们都跑得快。 比如 pizza 列上那个 GIN 索引，除了按类型过滤，还能加速按 JSON 里其他字段过滤的查询。统计“大号三重奶酪”披萨： 

EXPLAIN (analyze, buffers on)
SELECT count(*)
FROM pizzeria.order_items
WHERE pizza @> '{"size": "large"}' AND pizza @> '{"type": "three cheese"}';

 Aggregate (cost=131.04..131.05 rows=1 width=8) (actual time=0.661..0.662 rows=1 loops=1)
   -> Bitmap Heap Scan on order_items (cost=22.54..130.67 rows=147 width=0)
                                      (actual time=0.328..0.642 rows=153 loops=1)
         Recheck Cond: ((pizza @> '{"size": "large"}'::jsonb)
                        AND (pizza @> '{"type": "three cheese"}'::jsonb))
         -> Bitmap Index Scan on idx_pizza_orders_gin ...
 Execution Time: 0.722 ms

条件变了，数据库还是复用了同一个索引。总之，索引策略要追求平衡：太少导致索引不足，太多导致过度索引，合适的点在中间，而且因场景而异。

A.3 使用连接池

全书都用 psql 连接容器里的 Postgres：

docker exec -it postgres psql -U postgres
# 没写端口，默认连 5432，等价于：
docker exec -it postgres psql -U postgres -p 5432

Postgres 启动时会运行一个叫 postmaster 的特殊进程，监听 5432 端口。psql 一连上来，postmaster 就新起一个操作系统进程专门服务这个会话；会话关闭时，这个进程也随之结束，不会留给之后连接的客户端复用。

如果应用并发执行查询，每个查询都新开一个连接、执行、再关闭，Postgres 就得为每个并发查询新建一个 OS 进程、执行、再结束进程。 创建进程虽然是轻量操作（在 Unix 上尤其如此），但积少成多会增加查询总耗时，也让 Postgres 和操作系统多做很多工作。连接池能复用已经打开的连接，大幅减少这种开销。

  • 客户端连接池：由某种语言的库或框架为应用管理连接。应用要执行查询时不直接连数据库，而是从池里借一个连接，执行完再还回去。池不会关闭归还的连接，而是留着给下一个请求复用。池的最大连接数可以配置，从而控制能同时向数据库发多少查询。
  • 服务端（数据库端）连接池：适合数据库被多个应用或微服务访问的情况。即使每个应用都有自己的客户端池，加起来也会给数据库很大压力 —— 它要维护的连接数（OS 进程数）等于所有客户端池的总和。Postgres 没有内置连接池，也不需要：生态里有很多久经考验的选择，比如 Pgpool、PgBouncer、Odyssey。托管的 Postgres 服务通常已经自带服务端连接池。

在 Python、Node.js 代码里怎样配置连接池、PgBouncer 事务模式有哪些限制，见专题 5：从应用连接 Postgres。

💡 看看底层发生了什么

想亲眼看到 Postgres 怎样为每个新连接起一个专门的 OS 进程、连接池又如何优化这件事，可以看仓库 postgres_internals_videos.md 里的视频：“Database Connection Pooling: Why It Matters? Essential OS-Level Insights”。

A.4 只查询真正需要的

一般情况

如果应用里有一条 SELECT * FROM tableA WHERE …，先想想 * 是不是真的必要。它让 Postgres 取出满足条件的行的所有列。 表里只有几列、而且都是 int、timestamp、point 这种定长基础类型时，用不用 * 差别不大；但如果表有几十列，或者有 text、vector、jsonb、polygon 这种变长类型，就该只取应用真正要用的列。

假设表有 15 列，某个业务操作只用其中 5 列，但应用还是 SELECT *（可能图方便，也可能 ORM 默认就取所有列）。多取的 10 列可不是免费的：

  1. Postgres 要从表结构里取出这 10 列的值，把副本加进结果集 —— 每一行都要这样。返回 1 行就有 10 个多余的值，10 行就是 100 个。
  2. 结果集要序列化，切成小的网络包，经过一个个路由器从数据库传到应用服务器。都是 byte 类型的话只多传 100 字节；但只要有一列是 text、jsonb 这类变长类型，多余数据轻松达到 KB 甚至 MB 级别。
  3. 应用要接收这些网络包、反序列化成结果集，可能还要转换成编程语言或框架用的对象结构 —— 为这 100 个没用的值消耗计算和内存，白忙一场。

偶尔执行一次不会有人注意到。但每秒执行 100 次呢？就是 100 次 × 10 行 × 10 列 = 每秒 10,000 个值被取出、传输、丢弃。 所以要养成习惯：业务操作真正需要什么就只查什么。15 列里只要 5 列，就明确写 SELECT col1, col2, col3, col4, col5 FROM tableA。用 ORM 的话，留意它自动生成的 SQL，必要时调整，确保只取真正需要的。

count(*) 是个例外

Postgres 对 count(*) 有专门优化：执行 SELECT count(*) FROM tableA WHERE … 时，它只数行数，不取任何列的值。这也是全书一直用 count(*) 的原因：

EXPLAIN (analyze)
SELECT count(*)
FROM pizzeria.order_items;

 Aggregate (cost=91.69..91.70 rows=1 width=8) (actual time=0.721..0.723 rows=1 loops=1)
   -> Index Only Scan using order_items_pkey on order_items
        (cost=0.28..84.35 rows=2938 width=0) (actual time=0.091..0.532 rows=2938 loops=1)
         Heap Fetches: 0
 Execution Time: 0.771 ms

Index Only Scan 数出 2938 行，但每行的大小是 0（width=0）—— 没有读任何列的值。换成 count(order_item_id)：

 Aggregate (cost=91.69..91.70 rows=1 width=8) (actual time=0.884..0.885 rows=1 loops=1)
   -> Index Only Scan using order_items_pkey on order_items
        (cost=0.28..84.35 rows=2938 width=4) (actual time=0.031..0.534 rows=2938 loops=1)
         Heap Fetches: 0
 Execution Time: 0.933 ms

这次每行 4 字节（width=4）—— order_item_id 是 INT 类型，Postgres 开始读取这一列的值了。

ⓘ count(列) 和 count(*) 的语义也不同

count(列) 只统计该列不为 NULL 的行，count(*) 统计所有行。想数行数就用 count(*)，既正确又更快。

A.5 用好数据库的计算能力

Postgres 不只是一个把数据放进去、再取出来的存储容器，它是一个强大的计算平台。全书都在展示：它能用内置函数、CTE、窗口函数等轻松地排序、分组、聚合和处理数据，还能用自定义函数、存储过程、触发器运行你自己的业务逻辑。

  • 要排序？用 ORDER BY，别把数据取到应用里再排。
  • 要按条件分组？多半用不着自己写逻辑，GROUP BY 就能搞定。
  • 要执行一个严重依赖 Postgres 里数据的计算密集或数据密集的业务操作？考虑写一个完全在数据库里运行的函数或存储过程（回顾第 2 章的银行计息例子）。

能交给数据库的越多，应用这边要处理的就越少，逻辑可能更清晰，整个技术栈的资源利用也更高效。

动手练习

  1. 挑本书任意一条查询，分别用 EXPLAIN、EXPLAIN ANALYZE、EXPLAIN (analyze, buffers on) 执行，逐项对照图 A-1 解读输出。
    参考答案

    以第 4 章清单 4.7 为例（先按第 4 章建好 idx_region_score_win_count）：

    EXPLAIN
SELECT username, region, score, win_count FROM game.player_stats
WHERE region = 'NA' AND score > 5000 AND win_count > 10;

EXPLAIN ANALYZE
SELECT …;                    -- 同一条查询

EXPLAIN (analyze, buffers on)
SELECT …;

    三者的区别：EXPLAIN 只有估算（cost、rows、width），查询并不执行；ANALYZE 真的执行一遍，多出 actual time、实际 rows 和 loops，可以和估算对比，差得多说明统计信息不准； buffers 再加上读了多少页（shared hit 来自缓存，read 来自磁盘或系统缓存）。注意 ANALYZE 会真的执行，对 UPDATE / DELETE 用它时记得放在事务里再 ROLLBACK。

  2. 对 game.player_stats（第 4 章）执行 SELECT indexrelname, idx_scan FROM pg_stat_user_indexes WHERE schemaname = 'game';，找出从来没被用过的索引 —— 它们就是过度索引的候选。
    参考答案 
    SELECT indexrelname, idx_scan, pg_size_pretty(pg_relation_size(indexrelid)) AS size
FROM pg_stat_user_indexes
WHERE schemaname = 'game'
ORDER BY idx_scan, indexrelname;

    idx_scan 是这个索引自统计重置以来被扫描的次数，为 0 的就是候选。但要注意三点： 主键和唯一约束的索引即使 idx_scan = 0 也不能删，它们在保证约束（每次插入都要检查）； 统计是从上次 pg_stat_reset() 或建库以来累计的，刚建的索引、只在月底报表用的索引也可能是 0； 有只读副本时，副本上的使用情况要去副本上查。确认没用后再 DROP INDEX CONCURRENTLY。

  3. 对第 8 章的 omdb.movies 比较 SELECT * 和 SELECT id, name 的 EXPLAIN (analyze) 输出中的 width，体会 1024 维向量列有多“重”。
    参考答案 
    EXPLAIN (analyze) SELECT * FROM omdb.movies;
--  Seq Scan on movies  (cost=0.00..220.24 rows=4224 width=304) (actual time=0.007..0.536 rows=4224 loops=1)
EXPLAIN (analyze) SELECT id, name FROM omdb.movies;
--  Seq Scan on movies  (cost=0.00..220.24 rows=4224 width=24)  (actual time=0.005..0.454 rows=4224 loops=1)

    width 从 24 字节变成 304 字节，但两条查询的执行时间几乎一样，这是个陷阱：1024 维向量（约 4 KB）太大，被 TOAST 存到了表外， EXPLAIN ANALYZE 只扫描表本身，既不取出 TOAST 里的数据，也不把结果发给客户端。Postgres 17 新增的 SERIALIZE 选项能把这部分算进来： 

    EXPLAIN (analyze, serialize, costs off) SELECT * FROM omdb.movies;
--  Serialization: time=139.983 ms  output=53843kB  format=text
--  Execution Time: 141.080 ms
EXPLAIN (analyze, serialize, costs off) SELECT id, name FROM omdb.movies;
--  Serialization: time=0.441 ms  output=127kB  format=text
--  Execution Time: 1.449 ms

    在 psql 里用 \timing 实际跑一遍：SELECT * 约 200 ms、返回 55 MB；SELECT id, name 约 2.5 ms、95 KB。差了约 80 倍，这就是 A.4 节“只查询真正需要的”的意义。

  4. 用你熟悉的语言写一个小程序，分别用“每次新建连接”和“连接池”执行 1000 次简单查询，比较总耗时。
    参考答案 
    import time, psycopg
from psycopg_pool import ConnectionPool
DSN = "postgresql://postgres:password@localhost:5432/postgres"
N = 1000

t = time.perf_counter()
for _ in range(N):
    with psycopg.connect(DSN) as conn:           # 每次新建连接
        conn.execute("SELECT 1").fetchone()
new_conn = time.perf_counter() - t

with ConnectionPool(DSN, min_size=1, max_size=4, open=True) as pool:
    pool.wait()
    t = time.perf_counter()
    for _ in range(N):
        with pool.connection() as conn:         # 从池里借已经建好的连接
            conn.execute("SELECT 1").fetchone()
    pooled = time.perf_counter() - t

print(f"每次新建连接: {new_conn:.2f} s；连接池: {pooled:.2f} s")

    每次新建连接: 7.39 s（平均 7.39 ms/次）
连接池:       0.19 s（平均 0.19 ms/次）
快了约 39 倍

    每次新建连接都要经过 TCP 握手、密码认证（这里是 SCRAM，本身就要做几千次哈希）、Postgres 新起一个进程；查询本身只占零头。各语言的写法见专题 5。
