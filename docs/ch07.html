第 7 章 · 第三部分：扩展与生态

Postgres 扩展

扩展是 Postgres 如此流行的主要原因之一。事实上，“Just use Postgres”这句口号很大程度上就是因为它丰富的扩展生态 —— 扩展让数据库能做的事远远超出前几章的范围。这一章快速巡览扩展生态，并动手用一个 Postgres 标准发行版自带的扩展。 后面四章会分别深入 pgvector、TimescaleDB、PostGIS 和 pgmq。

本章目标

  • 了解 Postgres 可扩展性的由来，以及支撑它的三大技术基础
  • 知道扩展的安装分两步：装到服务器上、在数据库里启用
  • 会用 pg_available_extensions、CREATE EXTENSION、DROP EXTENSION
  • 用 pgcrypto 安全地存储和校验密码
  • 对开发者常用的五类扩展有一张“地图”，并了解 Postgres 兼容方案

Postgres 可扩展性的根源

Postgres 起源于加州大学伯克利分校的研究项目，由图灵奖得主 Michael Stonebraker 领导。 在 2017 年的图灵奖访谈中，他讲了一个故事，解释为什么可扩展性是 Postgres 的立身之本：

80 年代初有几十篇研究论文都在说类似的事：关系数据库理论上很好，但在某个场景下效果不好，甚至完全不能用；然后论文介绍自己发明了什么来解决。 Stonebraker 由此看清：当时的关系数据库在商业数据处理之外表现不佳（对地理信息管理系统完全不适用）， 应该有更好的办法让数据库适应特定场景，而不是去执行各种论文开出的一长串药方。 于是他的团队开始构建 Postgres，把可扩展性定为主要需求之一。从那以后，这项能力不断演进，让 Postgres 能适应今天的各种新场景。

开始使用扩展

Postgres 有几百个扩展，用途五花八门。如果核心 Postgres 缺少你需要的功能，很可能已经有扩展实现了。生态之所以这么丰富，是因为 Postgres 在设计上提供了三大基础：

  • 目录驱动的操作：Postgres 把表、列、数据类型、函数等对象的信息存在系统目录（system catalog）里。它们和普通表差不多，只是存的是数据库内部的元数据。扩展可以读写系统目录，从而给 Postgres 添加新的数据类型和函数。
  • 数据库钩子：Postgres 代码里预留了一些钩子点，扩展可以在那里注入自定义逻辑，就像回调函数或事件监听器。比如扩展可以拦截查询规划、执行、认证等环节的钩子，处理特定事件或修改数据库行为。
  • 动态加载扩展逻辑：扩展可以用纯 SQL、PL/pgSQL 这类过程语言，或者 C、Rust 这类编译语言来写。SQL 和 PL/pgSQL 由数据库引擎直接解释，不需要外部库；编译语言写的扩展则在运行时动态加载共享库，不需要重新编译数据库引擎。

使用扩展前，要先把它装到数据库服务器上，再在某个数据库（用 CREATE DATABASE 建的那种）里启用它：

有些扩展用得太普遍、太重要了，直接随标准 Postgres 发行版一起分发，存在专门的目录里，需要时直接启用即可。其他扩展可以通过以下途径装到服务器上：

  • 扩展仓库：很多扩展可以在 PGXN 这类仓库里找到并安装。
  • 预构建容器镜像：很多扩展作者提供了“标准 Postgres + 该扩展”的 Docker 镜像，部署很快。
  • Linux 包管理器：热门扩展通常能用 APT（Debian/Ubuntu）或 DNF/YUM（RedHat/CentOS）安装。
  • 二进制或源码：都不行的话，就按维护者的说明从源码编译；有些提供方也会为特定操作系统提供二进制包。

安装和使用扩展：pgcrypto

后面几章会用 Docker 镜像来完成第一步（把扩展装到服务器上）。这里先练习第二步：启用一个随发行版自带的扩展 pgcrypto。 它提供各种加密函数，让我们能在数据库里安全地存储和处理敏感数据。

启用 pgcrypto

SELECT name, default_version, installed_version
FROM pg_available_extensions
WHERE name = 'pgcrypto';

   name   | default_version | installed_version
----------+-----------------+-------------------
 pgcrypto | 1.3             |
(1 row)

服务器上有 1.3 版，但当前数据库还没启用。启用只需一条命令：

CREATE EXTENSION pgcrypto;

再执行清单 7.1，installed_version 变成了 1.3。pg_extension 视图只记录当前数据库已启用的扩展：

SELECT extname, extversion FROM pg_extension;

 extname  | extversion
----------+------------
 plpgsql  | 1.0
 pgcrypto | 1.3
(2 rows)

用 pgcrypto 安全存储密码

应用把用户名和密码哈希存在 accounts 表里：

CREATE TABLE accounts (
    id SERIAL PRIMARY KEY,
    username TEXT NOT NULL,
    password_hash TEXT NOT NULL
);

新用户注册时：

INSERT INTO accounts (username, password_hash)
VALUES ('ahamilton', crypt('SuperSecret123', gen_salt('bf')));
  • gen_salt('bf')：用 Blowfish（bf）算法生成一个随机盐（salt）。每个新密码都要生成一个新的盐。为什么不用一个固定的盐？因为固定盐一旦泄露，攻击者可以一次性尝试破解所有密码；用随机盐，泄露一个盐只影响一个密码。
  • crypt(密码, 盐)：把原始密码和盐组合起来算出安全的哈希。因为盐是随机的，就算两个人密码相同，哈希也不同。盐本身也存在哈希值里，以便以后验证。

就算攻击者拿到了数据库，也看不到真实密码：

 id | username  |                        password_hash
----+-----------+--------------------------------------------------------------
  1 | ahamilton | $2a$06$NzaPtzIucejO/LVefQRHuOAmW90LGKZf..l70dv48.vO9p/kSx/Qi
(1 row)

第二天用户回来登录，输入用户名和密码，应用执行：

SELECT username FROM accounts
WHERE username = 'ahamilton'
AND password_hash = crypt('SuperSecret123', password_hash);

这次把用户输入的原始密码和已存储的 password_hash 一起传给 crypt：函数从存储的哈希里取出盐，用它对输入的密码再算一次哈希。 算出来的和存的一样，就返回用户名，登录成功。如果用户把密码输成 SuperSecret1243，哈希对不上，返回空结果（0 rows），应用就可以提示密码错误。

停用 pgcrypto

不需要某个扩展时，用 DROP EXTENSION 在当前数据库里停用它：

DROP EXTENSION pgcrypto;

SELECT extname, extversion FROM pg_extension;
-- 只剩 plpgsql

没了 pgcrypto，再用 crypt 验证用户就会报错：

ERROR: function crypt(unknown, text) does not exist
LINE 3: AND password_hash = crypt('SuperSecret123', password_hash);
                            ^
HINT: No function matches the given name and argument types.
You might need to add explicit type casts.

改主意了？再 CREATE EXTENSION pgcrypto; 就行。

⚠ DROP EXTENSION 会连带删除

扩展创建的类型、函数、运算符都会随 DROP EXTENSION 一起删除。如果你的表用了扩展提供的类型（比如第 8 章 pgvector 的 vector 列），删除扩展会失败，加上 CASCADE 则会连那些列一起删掉。生产环境务必谨慎。

开发者必备的扩展

扩展没有官方分类，但我们可以按自己的标准分成五组，帮你扩充工具箱：

① 超越关系型

前几章已经看到，核心 Postgres 支持 JSON 和全文搜索，但那只是冰山一角，大部分非关系型能力来自扩展：

  • pgvector、pgai、pgvectorscale 让 Postgres 支持生成式 AI 和其他 AI/ML 工作负载，实际上把它变成了向量数据库。pgai 能直接在 Postgres 里生成嵌入、调用大模型、跑完整的 RAG 流程；pgvectorscale 通过 StreamingDiskANN 索引、统计二值量化等优化，让大规模向量搜索更省钱、更快。第 8 章详细讲。
  • TimescaleDB：轻松存储和分析海量时序和事件数据。第 9 章。
  • PostGIS：把 Postgres 变成能存储、索引、查询地理空间数据的数据库。第 10 章。
  • pgmq：把 Postgres 当作轻量级消息队列，持久化并投递消息和事件。第 11 章。
  • pg_duckdb：嵌入 DuckDB 的列式向量化存储引擎，为 Postgres 提供高性能分析能力。

② 编程与过程语言

第 2 章用 PL/pgSQL 写了函数，但你不必成为 PL/pgSQL 专家。大多数情况下都能找到扩展，让你用自己熟悉的语言写数据库函数：

  • PLV8 把 V8 JavaScript 引擎嵌进 Postgres，可以用 JavaScript 写数据库逻辑、从 SQL 调用。配合 PgCompute 客户端库，还能绕过 SQL，从应用直接在数据库上执行 JavaScript 函数。
  • PL/Java、PL/Python、PL/Rust 等分别让你用 Java、Python、Rust 写函数、过程和触发器。
-- 示意：用 PLV8 写一个 JavaScript 函数（需要先安装 plv8 扩展）
CREATE EXTENSION plv8;

CREATE FUNCTION js_upper(s text) RETURNS text AS $$
    return s.toUpperCase();
$$ LANGUAGE plv8;

SELECT js_upper('just use postgres');   -- JUST USE POSTGRES

③ 连接器与外部数据包装器（FDW）

这类扩展让 Postgres 连接外部数据源，用标准 SQL 透明地查询远程数据，就像查本地的表一样。Postgres 由此成为一个统一的数据层，甚至能从本身不支持 SQL 的数据源拉数据：

  • file_fdw：查询文件系统里的数据。
  • postgres_fdw、mysql_fdw、oracle_fdw、sqlite_fdw：连接并查询远程 Postgres、MySQL、Oracle、SQLite。
  • redis_fdw、parquet_s3_fdw、kafka_fdw：从 Redis、S3、Kafka 这些非 SQL 数据源获取数据。

④ 查询与性能优化

  • pg_stat_statements：跟踪 Postgres 执行过的所有 SQL 语句的规划和执行统计（附录 A 会用到）。
  • auto_explain：自动记录慢查询的执行计划，不用手动跑 EXPLAIN ANALYZE 就能诊断性能问题。
  • hypopg：支持假想索引，不用真的建索引就能测试不同的索引策略。

⑤ 工具与实用程序

  • pg_cron：运行在 Postgres 内部的 cron 定时调度器，自动执行例行任务（比如第 2 章提到的定时刷新物化视图）。
  • PostgreSQL Anonymizer：用动态脱敏、假名化等技术对个人和敏感数据做匿名或遮蔽。
  • pgaudit：通过 Postgres 的标准日志功能提供详细的会话级和对象级审计日志。
  • pg_partman：简化基于时间和基于数字的表分区的创建和管理（第 11 章讲分区时会提到）。

这份清单远不完整，但足以说明扩展把数据库的边界推得多远。这一切得益于 Postgres 的可扩展设计： 相对保守的核心引擎 + 让它始终站在创新前沿的扩展生态，两者达成了恰到好处的平衡。

Postgres 兼容方案

Postgres 发展得太快，以至于它的通信协议、功能、源代码被很多不属于扩展的方案所采用。 这些“Postgres 兼容方案”提供了 Postgres 本身和任何扩展都没有的能力。

它们通常针对某一类很难或无法用扩展解决的问题：可能 Postgres 没有提供需要的钩子，也可能方案的架构和 Postgres 差别太大，做成扩展不现实。 于是要么从零构建，支持 Postgres 的线协议和部分功能；要么基于 Postgres 源码做修改。

ⓘ 什么是线协议（wire-level protocol）

Postgres 线协议定义了 Postgres 客户端和服务器之间通信用的消息格式和命令。应用发出的每一条 SQL 命令都按这个协议传输和处理。支持线协议，意味着 psql、各语言的 Postgres 驱动、ORM 可以直接连上去。

  • Google Spanner 和 CockroachDB 是从零构建的分布式 Postgres 兼容数据库，支持 Postgres 线协议、DML 和 DDL 语法以及部分 Postgres 功能。因此可以复用一部分现有的 Postgres 第三方工具和框架，同时构建可扩展、高可用的应用。
  • Neon（Serverless 数据库）和 YugabyteDB（分布式数据库）基于 Postgres 源码构建，在存储层做了修改和增强。它们复用了大部分源码，现有的 Postgres 应用可以原样运行，或者只需很少的迁移工作；大多数 Postgres 库、工具、框架也都能继续用。

所以，如果某个问题用 Postgres 和扩展都解决不了，可以看看兼容方案 —— 它们可能正好有你需要的，同时你的 Postgres 技能依然能派上用场。

小结

  • 可扩展性是 Postgres 最初的主要设计需求之一。
  • Postgres 通过目录驱动的操作、数据库钩子和动态加载外部逻辑实现可扩展。
  • 扩展可以通过扩展仓库、包管理器、预构建容器镜像安装，或从源码构建；标准发行版自带几十个扩展。
  • 安装分两步：装到服务器（pg_available_extensions 可见），再用 CREATE EXTENSION 在每个数据库里启用（pg_extension / \dx 可见）。
  • 开发者可以用大量扩展超越关系型负载、查询远程数据源、简化查询优化等。
  • Postgres 兼容方案解决扩展难以解决的特定问题：要么支持线协议和部分功能，要么基于 Postgres 源码修改。
