UPSERT：INSERT … ON CONFLICT

一张库存表，sku 是主键：

CREATE TABLE inventory (
  sku text PRIMARY KEY,
  name text,
  qty int NOT NULL DEFAULT 0,
  updated_at timestamptz DEFAULT now()
);

INSERT INTO inventory (sku, name, qty) VALUES ('COF-01', 'Sunrise Blend', 10);

同一个 sku 再插一次，主键冲突，整条语句失败：

ERROR:  duplicate key value violates unique constraint "inventory_pkey"
DETAIL:  Key (sku)=(COF-01) already exists.

很多应用的第一反应是“先 SELECT 看看有没有，没有再 INSERT，有就 UPDATE”。但这在并发下是错的：两个请求可能同时发现“没有”，然后都去 INSERT。 Postgres 的答案是 ON CONFLICT，把“检查 + 插入 / 更新”做成一个原子操作。

冲突时什么都不做

INSERT INTO inventory (sku, name, qty) VALUES ('COF-01', 'Sunrise Blend', 5)
ON CONFLICT (sku) DO NOTHING;
-- INSERT 0 0     没插入，也没报错

适合“幂等写入”：比如消息被重复投递，同一个事件 ID 写第二次时直接忽略。

冲突时更新

INSERT INTO inventory (sku, name, qty) VALUES
  ('COF-01', 'Sunrise Blend', 5),
  ('MUG-01', 'Mug', 3)
ON CONFLICT (sku) DO UPDATE
  SET qty = inventory.qty + EXCLUDED.qty,
      updated_at = now()
RETURNING sku, qty, (xmax = 0) AS inserted;

  sku   | qty | inserted
--------+-----+----------
 COF-01 |  15 | f
 MUG-01 |   3 | t
(2 rows)
  • ON CONFLICT (sku)：指定按哪一列（或哪个唯一约束）判断冲突。这一列上必须有唯一索引或唯一约束。
  • EXCLUDED：一个特殊的表名，代表“本来想插入、因冲突而被排除的那一行”；inventory.qty 则是表里已有的值。
  • RETURNING：返回最终的行。(xmax = 0) AS inserted 是社区常用的小技巧：新插入的行 xmax 为 0，被更新的行不为 0，借此区分这一行是插入还是更新。注意它依赖 MVCC 的实现细节（见专题 4），不是官方文档承诺的接口。

带条件的更新

DO UPDATE 后面可以跟 WHERE，只有满足条件才更新。比如“只接受更大的库存数”：

INSERT INTO inventory (sku, name, qty) VALUES ('COF-01', 'Sunrise Blend', 100)
ON CONFLICT (sku) DO UPDATE SET qty = EXCLUDED.qty
  WHERE inventory.qty < EXCLUDED.qty
RETURNING sku, qty;
-- COF-01 | 100     15 < 100，更新了

INSERT INTO inventory (sku, name, qty) VALUES ('COF-01', 'Sunrise Blend', 1)
ON CONFLICT (sku) DO UPDATE SET qty = EXCLUDED.qty
  WHERE inventory.qty < EXCLUDED.qty
RETURNING sku, qty;
-- (0 rows)        100 < 1 不成立，什么也没做
★ ON CONFLICT 还是 MERGE？

第 2 章用了 MERGE（清单 2.22）。两者都能“有则改、无则插”，区别在于： ON CONFLICT 借助唯一索引，在并发下也保证“要么插入、要么更新”； MERGE 更灵活（可以按任意条件匹配、可以 DELETE、能处理多种分支），但官方文档指出，并发插入时 MERGE 仍可能遇到唯一约束冲突报错。 简单的“按主键 / 唯一键 UPSERT”优先用 ON CONFLICT；需要复杂的同步逻辑（比如拿一张临时表去同步一张目标表）再用 MERGE。

Postgres 特色类型

数组

任何类型都可以加上 [] 变成数组。适合标签、多个电话号码这类“一行有几个、通常整体读写”的数据：

CREATE TABLE posts (id serial PRIMARY KEY, title text, tags text[]);

INSERT INTO posts (title, tags) VALUES
  ('Postgres 索引入门', ARRAY['postgres', 'index']),   -- ARRAY[...] 写法
  ('JSONB 实战',        '{postgres,json}'),             -- 字面量写法
  ('Redis 缓存',        '{redis,cache}');

SELECT title FROM posts WHERE 'json' = ANY(tags);                 -- JSONB 实战
SELECT title FROM posts WHERE tags @> ARRAY['postgres','index'];  -- Postgres 索引入门
SELECT title FROM posts WHERE tags && ARRAY['redis','json'];      -- JSONB 实战、Redis 缓存

-- 展开成行再统计：最热门的标签
SELECT unnest(tags) AS tag, count(*) FROM posts GROUP BY tag ORDER BY 2 DESC, 1;

   tag    | count
----------+-------
 postgres |     2
 cache    |     1
 index    |     1
 json     |     1
 redis    |     1
(5 rows)

-- 多行聚合成一个数组
SELECT array_agg(title ORDER BY id) FROM posts;
-- {"Postgres 索引入门","JSONB 实战","Redis 缓存"}

-- 增删元素
UPDATE posts SET tags = array_append(tags, 'beginner') WHERE id = 1 RETURNING tags;
-- {postgres,index,beginner}
UPDATE posts SET tags = array_remove(tags, 'beginner') WHERE id = 1 RETURNING tags;
-- {postgres,index}

给数组建 GIN 索引（和第 5 章 JSONB 一样是倒排索引）：

CREATE INDEX posts_tags_gin ON posts USING GIN (tags);
SET enable_seqscan = off;   -- 表里只有 3 行，规划器本会直接全表扫描；先禁止它，看索引能不能用上

EXPLAIN (costs off) SELECT title FROM posts WHERE tags @> ARRAY['postgres'];
--  Bitmap Heap Scan on posts
--    Recheck Cond: (tags @> '{postgres}'::text[])
--    ->  Bitmap Index Scan on posts_tags_gin           ✓ 用上了

EXPLAIN (costs off) SELECT title FROM posts WHERE 'postgres' = ANY(tags);
--  Seq Scan on posts
--    Filter: ('postgres'::text = ANY (tags))          ✗ 禁止了全表扫描也用不上

RESET enable_seqscan;
⚠ 想用索引，就写 @>

'x' = ANY(tags) 最直观，但 GIN 索引只支持 @>、&&、<@、= 这些数组运算符。查“包含某个标签”时写成 tags @> ARRAY['x']，意思一样，还能走索引。

💡 数组、JSONB 还是关联表？

标签这种“简单值的列表”，数组最轻量。元素本身有结构（标签还要带颜色、创建人），用 JSONB（第 5 章）。 元素需要被单独引用、要有外键约束、或者经常被单独修改，就老老实实建一张关联表（第 2 章的 order_items 就是）。

范围类型与排他约束

范围类型用一个值表示“从哪到哪”。内置的有 int4range、int8range、numrange、daterange、tsrange、tstzrange。 方括号 [ 表示包含边界，圆括号 ) 表示不包含： 

SELECT int4range(1, 10) @> 5,      -- t   包含 5
       int4range(1, 10) @> 10,     -- f   默认左闭右开 [1,10)
       '[1,10]'::int4range;        -- [1,11)   整数范围会被规范化成左闭右开

SELECT daterange('2025-06-01', '2025-06-05') && daterange('2025-06-04', '2025-06-08');
-- t   两个范围重叠

SELECT tstzrange('2025-06-01 09:00', '2025-06-01 10:00')
     * tstzrange('2025-06-01 09:30', '2025-06-01 11:00');
-- ["2025-06-01 09:30:00+00","2025-06-01 10:00:00+00")   * 是取交集

范围类型真正的杀手锏是配合排他约束（第 2 章清单 2.21 见过 EXCLUDE）：同一个会议室的预订时间不能重叠。这条规则交给数据库保证，应用层再怎么并发也不会出错： 

CREATE EXTENSION btree_gist;   -- 让 GiST 也能处理 text 的 = 比较

CREATE TABLE bookings (
  id serial PRIMARY KEY,
  room text NOT NULL,
  during tstzrange NOT NULL,
  EXCLUDE USING gist (room WITH =, during WITH &&)
);

INSERT INTO bookings (room, during) VALUES ('A101', '[2025-06-01 09:00, 2025-06-01 10:00)');
INSERT INTO bookings (room, during) VALUES ('A101', '[2025-06-01 10:00, 2025-06-01 11:00)');  -- ✓ 首尾相接不算重叠
INSERT INTO bookings (room, during) VALUES ('B202', '[2025-06-01 09:30, 2025-06-01 10:30)');  -- ✓ 不同房间
INSERT INTO bookings (room, during) VALUES ('A101', '[2025-06-01 09:30, 2025-06-01 10:30)');  -- ✗

ERROR:  conflicting key value violates exclusion constraint "bookings_room_during_excl"
DETAIL:  Key (room, during)=(A101, ["2025-06-01 09:30:00+00","2025-06-01 10:30:00+00"))
conflicts with existing key (room, during)=(A101, ["2025-06-01 09:00:00+00","2025-06-01 10:00:00+00")).
ⓘ 为什么要 btree_gist

排他约束要用 GiST 索引来检查 &&（重叠），但 GiST 默认不支持 text 的 =。随发行版自带的 btree_gist 扩展补上了这个能力（第 7 章列出的 45 个自带扩展之一）。左闭右开 [) 是表示时间段的最佳习惯：10:00 结束和 10:00 开始不算冲突。

枚举

第 11 章已经用过枚举（mq.status）。它把列限制在一组固定的值里，排序按声明顺序而不是字母序：

CREATE TYPE order_status AS ENUM ('pending', 'paid', 'shipped', 'delivered');
CREATE TABLE orders (id serial PRIMARY KEY, status order_status NOT NULL DEFAULT 'pending');
INSERT INTO orders (status) VALUES ('paid'), ('pending'), ('delivered'), ('shipped');

INSERT INTO orders (status) VALUES ('refunded');
-- ERROR:  invalid input value for enum order_status: "refunded"

SELECT id, status FROM orders ORDER BY status;           -- pending, paid, shipped, delivered
SELECT id, status FROM orders WHERE status >= 'shipped';  -- shipped、delivered：可以比较“先后”

ALTER TYPE order_status ADD VALUE 'refunded' AFTER 'delivered';   -- 可以加
ALTER TYPE order_status RENAME VALUE 'paid' TO 'payed';           -- 可以改名
SELECT enum_range(NULL::order_status);
-- {pending,payed,shipped,delivered,refunded}
方案优点缺点适合
ENUM 类型紧凑（4 字节）、自带顺序、可读不能删除值，要删只能重建类型；改动需要 DDL几乎不变的状态机
text + CHECK (… IN (…))改约束即可增删值（第 2 章的写法）没有内置顺序偶尔会变的取值
字典表 + 外键值可以带属性（显示名、排序号），运营可在线维护多一次 JOIN经常变、要多语言显示

锁：并发写入的正确姿势

第 2 章演示过：两个事务同时改同一行，后来的会等先来的提交（图 2-6）。但如果“读 → 在应用里计算 → 写回”，即便有这种行锁，也会出事。

丢失更新

Alice 账户里有 100 元。两个请求几乎同时到达：一个扣 10 元，一个扣 30 元。应用的写法是先读余额、在代码里算好、再写回：

-- 会话 A                                   -- 会话 B（晚 0.2 秒开始）
BEGIN;                                      BEGIN;
SELECT balance FROM accounts WHERE id=1;    SELECT balance FROM accounts WHERE id=1;
-- 100，应用算出 100-10=90                  -- 100，应用算出 100-30=70
UPDATE accounts SET balance = 90 WHERE id=1;
COMMIT;                                     UPDATE accounts SET balance = 70 WHERE id=1;
                                            COMMIT;

 balance
---------
      70        ← 应该是 60，A 扣的 10 元凭空消失了

问题在于计算发生在应用里，数据库只看到“把余额设成 90”“把余额设成 70”两条互不相干的指令。两种修复：

  1. 让数据库来算：UPDATE accounts SET balance = balance - 10 WHERE id = 1（第 2 章清单 2.12 就是这么写的）。UPDATE 在行锁下读取最新值再计算，不会丢。能这么写就这么写。
  2. 先锁住再读：业务逻辑复杂、必须在应用里计算时，用 SELECT … FOR UPDATE 在读的时候就加上行锁：
-- 会话 A                                          -- 会话 B
BEGIN;                                             BEGIN;
SELECT balance FROM accounts                       SELECT balance FROM accounts
  WHERE id=1 FOR UPDATE;   -- 100，行被锁住          WHERE id=1 FOR UPDATE;   -- ⏸ 等 A
UPDATE accounts SET balance = 90 WHERE id=1;
COMMIT;                                            -- 解除阻塞，读到 90
                                                   UPDATE accounts SET balance = 60 WHERE id=1;
                                                   COMMIT;

 balance
---------
      60        ✓

不想等：NOWAIT 和 lock_timeout

默认情况下拿不到锁就一直等。有时候宁可立刻失败、给用户提示“稍后再试”：

-- 会话 A 正持有 id=1 的行锁时，会话 B：
SELECT * FROM accounts WHERE id = 1 FOR UPDATE NOWAIT;
-- ERROR:  could not obtain lock on row in relation "accounts"

SET lock_timeout = '500ms';
UPDATE accounts SET balance = 0 WHERE id = 1;
-- （等了 0.5 秒）ERROR:  canceling statement due to lock timeout

第 11 章用到的 SKIP LOCKED 是第三种选择：拿不到锁的行直接跳过。三者对比：

写法遇到被锁的行典型场景
FOR UPDATE一直等扣库存、转账：必须处理这一行
FOR UPDATE NOWAIT立刻报错交互式操作，宁可提示用户也不卡住
SET lock_timeout等一会儿再报错给所有语句一个等待上限，防止雪崩
FOR UPDATE SKIP LOCKED跳过任务队列：随便处理哪一行都行（第 11 章）

死锁

A 给 B 转账、同时 B 给 A 转账，两个事务各自先锁住了一行，然后都去等对方手里的那一行：

-- 会话 A                                            -- 会话 B
BEGIN;                                               BEGIN;
UPDATE accounts SET balance = balance - 10 WHERE id=1;
                                                     UPDATE accounts SET balance = balance - 10 WHERE id=2;
UPDATE accounts SET balance = balance + 10 WHERE id=2;  -- ⏸ 等 B
                                                     UPDATE accounts SET balance = balance + 10 WHERE id=1;  -- ⏸ 等 A

ERROR:  deadlock detected
DETAIL:  Process 258 waits for ShareLock on transaction 809; blocked by process 265.
Process 265 waits for ShareLock on transaction 808; blocked by process 258.
HINT:  See server log for query details.
CONTEXT:  while updating tuple (0,2) in relation "accounts"

Postgres 会定期（默认等待超过 deadlock_timeout = 1 秒后）检查有没有等待的环，发现后取消其中一个事务，另一个就能继续完成。 被取消的那个要由应用重试。预防的办法是所有事务按同样的顺序加锁，比如转账时总是先锁 id 小的那一行： 

-- 不管谁转给谁，先按 id 顺序把两行都锁住
SELECT * FROM accounts WHERE id IN (1, 2) ORDER BY id FOR UPDATE;
UPDATE accounts SET balance = balance - 10 WHERE id = 1;
UPDATE accounts SET balance = balance + 10 WHERE id = 2;
COMMIT;

咨询锁

有时要锁的不是某一行，而是一件“事”：比如“同一时间只能有一个进程在生成月度报表”。咨询锁（advisory lock）就是一个以数字命名、由应用自己约定含义的锁：

SELECT pg_try_advisory_lock(42);     -- t：拿到了；另一个会话再调用会返回 f
-- ……生成报表……
SELECT pg_advisory_unlock(42);

-- 事务级版本：事务结束自动释放，不怕忘记解锁
BEGIN;
SELECT pg_advisory_xact_lock(42);
-- ……
COMMIT;

会话级的咨询锁在会话断开时也会自动释放。它很适合多个应用实例之间的“选主”或防止定时任务重复执行。

隔离级别

第 2 章说过，Postgres 默认是读已提交（READ COMMITTED），此外还有 REPEATABLE READ 和 SERIALIZABLE。 它们的区别在于：并发事务之间，能“看到”对方多少东西。用一个事务里读两次同一行的实验来看： 

-- 会话 A                                           -- 会话 B（0.5 秒后）
BEGIN;  -- 或 BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT balance FROM accounts WHERE id=1;   -- 100
                                                    UPDATE accounts SET balance = 50 WHERE id=1;
SELECT pg_sleep(1.5);
SELECT balance FROM accounts WHERE id=1;   -- ?
COMMIT;

READ COMMITTED                     REPEATABLE READ
 first_read  | 100                  first_read   | 100
 second_read |  50  ← 变了          second_read  | 100  ← 没变
                                    after_commit |  50  ← 事务结束后才看到

可重复读：并发修改会报错

可重复读下，如果你要修改的行在你的快照之后被别人改过，Postgres 不会让你基于旧数据去覆盖它：

-- 会话 A                                           -- 会话 B
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT balance FROM accounts WHERE id=1;   -- 100
                                                    UPDATE accounts SET balance = balance - 30 WHERE id=1;
UPDATE accounts SET balance = balance - 10 WHERE id=1;
-- ERROR:  could not serialize access due to concurrent update

A 必须回滚并重试整个事务。结果余额是 70（只有 B 生效），不会出现基于过期数据的错误写入。

串行化：连写偏斜也能防住

医院规定：任何时候至少要有一位医生值班。Alice 和 Bob 都在值班，两人几乎同时申请下班，各自的事务都先检查“值班人数 ≥ 2”，然后把自己设为下班： 

CREATE TABLE doctors (name text PRIMARY KEY, on_call boolean NOT NULL);
INSERT INTO doctors VALUES ('Alice', true), ('Bob', true);

-- 会话 A（Alice）                                  -- 会话 B（Bob）
BEGIN ISOLATION LEVEL REPEATABLE READ;              BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT count(*) FROM doctors WHERE on_call;  -- 2   SELECT count(*) FROM doctors WHERE on_call;  -- 2
UPDATE doctors SET on_call=false WHERE name='Alice'; UPDATE doctors SET on_call=false WHERE name='Bob';
COMMIT;                                             COMMIT;

 name  | on_call
-------+---------
 Alice | f
 Bob   | f          ← 没有人值班了！

两个事务改的是不同的行，所以既没有行锁冲突，可重复读也不报错。但合起来违反了业务规则 —— 这叫写偏斜（write skew）。换成 SERIALIZABLE： 

ERROR:  could not serialize access due to read/write dependencies among transactions
DETAIL:  Reason code: Canceled on identification as a pivot, during write.
HINT:  The transaction might succeed if retried.

 name  | on_call
-------+---------
 Bob   | t          ← 还有人值班 ✓
 Alice | f

串行化级别会追踪事务之间的读写依赖，发现“不可能按某种先后顺序依次执行得到这个结果”时，就取消其中一个。 Bob 的事务重试时会读到“值班人数 = 1”，从而拒绝下班。

★ 怎么选
  • 大多数场景保持默认的 READ COMMITTED，配合原子更新和 FOR UPDATE。
  • 报表、对账这类需要“同一时刻一致视图”的只读事务，用 REPEATABLE READ。
  • 业务规则跨越多行、很难靠锁表达（排班、额度、库存总量），用 SERIALIZABLE，并且一定要写重试逻辑：捕获 SQLSTATE 40001（serialization_failure）和 40P01（deadlock_detected），回滚后整个事务重来。

小结

  • INSERT … ON CONFLICT 是并发安全的 UPSERT；EXCLUDED 代表被排除的新行，DO UPDATE … WHERE 可以有条件地更新。简单 UPSERT 优先用它，复杂同步用 MERGE。
  • 数组适合简单值的列表，查询用 @> / && 才能走 GIN 索引。
  • 范围类型 + EXCLUDE USING gist 能在数据库层面杜绝时间冲突。
  • 枚举紧凑有序，但不能删除值；经常变的取值用 CHECK 或字典表。
  • “读 → 应用计算 → 写”会丢失更新：用原子 UPDATE 或 SELECT … FOR UPDATE。NOWAIT / lock_timeout / SKIP LOCKED 应对等不起的场景。
  • 死锁由 Postgres 自动检测并取消一方；按固定顺序加锁可以预防。咨询锁用来锁“一件事”。
  • 隔离级别越高能防住的现象越多（不可重复读、丢失更新、写偏斜），代价是要处理串行化失败并重试。
