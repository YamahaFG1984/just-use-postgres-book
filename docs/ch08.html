生成式 AI 与 pgvector

生成式人工智能（gen AI）用专门的模型生成文本、图片、视频等内容。比如大语言模型（LLM）在海量文本上训练，能用英语、日语等自然语言回答问题、对话、完成任务。 这一章我们继续开发第 6 章的电影推荐服务：把电影简介变成向量嵌入存进 Postgres，用向量相似度搜索和检索增强生成（RAG）提供更聪明、更个性化的推荐。

本章目标

  • 理解 LLM 和嵌入模型分别能和 Postgres 怎样配合
  • 搞懂“向量嵌入”到底是什么，为什么相似的内容在向量空间里挨得近
  • 用 Docker 启动带 pgvector 的 Postgres，存储和查询 vector 类型
  • 用余弦距离 <=> 做语义搜索
  • 理解近似最近邻（ANN）与召回率，会用 IVFFlat 和 HNSW 索引并调参
  • 用 Postgres + 嵌入模型 + LLM 搭一个 RAG 原型

Postgres 如何与生成式 AI 配合

电影推荐服务可以用好几种方式结合 gen AI 和 Postgres：最起码，可以把电影简介的向量嵌入存进数据库，让用户用自然语言描述来找电影； 更进一步，可以用 LLM 做一个 AI 智能体，根据用户偏好和 Postgres 里的电影目录给出推荐，甚至按用户的要求增删“想看”清单。 先看看 LLM 和嵌入模型分别怎样与 Postgres 集成。

Postgres 与 LLM

LLM 在海量文本上训练，擅长回答各种通用问题。比如在 ChatGPT 网站上问：“制作《怪物史瑞克》的那家工作室，还做过哪两部电影？” 选用 GPT-4 模型时，回答大意是：“《怪物史瑞克》背后的梦工厂动画（DreamWorks Animation）作品很多，《马达加斯加》和《功夫熊猫》就是其中两部著名作品。”

LLM 提供商一般通过 API 提供模型，比如 OpenAI 的 GPT、Anthropic 的 Claude，用简单的 REST 调用就能访问；Meta 的 Llama、幻方的 DeepSeek 这类免费模型还可以部署在自己的基础设施上。 我们可以借此给推荐服务加一个聊电影的聊天机器人。但 LLM 不止能聊天 —— 它能理解提示词背后的意图，还能调用各种工具替我们干活：

  • Web 工具：每个模型都有知识截止日期（训练数据最后收集的时间），对之后发生的事一无所知；但它能通过 Web 工具上网获取最新信息。
  • Matplotlib：要画图时，模型可以生成用 Matplotlib 绘图的 Python 脚本。
  • 基础设施：LLM 可以连接公有云或本地机房，启动应用实例、跑基准测试、做运维。
  • Jupyter 环境：模型不仅能生成代码给我们，还能在类似 Jupyter 的环境里自己写、测、调试 Python 代码。
  • Postgres：LLM 可以读取私有数据来辅助完成业务任务、扩充知识，也可以替我们操作数据。

本章会在笔记本电脑上跑一个开源 LLM，用 RAG 把 Postgres 里的数据提供给它。

Postgres 与嵌入模型

除了 LLM，gen AI 应用里另一类常用模型是嵌入模型（embedding model）：输入文本或其他数据，输出一个高维的数值向量，叫向量嵌入（vector embedding）。

★ 向量嵌入是什么

向量嵌入是词、句子等数据的数值表示，它捕捉了含义和相互关系。本质上就是一个 n 维坐标，表示这段文本在 n 维空间里的位置。 比如电影《功夫熊猫》的嵌入如果是二维的，可能是 [-1.5, -0.7] —— 可以画在平面上。

  • 维度越多，越能捕捉上下文中的含义。实际的嵌入通常有几百到几千维。比如“panda”可以指以竹子为食、产自中国西南的黑白熊，也可以指那个精通功夫、爱吃包子的动画角色 —— 维度更多的模型能更好地分辨这些细微差别。
  • 嵌入模型还被训练来识别关系。《功夫熊猫》《怪物史瑞克》《马达加斯加》都是梦工厂出品，它们的嵌入会形成一个簇；《玩具总动员》《海底总动员》《怪兽电力公司》出自皮克斯和迪士尼，形成另一个簇。
  • 高维模型还能编码其他关系：上映年份、预算、演员、类型（动画还是恐怖片）……于是电影可以按各种标准在高维空间里聚类。

这和 Postgres 有什么关系？我们可以为数据库里（以及其他文档、数据源里）的私有数据生成嵌入，存进 Postgres，再用向量相似度搜索找出和搜索词相关的数据。比如为电影简介生成嵌入后，推荐服务就能支持：

🔍

语义搜索

按用户的描述找电影，不要求关键词完全一致。

🧩

聚类

找出剧情、类型等方面相关的电影。

🎬

推荐

推荐和用户最近看过的相似的电影。

🤖

RAG

从私有数据里检索相关上下文交给 LLM，让它生成更相关的回答或执行操作。

启动带 pgvector 的 Postgres

pgvector 扩展为 Postgres 提供了存储和查询向量嵌入的基础能力：它引入 vector 数据类型、向量相似度运算符，以及专门的向量索引。 简单说，pgvector 把 Postgres 变成了向量数据库。它可以从扩展仓库、包管理器、二进制包安装，也有打包好的 Docker 镜像 —— 我们用最后这种。

生成嵌入

为私有文本数据生成嵌入，至少要考虑四件事：

  1. 目标数据：要为哪些文本生成嵌入？可以来自文档、数据库记录等。应该挑和语义搜索、RAG 等场景相关的数据。
  2. 嵌入模型：把文本转成向量的模型。有 OpenAI、Anthropic 等提供的专有模型服务，也有能部署在自己机器上的开源模型。另一个关键因素是维度：有的几百维，有的几千维。维度越多，相似度搜索通常越准，但也越耗内存、存储和算力。
  3. 分块（chunking）：把大段文本切成小块再送进模型。块的大小通常用 token（词、子词或符号）衡量，模型一般会给出建议值；也可以按句子或段落切。
  4. 向量数据库：能存储嵌入、支持相似度搜索，还要支持专门的向量索引。

为电影生成嵌入

新版推荐服务的表结构和第 6 章类似，只是把 tsvector 列换成了 vector 列：

CREATE TABLE omdb.movies (
    id BIGINT PRIMARY KEY,
    name TEXT NOT NULL,
    description TEXT NOT NULL,
    movie_embedding VECTOR(1024),    -- 1024 维的向量
    release_date DATE,
    runtime INT,
    budget NUMERIC,
    revenue NUMERIC,
    vote_average NUMERIC,
    votes_count BIGINT
);

vector 类型由 pgvector 提供，括号里指定维数。我们用免费的开源嵌入模型 mxbai-embed-large，可以在本地运行，它生成 1024 维向量，所以列定义为 vector(1024)。 做法是：取每部电影的片名和简介，用空格拼起来送进模型，把得到的 1024 维嵌入存回 movie_embedding 列： 

# 从数据库取出所有电影
movies = database.execute("SELECT id, name, description FROM omdb.movies")

# 逐部电影生成嵌入
for each movie in movies:
    id = movie.id
    name = movie.name
    description = movie.description

    # 片名 + 简介拼在一起
    combined_text = name + " " + description

    # 用模型生成嵌入
    embedding = embedding_model.generate_embedding(combined_text)

    # 把嵌入写回数据库
    database.execute(
        "UPDATE omdb.movies SET movie_embedding = ? WHERE id = ?", embedding, id)

这里没有分块：拼接后的电影介绍本来就很短，已经包含了电影的关键信息；硬要切开反而会丢失上下文，影响相似度搜索的准确性。 这段伪代码可以用任何有 Postgres 驱动和 gen AI 库的语言实现：JavaScript 可以用 node-postgres + LangChain，Java 可以用 Postgres JDBC + Spring AI。

以及一个辅助函数 omdb.get_embedding(input_phrase)：在字典表里查短语，返回它的嵌入；查不到就报错：

CREATE OR REPLACE FUNCTION omdb.get_embedding(input_phrase TEXT)
RETURNS VECTOR(1024) AS $$
DECLARE
    embedding VECTOR(1024);
BEGIN
    SELECT phrase_embedding INTO embedding
    FROM omdb.phrases_dictionary
    WHERE LOWER(phrase) = LOWER(input_phrase);

    IF NOT FOUND THEN
        RAISE EXCEPTION
            'The seach phrase does not exist in the dictionary table.';
    END IF;

    RETURN embedding;
END;
$$ LANGUAGE plpgsql;
ⓘ 为什么要预生成短语的嵌入

真实应用里，用户输入的问题要实时送进嵌入模型。为了让你不用部署模型也能体验，数据集预先为 4 个短语生成了嵌入：
May the force be with you · A movie about a Jedi who fights against the dark side of the force · A pirate captain who sails the seven seas in search of treasure · A clown fish who gets lost in the ocean and tries to find his way home

向量相似度搜索

向量相似度搜索，也叫最近邻搜索或语义搜索，根据向量表示找出数据集中相似或相关的条目。 用户用自然语言提问，应用为问题生成嵌入，和数据库里的嵌入比较，返回最相关的数据：

  1. 用户在推荐服务里输入问题或提示，发给后端。
  2. 后端用生成电影嵌入时用的同一个模型（mxbai-embed-large）把问题转换成嵌入。
  3. 模型返回嵌入。
  4. 后端在 Postgres 里做相似度搜索，把问题的嵌入和 movie_embedding 列比较。
  5. 数据库返回和问题最相关的电影 —— 也就是在高维空间里离问题嵌入最近的那些。
  6. 后端整理结果返回给用户。

（我们用 omdb.get_embedding 查预生成的嵌入代替了第 2、3 步，但那些嵌入也是用 mxbai-embed-large 生成的。）

距离运算符与余弦距离

相似度搜索靠距离函数：在高维空间里离得最近的向量就是最相关的“最近邻”。pgvector 提供了几种距离运算符：

运算符距离索引运算符类说明
<=>余弦距离vector_cosine_ops比较向量的夹角。文本嵌入最常用，尤其是 L2 归一化（长度恒为 1）的嵌入
<->欧几里得距离（L2）vector_l2_ops两点之间的直线距离
<#>负内积vector_ip_ops返回的是内积的相反数，所以同样是越小越相似

mxbai-embed-large 生成的是归一化的嵌入，所以我们用余弦距离。用户搜索“May the force be with you”（愿原力与你同在）：

SELECT id, name, description
FROM omdb.movies
ORDER BY movie_embedding <=> omdb.get_embedding('May the force be with you')
LIMIT 3;

第三部看起来毫不相关，这说明了两点：

  • 和 LLM 一样，嵌入模型也会幻觉（hallucination），产生不准确的结果。
  • 生成嵌入时提供更多上下文，可以减少幻觉。这部电影的简介是空的，嵌入只由片名“On Your Mark”生成，模型很难把它和训练数据有意义地联系起来。

在应用层做相似度搜索时，伪代码很简单 —— 把问题的嵌入作为查询参数传给 Postgres：

# 为短语生成嵌入
embedding = embedding_model.generate_embedding("May the force be with you")

# 创建 SQL 查询
query = query.create(
   "SELECT id, name, description FROM omdb.movies
    ORDER BY movie_embedding <=> ::phrase_embedding
    LIMIT 3;")

# 把嵌入作为参数传入
query.set_param("phrase_embedding", embedding)

# 执行向量相似度搜索
movies = database.execute(query)

换个说法，结果更准

把距离也显示出来：

WITH phrase AS (
  SELECT omdb.get_embedding('May the force be with you') AS embedding
)
SELECT id, name, description, m.movie_embedding <=> p.embedding AS distance
FROM omdb.movies m CROSS JOIN phrase p
ORDER BY distance LIMIT 3;

用 CTE 先取出短语的嵌入，再用 CROSS JOIN 让每部电影都和它配对算距离。结果的距离分别是 0.393、0.404、0.412。这里的余弦距离落在 0~1 之间，越接近 0 越相关。现在把搜索短语换得更具体：

WITH phrase AS (
  SELECT omdb.get_embedding(
    'A movie about a Jedi who fights against the dark side of the force')
     AS embedding
)
SELECT id, name, description, m.movie_embedding <=> p.embedding AS distance
FROM omdb.movies m CROSS JOIN phrase p
ORDER BY distance LIMIT 3;

这次三部全是星战，最近的距离约 0.27，明显比之前的 0.39 更近。想试试别的短语，可以运行仓库里的 similarity_search.ipynb 笔记本（里面也有用 Ollama 在本地启动嵌入模型的说明）。

⚠ 每个嵌入有 4 KB

1024 维 × 每维 4 字节浮点数 + 8 字节头 = 4104 字节（约 4 KB）。 每次搜索都要扫描整个电影目录、对每个 4 KB 的数组算一次余弦距离、再排序。数据量小还行，数据或查询量一涨就撑不住了。

近似最近邻与召回率

pgvector 目前支持两种向量索引：IVFFlat（inverted file with flat compression，倒排文件 + 平坦压缩）和 HNSW（hierarchical navigable small world，分层可导航小世界）。 此外 pgvectorscale 扩展还提供 StreamingDiskANN 索引。

不管选哪种，都要记住：它们和 B-tree、GIN、GiST 的行为不一样，向量索引返回的是近似结果。 用 B-tree 找 revenue > 1000000 的电影，所有匹配行一个不落；但用向量索引找“May the force be with you”相关的电影，它只比较一部分嵌入，结果未必最准。

向量索引做的是近似最近邻（ANN）搜索。所以评估向量索引时，除了性能和大小，还要关注召回率（recall）：返回的“最近”嵌入中，有多少是真正的最近邻。 全表扫描做的是精确最近邻（ENN）搜索，和每一个嵌入都比较过，召回率是 1。

IVFFlat 索引

IVFFlat 把向量嵌入分成若干列表（list），也叫簇（cluster），每个列表里的嵌入彼此相似。 每个列表有一个质心（centroid），代表簇的中心点，由对嵌入运行 k-means 聚类算出。算好质心后，每个嵌入被分配到离它最近的质心所在的列表。

质心不仅在建索引时用来分配嵌入，搜索时也用：Postgres 先计算查询嵌入和每个质心的距离，然后只在质心最近的那个列表里继续搜索。 对“May the force be with you”来说，存着星战电影的列表 1 的质心最近，其他列表都被跳过。

创建和使用索引

CREATE INDEX movie_embeddings_ivfflat_idx
ON omdb.movies
USING ivfflat (movie_embedding vector_cosine_ops) WITH (lists = 5);
  • vector_cosine_ops：建索引时用余弦距离把嵌入分配到各个列表。查询也必须用同一种距离（<=>），换成别的运算符索引就用不上。
  • WITH (lists = 5)：分成 5 个列表。pgvector 文档建议：100 万行以内从 行数 / 1000 开始试，超过 100 万行用 sqrt(行数)。

建好后再看执行计划 —— 仍然是 Seq Scan！

⚠ 规划器不认 omdb.get_embedding()

查询用了余弦距离、有 ORDER BY 和 LIMIT，看起来都对，但规划器还是忽略了索引，原因是调用了 omdb.get_embedding(…) 函数。 写书时，规划器期望更简单的查询形式。把函数换成直接查字典表的子查询就好了： 

EXPLAIN (analyze, costs off)
SELECT id, name, description
FROM omdb.movies
ORDER BY movie_embedding <=>
    (SELECT phrase_embedding
    FROM omdb.phrases_dictionary
    WHERE phrase = 'May the force be with you')
LIMIT 3;

   InitPlan 1
     -> Seq Scan on phrases_dictionary (actual time=0.022..0.023 rows=1 loops=1)
           Filter: (phrase = 'May the force be with you'::text)
           Rows Removed by Filter: 3
   -> Index Scan using movie_embeddings_ivfflat_idx on movies
        (actual time=1.400..1.434 rows=3 loops=1)

先在字典表里查到短语的嵌入（InitPlan），再用 IVFFlat 索引做 Index Scan。约 1 ms vs 约 50 ms。

💡 应用层不用改

如果应用像前面的伪代码那样，先在应用里生成嵌入、再把它作为参数传给 ORDER BY movie_embedding <=> $1，规划器能轻松识别出可以用 IVFFlat 索引，应用这边什么都不用改。

ⓘ IVFFlat 的局限
  • 需要多少 probes 才能有好的召回率，取决于数据量、列表数和具体查询。务必充分测试，在召回率和性能之间找平衡。
  • IVFFlat 最适合在已有数据上建索引、之后数据变化不大的场景。质心只在建索引时算一次，之后不会更新。数据大量增长或频繁更新后，新嵌入仍按旧质心分配，分布可能不再理想，召回率下降。这时可以重建索引，或者换用 HNSW —— 它更灵活，甚至可以在空表上建。

HNSW 索引

HNSW 构建一个多层图：每个节点代表一个向量，边连接相近的向量。上层稀疏、下层稠密，出现在高层的节点也出现在所有更低的层。

搜索总是从最高层（第 3 层）开始，逐层下降，每层只走离查询嵌入最近的节点。 搜“May the force be with you”时，先在第 3 层计算它和 Iron Man、Avengers、A New Hope、The Mandalorian 四个节点的距离，发现后两者最近； 于是在第 2 层只在星战那片区域继续，漫威电影不再访问；最后在第 1 层发现更多星战电影，整理出最终结果。

创建和使用索引

先删掉 IVFFlat 索引（同一张表没必要有两个向量索引），再建 HNSW：

DROP INDEX omdb.movie_embeddings_ivfflat_idx;

CREATE INDEX movie_embeddings_hnsw_idx
ON omdb.movies
USING hnsw (movie_embedding vector_cosine_ops)
WITH (m = 8, ef_construction = 16);
参数阶段含义默认调大的效果
m建索引每个节点最多有几条边16图更稠密，召回更好、跳数更少；但建索引更慢、更占内存
ef_construction建索引构建时候选列表的大小：遍历时保存的最近候选，结束后截断成 m 个最近邻64考虑的候选更多，索引质量更好；建索引更慢
hnsw.ef_search查询搜索时保存的候选节点数40探索更多可能的近邻，召回更好；查询更慢

我们的数据集比较小，所以 m 设成 8；ef_construction 设成 16，保证至少是 m 的两倍。

提高搜索时的召回率：ef_search

上线前应该用更多用户可能输入的短语充分测试，调整 m 和 ef_construction，在召回率、性能、索引大小之间找平衡。 假设上线后发现某些短语召回率不好，除了重建索引，还可以不动索引、调大查询时的 hnsw.ef_search。 它可以用 SET hnsw.ef_search = 值 对整个会话生效，也可以在事务里用 SET LOCAL 只对一个查询生效：

  FROM omdb.phrases_dictionary

  'A movie about a Jedi who fights against the dark side of the force')

IVFFlat 还是 HNSW？

电影目录会不断增长，我们希望这对召回率和搜索性能影响很小，所以推荐服务选 HNSW。

实现 RAG

pgvector 很好地说明了扩展生态为什么对 Postgres 的普及如此重要：启用它，Postgres 就成了向量数据库，能存嵌入、做相似度搜索、用专门的索引优化。 现在推荐服务已经能根据用户的提示推荐电影了。但如果我们想更进一步 —— 不只是检索出数据展示给用户，而是把检索到的数据作为上下文交给 LLM，让它据此生成回答或执行任务呢？这就是 RAG（Retrieval-Augmented Generation，检索增强生成）。

有了 RAG，LLM 就成了应用的一个组件：和用户交互，同时考虑我们的私有数据和知识库。收到用户提示后：

  • 检索上下文：用用户的提示在私有数据里找相关信息。
  • 增强 LLM：把检索到的上下文交给 LLM，扩充它的知识或影响它的行为。
  • 生成回答：让 LLM 完成任务（如果需要）并生成最终回答。
  1. 用户打开聊天机器人提问，问题从前端发到后端。
  2. 后端调用“获取上下文”模块，从 Postgres 的私有数据中检索上下文。
  3. 模块用嵌入模型为问题生成嵌入。
  4. 嵌入模型返回嵌入。
  5. 模块用这个嵌入在 Postgres 里做相似度搜索，找出和问题相关的电影。
  6. Postgres 返回结果，这就是要交给 LLM 的上下文。
  7. 模块把上下文返回给后端。
  8. 后端把问题和上下文一起交给 LLM，让它生成推荐。如果需要，还可以把之前的对话历史一起带上。
  9. LLM 生成回答。
  10. 回答发回前端，显示在聊天窗口里。

和 LLM 交互

笔记本定义了 answer_question(question, context) 函数，让 TinyLlama 结合提供的上下文回答用户问题：

def answer_question(question, context):
    # 通过 LangChain 的 Ollama 接口连接 tinyllama 模型
    llm = OllamaLLM(model="tinyllama", temperature=0.6)

    # 结合上下文生成给 LLM 的最终提示词
    prompt = f"""
    You're a movie expert and your task is to answer questions about movies
    based on the provided context.

    This is the user's question: {question}
    Consider the following context to provide a detailed and
    accurate answer: {context}

    The context includes the following details for each movie:
    - "Title" of the movie
    - "Vote Average" - the average rating of the movie
    - "Budget" - the budget allocated for the movie in US dollars
    - "Revenue" - the total revenue generated by the movie in US dollars
    - "Release Date" - the date the movie was released

    Respond in an engaging style that inspires the user to watch the movies.
    """

    # 调用 LLM，生成回答
    response = llm.invoke(prompt)
    return response
  1. 用 LangChain 框架的 OllamaLLM 接口连接 TinyLlama。temperature 控制回答的随机性。
  2. 组装 prompt：用 {question} 放入用户原始问题，{context} 放入从 Postgres 检索到的上下文，并说明 LLM 该如何使用这些信息、生成什么样的回答。
  3. 调用 llm.invoke(prompt) 生成回答。

为 LLM 检索上下文

def retrieve_context_from_postgres(question):
    # 连接带 pgvector 扩展的 Postgres 实例
    db_params = {
    "host": "localhost",
    "port": 5432,
    "dbname": "postgres",
    "user": "postgres",
    "password": "password"
    }
    conn = psycopg2.connect(**db_params)
    cursor = conn.cursor()

    # 通过 OllamaEmbeddings 接口连接嵌入模型
    embedding_model = OllamaEmbeddings(model="mxbai-embed-large:335m")

    # 为用户的问题生成嵌入
    embedding = embedding_model.embed_query(question)

    # 做向量相似度搜索，找出相关电影
    query = """
    SELECT name, vote_average, budget, revenue, release_date
    FROM omdb.movies
    ORDER BY movie_embedding <=> %s::vector LIMIT 3
    """

    cursor.execute(query, (embedding, ))

    context = ""

    # 把查询结果拼成上下文
    for row in cursor.fetchall():
        context += f"Movie title: {row[0]}, Vote Average: {row[1]}"
        context += f", Budget: {row[2]}, Revenue: {row[3]}"
        context += f", Release Date: {row[4]}\n"

    cursor.close()
    conn.close()

    return context

连接本地 Postgres → 用嵌入模型为问题生成嵌入 → 相似度搜索取最相关的三部电影（%s::vector 把参数转成 vector 类型）→ 把结果拼成给 LLM 的上下文。

embeddings_generator.ipynb：生成数据集里的嵌入

from langchain_ollama import OllamaEmbeddings
import psycopg2

embedding_model = OllamaEmbeddings(model="mxbai-embed-large:335m")
conn = psycopg2.connect(host="localhost", port=5432, dbname="postgres",
                        user="postgres", password="password")
cursor = conn.cursor()

# 先清空旧的嵌入
cursor.execute("UPDATE omdb.movies SET movie_embedding = NULL")
conn.commit()

cursor.execute("SELECT id, name, description FROM omdb.movies")
movies = cursor.fetchall()

counter = 0
for movie in movies:
    id, name, description = movie
    combined_text = f"{name} {description}"
    embedding = embedding_model.embed_query(combined_text)

    cursor.execute(
        "UPDATE omdb.movies SET movie_embedding = %s WHERE id = %s",
        (embedding, id)
    )

    counter += 1
    if counter % 100 == 0:      # 每 100 部提交一次
        print(f"Processed {counter} movies")
        conn.commit()

conn.commit()

# 再为字典表里的 4 个短语生成嵌入
phrases = [
    'May the force be with you',
    'A movie about a Jedi who fights against the dark side of the force',
    'A pirate captain who sails the seven seas in search of treasure',
    'A clown fish who gets lost in the ocean and tries to find his way home'
]
for phrase in phrases:
    embedding = embedding_model.embed_query(phrase)
    cursor.execute(
        "INSERT INTO omdb.phrases_dictionary (phrase, phrase_embedding) VALUES (%s, %s)",
        (phrase, embedding)
    )
conn.commit()

新句子的嵌入：用 fastembed 在 Python 里直接跑同一个模型

fastembed 用 ONNX Runtime 在 CPU 上运行嵌入模型，不需要 Ollama、Docker 或 GPU，pip install 就能用。 它支持 mixedbread-ai/mxbai-embed-large-v1，就是 Ollama 里 mxbai-embed-large 的同一个模型，所以生成的向量能直接和数据集里的嵌入比较： 

pip install fastembed "psycopg[binary]"

# search_without_ollama.py
import psycopg
from fastembed import TextEmbedding

# 第一次运行会下载模型（约 1.3 GB），之后从缓存加载
model = TextEmbedding("mixedbread-ai/mxbai-embed-large-v1")

def embed(text):
    vec = next(iter(model.embed([text])))
    return "[" + ",".join(str(float(x)) for x in vec) + "]"   # pgvector 的文本格式

phrase = "A team of superheroes come together to save the world"
with psycopg.connect("postgresql://postgres:password@localhost:5432/postgres") as conn:
    rows = conn.execute(
        "SELECT name FROM omdb.movies ORDER BY movie_embedding <=> %s::vector LIMIT 3",
        (embed(phrase),),
    ).fetchall()
    for (name,) in rows:
        print(name)

ⓘ 关于这组数字

受测试机内存所限（完整精度的模型加载时内存占用超过 1.3 GB，测试机放不下），上表用的是同一模型仓库里的 int8 量化版（onnx/model_quantized.onnx）， 搜索结果是用 numpy 在数据集的 4224 个电影向量上按余弦距离排序得到的，和 pgvector 的 <=> 是同一种计算。 量化会带来少量误差，用 fastembed 默认的完整精度模型，结果只会和数据集更接近。内存小于 2 GB 的机器，也可以直接用 onnxruntime 加载量化版。

RAG 的生成部分：换成云端 LLM

RAG 里负责“组织语言”的 LLM 和嵌入模型是两回事，可以独立替换。把 rag.ipynb 里的 answer_question 换成调用任意云端聊天模型即可，检索部分（retrieve_context_from_postgres）不用动。以 Anthropic 的 Python SDK 为例： 

# pip install anthropic   需要在环境变量 ANTHROPIC_API_KEY 里配置 API Key
import anthropic

client = anthropic.Anthropic()

def answer_question(question, context):
    prompt = f"""You're a movie expert. Answer the user's question using ONLY the movies in the context.
If the context is not enough, say so instead of making things up.

Question: {question}
Context (title, vote average, budget, revenue, release date, description):
{context}"""
    msg = client.messages.create(
        model="claude-haiku-5-5",
        max_tokens=1024,
        messages=[{"role": "user", "content": prompt}],
    )
    return msg.content[0].text

这段代码没有在本站实测（需要付费的 API Key），用 OpenAI 等其他服务时写法类似。 云端大模型比 TinyLlama 强得多，上文提到的“对《聚魂棺》的描述完全是错的”这类问题会少很多，但仍要在提示词里要求它只依据上下文回答。 另外要意识到：检索到的上下文会发送给第三方服务，涉及私有数据时要先确认是否允许。

如果连嵌入模型也要换

想改用云端嵌入 API（如 OpenAI 的 text-embedding-3-small，或 Anthropic 推荐的 Voyage AI），记住一条：查询向量和数据向量必须来自同一个模型。不同模型的向量空间互不相通，维数也往往不同。 所以要先 ALTER TABLE omdb.movies ALTER COLUMN movie_embedding TYPE vector(新维数)（旧数据维数不符时要先清空该列）， 再按 embeddings_generator.ipynb 的循环，用新模型把 4224 部电影的嵌入全部重新生成，索引也要重建。

小结

  • Postgres 可以和 LLM、嵌入模型配合，构建推荐服务、自主 AI 智能体等新型 gen AI 应用。
  • 向量嵌入是文本含义的数值坐标；相似的内容在高维空间里离得近。
  • pgvector 把 Postgres 变成向量数据库：vector 类型、<=> 等距离运算符、专用索引。
  • 向量索引做近似搜索，要关注召回率。IVFFlat（lists / probes）小而快建、适合静态数据；HNSW（m / ef_construction / ef_search）准而快查、适合持续增长的数据。
  • Postgres 是实现 RAG 等 gen AI 场景的强大向量数据库：检索上下文 → 增强提示词 → LLM 生成回答。

  2. 把清单 8.5 的 <=> 换成 <->（欧氏距离）和 <#>（负内积），比较结果顺序。为什么对归一化的向量，三者排序基本一致？
    参考答案 
    WITH p AS (SELECT omdb.get_embedding('May the force be with you') AS e)
SELECT name,
       movie_embedding <=> e AS cosine,
       movie_embedding <-> e AS l2,
       movie_embedding <#> e AS neg_inner
FROM omdb.movies, p
ORDER BY movie_embedding <=> e LIMIT 3;

                        name                    | cosine |   l2   | neg_inner
--------------------------------------------+--------+--------+-----------
 Star Wars: Episode VI - Return of the Jedi | 0.3926 | 0.8861 |   -0.6074
 The Acolyte                                | 0.4038 | 0.8987 |   -0.5962
 On Your Mark                               | 0.4117 | 0.9074 |   -0.5883

    分别按三种运算符取前 10 名，顺序完全相同。因为 mxbai-embed-large 输出的向量都已归一化（vector_norm 全是 1.0000）。 对长度为 1 的向量：内积就等于余弦相似度，所以 <#> = −cos = 余弦距离 − 1；欧氏距离满足 L2² = 2 − 2·cos（验算：0.8861² ≈ 0.7852 = 2 × 0.3926）。 三者都是余弦距离的单调函数，排序必然一致。这种情况下用 <#> 计算量最小。
