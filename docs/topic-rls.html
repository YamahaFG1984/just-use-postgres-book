行级安全 RLS

做 SaaS 时，经常是几百个客户（租户）的数据放在同一张表里，靠一列 tenant_id 区分。 只要某个查询忘了写 WHERE tenant_id = …，A 公司就能看到 B 公司的数据。 行级安全（Row-Level Security，RLS）把这条过滤规则交给数据库：哪怕应用忘了写，数据库也会替你加上。

ⓘ 本页的例子都实际运行过

输出均在 Postgres 17.2 上实测。RLS 要用普通角色来演示，因为超级用户永远不受 RLS 约束（后面会讲）。例子用 SET ROLE 在同一个 psql 里切换身份。

本页目标

  • 理解 RLS 解决什么问题：把“只能看自己的数据”从应用代码挪进数据库
  • 开启 RLS、编写策略，分清 USING 和 WITH CHECK
  • 在连接池环境里用 SET LOCAL 安全地传递“当前租户”
  • 知道哪些角色会绕过 RLS：超级用户、表的所有者、BYPASSRLS、视图
  • 组合多条策略，并给策略涉及的列建索引

为什么需要 RLS

第 2 章讲过权限（GRANT）：它控制一个角色能不能访问某张表。RLS 则更细一层，控制能访问表里的哪些行。 两者是叠加关系：先要有表的权限，RLS 再决定其中哪些行可见、可改。

准备数据和应用角色

CREATE DATABASE rlstopic;
\c rlstopic

CREATE TABLE tenants (id int PRIMARY KEY, name text);
INSERT INTO tenants VALUES (1, '咖啡店'), (2, '书店');

CREATE TABLE notes (
  id serial PRIMARY KEY,
  tenant_id int NOT NULL REFERENCES tenants,
  title text NOT NULL
);
INSERT INTO notes (tenant_id, title) VALUES
  (1, '采购咖啡豆'), (1, '招聘咖啡师'), (2, '盘点库存'), (2, '新书上架');

-- 应用连接数据库用的角色：不是超级用户，也不是表的所有者
CREATE ROLE app_user LOGIN PASSWORD 'app';
GRANT SELECT, INSERT, UPDATE, DELETE ON notes TO app_user;
GRANT USAGE ON SEQUENCE notes_id_seq TO app_user;

现在切换成 app_user，它能看到所有行，因为还没开启 RLS：

SET ROLE app_user;
SELECT * FROM notes;

 id | tenant_id |   title
----+-----------+------------
  1 |         1 | 采购咖啡豆
  2 |         1 | 招聘咖啡师
  3 |         2 | 盘点库存
  4 |         2 | 新书上架
(4 rows)

开启 RLS：默认拒绝

RESET ROLE;                                    -- 切回 postgres
ALTER TABLE notes ENABLE ROW LEVEL SECURITY;

SET ROLE app_user;
SELECT * FROM notes;

 id | tenant_id | title
----+-----------+-------
(0 rows)

一行都看不到了。这是 RLS 的重要设计：开启之后、还没有任何策略时，默认拒绝一切。 它不会报错，只是“什么都没有”。安全上这是对的：忘了写策略的后果是看不到数据，而不是看到所有数据。

第一条策略：按租户隔离

策略需要知道“当前是哪个租户”。最常见的做法是用一个自定义配置参数：名字里带一个点（如 app.tenant_id）就可以随意 SET， 再在策略里用 current_setting() 读出来： 

RESET ROLE;
CREATE POLICY tenant_isolation ON notes
  USING (tenant_id = current_setting('app.tenant_id', true)::int);
  • CREATE POLICY 名字 ON 表：不写 FOR … 时对 SELECT、INSERT、UPDATE、DELETE 全部生效。
  • USING (…)：一个布尔表达式，只有结果为 true 的行才对当前用户可见。
  • current_setting('app.tenant_id', true)：第二个参数 true 表示“没设置过就返回 NULL，不要报错”。tenant_id = NULL 不是 true，于是一行也看不到。
SET ROLE app_user;
SELECT * FROM notes;              -- (0 rows)  还没告诉数据库“我是谁”

SET app.tenant_id = '1';
SELECT * FROM notes;

 id | tenant_id |   title
----+-----------+------------
  1 |         1 | 采购咖啡豆
  2 |         1 | 招聘咖啡师
(2 rows)

SET app.tenant_id = '2';
SELECT * FROM notes;

 id | tenant_id |  title
----+-----------+----------
  3 |         2 | 盘点库存
  4 |         2 | 新书上架
(2 rows)

同一条 SQL，不同的租户看到不同的行。用 EXPLAIN 可以看到数据库到底做了什么：

EXPLAIN (costs off) SELECT * FROM notes WHERE title LIKE '%书%';

 Seq Scan on notes
   Filter: ((tenant_id = (current_setting('app.tenant_id'::text, true))::integer)
            AND (title ~~ '%书%'::text))

写入：USING 和 WITH CHECK

策略同样管写入。当前租户是 2，试着动租户 1 的数据：

-- 当前 app.tenant_id = '2'
INSERT INTO notes (tenant_id, title) VALUES (1, '偷偷写到咖啡店');
-- ERROR:  new row violates row-level security policy for table "notes"

UPDATE notes SET title = 'x' WHERE tenant_id = 1;   -- UPDATE 0   看不到的行改不了
DELETE FROM notes WHERE id = 1;                     -- DELETE 0   也删不了

UPDATE notes SET tenant_id = 1 WHERE id = 3;        -- 把自己的行“送”给别人
-- ERROR:  new row violates row-level security policy for table "notes"

INSERT INTO notes (tenant_id, title) VALUES (2, '书店的新笔记') RETURNING *;
--  6 |  2 | 书店的新笔记     ✓ 写自己的租户没问题

注意 UPDATE / DELETE 别人的数据不报错，只是影响 0 行，因为那些行对你来说“不存在”。 而 INSERT 和“把行改成别的租户”会直接报错。这是两种不同的检查（新行的 id 是 6 而不是 5，是因为失败的那次 INSERT 已经消耗了序列值 5，序列不会回滚）：

我们的策略只写了 USING，没写 WITH CHECK。这时 Postgres 会把 USING 的表达式同时当作 WITH CHECK 使用，所以写入也被约束住了。 需要两者不同时可以分开写，例如“可以读到全公司的公告，但只能写自己部门的”： 

CREATE POLICY p ON announcements
  USING (true)                                         -- 读：都能看
  WITH CHECK (dept_id = current_setting('app.dept_id', true)::int);  -- 写：只能写自己部门

在应用里设置“当前租户”

一定要用 SET LOCAL

普通的 SET 在整个连接里一直有效。而应用几乎都在用连接池（见专题 5）：一个请求用完的连接会被交给下一个请求。 如果上一个请求 SET 了租户 1，下一个请求又恰好忘了 SET，它就会以租户 1 的身份运行。 

BEGIN;
SET LOCAL app.tenant_id = '1';
SELECT count(*) FROM notes;     -- 2
COMMIT;
SELECT count(*) FROM notes;     -- 0   事务一结束，设置就没了

应用驱动里通常用参数化查询来传值，而 SET 语句不支持 $1 这样的参数。这时用等价的函数 set_config(名字, 值, is_local)，第三个参数 true 就是 LOCAL： 

BEGIN;
SELECT set_config('app.tenant_id', '2', true);   -- 应用里写成 set_config('app.tenant_id', $1, true)
SELECT title FROM notes;
COMMIT;

    title
--------------
 盘点库存
 新书上架
 书店的新笔记
(3 rows)
⚠ 租户 ID 只能来自服务器端

设置给 app.tenant_id 的值，必须来自服务器验证过的登录信息（session、JWT 里的声明），绝不能直接取请求参数。 否则用户把 URL 里的 tenant=1 改成 2，RLS 会忠实地把租户 2 的数据给他。RLS 只负责执行规则，“你是谁”仍然要由应用来认证。

坑：RESET 之后是空字符串，不是 NULL

一个自定义参数只要在会话里被设置过，之后再 RESET（或 SET LOCAL 所在的事务结束），它的值会变成空字符串，而 ''::int 会报错：

SET app.tenant_id = '1';
RESET app.tenant_id;
SELECT current_setting('app.tenant_id', true) IS NULL AS is_null,
       current_setting('app.tenant_id', true) = ''    AS is_empty;
--  is_null | is_empty
--  f       | t

SELECT * FROM notes;
-- ERROR:  invalid input syntax for type integer: ""

报错虽然不会泄露数据，但会让请求莫名其妙地失败。用 nullif 把空字符串变成 NULL，策略就稳妥了：

ALTER POLICY tenant_isolation ON notes
  USING (tenant_id = nullif(current_setting('app.tenant_id', true), '')::int);

SELECT * FROM notes;   -- (0 rows)   不再报错

顺手还可以把租户设为列的默认值，应用插入时就不必再写 tenant_id：

ALTER TABLE notes ALTER COLUMN tenant_id
  SET DEFAULT nullif(current_setting('app.tenant_id', true), '')::int;

BEGIN;
SET LOCAL app.tenant_id = '2';
INSERT INTO notes (title) VALUES ('不用写 tenant_id') RETURNING tenant_id, title;
--  2 | 不用写 tenant_id
COMMIT;

谁不受 RLS 约束

这是 RLS 最容易踩的坑：你用来测试的那个账号，可能根本不受 RLS 约束，于是你以为“策略不生效”。

超级用户与表的所有者

以 postgres（超级用户，也是表的所有者）身份查询，策略完全不起作用：

RESET ROLE;
SELECT count(*) FROM notes;                     -- 5   全部行
ALTER TABLE notes FORCE ROW LEVEL SECURITY;
SELECT count(*) FROM notes;                     -- 5   超级用户连 FORCE 也无视

换一个普通角色当所有者，就能看到 FORCE 的作用：

ALTER TABLE notes NO FORCE ROW LEVEL SECURITY;
CREATE ROLE app_owner LOGIN;
ALTER TABLE notes OWNER TO app_owner;

SET ROLE app_owner;
SELECT count(*) FROM notes;                     -- 5   所有者默认绕过 RLS
RESET ROLE;

ALTER TABLE notes FORCE ROW LEVEL SECURITY;
SET ROLE app_owner;
SELECT count(*) FROM notes;                     -- 0   FORCE 之后，所有者也要遵守策略
RESET ROLE;
★ 推荐的角色划分
  • 迁移角色（如 app_owner）：拥有表，只在部署时用来执行建表、改表。
  • 应用角色（如 app_user）：只有 SELECT / INSERT / UPDATE / DELETE 权限，不拥有任何表，应用日常用它连接。
  • 永远不要让应用用超级用户连接数据库。用 postgres 连接，RLS 就形同虚设。

BYPASSRLS 与 row_security

CREATE ROLE reporter LOGIN BYPASSRLS;     -- 后台报表、跨租户统计用
GRANT SELECT ON notes TO reporter;
SET ROLE reporter;
SELECT count(*) FROM notes;               -- 5
RESET ROLE;

普通角色想“关掉 RLS”是不行的。把 row_security 设成 off，查询不会悄悄返回全部数据，而是直接报错：

SET ROLE app_user;
SET row_security = off;
SELECT count(*) FROM notes;
-- ERROR:  query would be affected by row-level security policy for table "notes"

这个设置主要给 pg_dump 用：它在备份时把 row_security 设为 off，确保要么备份到全部数据，要么报错，而不是悄无声息地只备份出一部分（见专题 6）。

视图

视图默认以视图所有者的权限访问底层表。如果视图是 postgres 建的，通过它查询就绕过了 RLS：

CREATE VIEW notes_v AS SELECT id, tenant_id, title FROM notes;   -- 以 postgres 身份创建
GRANT SELECT ON notes_v TO app_user;

SET ROLE app_user;
SELECT count(*) FROM notes_v;            -- 5   ✗ 漏了！
RESET ROLE;

ALTER VIEW notes_v SET (security_invoker = true);   -- Postgres 15+
SET ROLE app_user;
SELECT count(*) FROM notes_v;            -- 2   ✓ 按查询者本人的身份检查

组合多条策略

一张表可以有多条策略。默认的策略是 PERMISSIVE（宽松）的，多条之间是 OR：满足任意一条就能看到。 标成 RESTRICTIVE（限制）的策略之间、以及它和宽松策略之间是 AND：必须同时满足。

例子：给 notes 加一个 archived 列，规定 app_user 读取时看不到已归档的笔记：

ALTER TABLE notes ADD COLUMN archived boolean NOT NULL DEFAULT false;
UPDATE notes SET archived = true WHERE id = 4;     -- 归档“新书上架”

CREATE POLICY hide_archived ON notes
  AS RESTRICTIVE           -- 限制策略：和租户策略 AND
  FOR SELECT               -- 只管读
  TO app_user              -- 只对这个角色生效
  USING (NOT archived);

SET ROLE app_user;
SET app.tenant_id = '2';
SELECT id, title, archived FROM notes;

 id |    title     | archived
----+--------------+----------
  3 | 盘点库存     | f
  6 | 书店的新笔记 | f
(2 rows)

策略的完整语法就是这几个部分的组合：

CREATE POLICY 名字 ON 表
  [ AS { PERMISSIVE | RESTRICTIVE } ]                  -- 默认 PERMISSIVE
  [ FOR { ALL | SELECT | INSERT | UPDATE | DELETE } ]  -- 默认 ALL
  [ TO { 角色 | PUBLIC | CURRENT_USER } [, ...] ]      -- 默认 PUBLIC（所有角色）
  [ USING ( 过滤已有行的条件 ) ]
  [ WITH CHECK ( 检查新行的条件 ) ];

另一种身份：每个数据库用户只看自己的行

如果每个最终用户都有自己的数据库角色（内部工具、数据分析平台常这样），可以直接用 current_user，不需要自定义参数：

CREATE TABLE diary (
  id serial PRIMARY KEY,
  owner name NOT NULL DEFAULT current_user,
  body text
);
ALTER TABLE diary ENABLE ROW LEVEL SECURITY;
CREATE POLICY own_rows ON diary USING (owner = current_user);
-- （给 alice、bob 授权的 GRANT 语句省略）

SET ROLE alice;  INSERT INTO diary (body) VALUES ('alice 的日记');  RESET ROLE;
SET ROLE bob;    INSERT INTO diary (body) VALUES ('bob 的日记');
SELECT * FROM diary;
--  2 | bob   | bob 的日记          只看到自己的

INSERT INTO diary (owner, body) VALUES ('alice', '冒充 alice');
-- ERROR:  new row violates row-level security policy for table "diary"

查看一张表上有哪些策略：psql 里 \d notes 的末尾会列出 Policies，或者查询系统视图 pg_policies。

性能：给策略用到的列建索引

策略只是一个附加的 WHERE 条件，所以第 4 章的规则同样适用：条件里的列没有索引，就得全表扫描。50 万行、1000 个租户的 notes 表：

-- 当前租户 42，没有索引
EXPLAIN ANALYZE SELECT count(*) FROM notes;
--  Parallel Seq Scan on notes
--    Filter: ((NOT archived) AND (tenant_id = (NULLIF(current_setting(…))…)
--    Rows Removed by Filter: 166502
--  Execution Time: 75.867 ms

CREATE INDEX ON notes (tenant_id);

EXPLAIN ANALYZE SELECT count(*) FROM notes;
--  Bitmap Heap Scan on notes
--    ->  Bitmap Index Scan on notes_tenant_id_idx
--          Index Cond: (tenant_id = (NULLIF(current_setting(…))…)
--  Execution Time: 0.700 ms
情况执行时间
没有 tenant_id 索引（全表扫描 50 万行）75.9 ms
有 tenant_id 索引0.7 ms

current_setting() 是 STABLE 函数，在一条语句里结果不变，所以规划器可以把它当成常量去用索引。 多租户表的复合索引一般把 tenant_id 放在最左边，如 (tenant_id, created_at)，因为每个查询都会带上它（第 4 章“最左前缀”规则）。 策略里尽量避免写子查询或复杂函数，它们会对每一行都执行一次。

RLS 管不到的地方

  • 唯一约束和外键会“泄露存在性”：如果 email 列在整张表上唯一，租户 2 插入一个租户 1 已经用过的 email 会报唯一冲突，从而得知它存在。多租户表的唯一约束通常应包含 tenant_id，如 UNIQUE (tenant_id, email)。
  • RLS 不加密：能拿到超级用户、能读数据文件或备份的人，照样看得到所有数据。
  • 认证在应用：RLS 只保证“按 app.tenant_id 过滤”，这个值对不对由应用负责。
  • TRUNCATE、表结构修改不受 RLS 管，它们由普通的表权限控制，应用角色不该有这些权限。

小结

  • RLS 控制“表里哪些行”能被访问，和控制“哪些表”的 GRANT 叠加生效。
  • ENABLE ROW LEVEL SECURITY 之后默认拒绝一切，再用 CREATE POLICY 放行。
  • USING 过滤已有的行（看不到就改不了、删不了），WITH CHECK 检查新写入的行（不满足就报错）；只写 USING 时它兼任 WITH CHECK。
  • 用 SET LOCAL 或 set_config(…, true) 在事务里设置当前租户，避免在连接池里串号；用 nullif(…, '') 防止空字符串报错。
  • 超级用户、表的所有者（除非 FORCE）、BYPASSRLS 角色和普通视图都会绕过 RLS。应用必须用一个普通角色连接。
  • 宽松策略之间是 OR，限制策略是 AND。
  • 给策略用到的列（通常是 tenant_id）建索引。

动手练习

  1. 按本页步骤建好 notes 表，然后故意用 postgres 身份测试策略，体会“为什么策略好像没生效”。
  2. 给 notes 增加一条策略：app.role 为 'admin' 时可以看到本租户已归档的笔记（提示：再写一条针对归档的宽松策略，或者修改 hide_archived 的条件）。
  3. 建一张 users(tenant_id, email) 表，分别用 UNIQUE (email) 和 UNIQUE (tenant_id, email) 测试，观察跨租户插入同一个 email 时的区别。
  4. 写一个 notes_summary 视图统计每个租户的笔记数，分别在有、没有 security_invoker 时用 app_user 查询它。
  5. 用你熟悉的语言写一个请求处理函数：开启事务 → set_config('app.tenant_id', $1, true) → 查询 → 提交（可参考专题 5）。
