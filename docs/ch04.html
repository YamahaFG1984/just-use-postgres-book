第 4 章

索引

遇到慢查询，人们第一个想到的优化手段往往就是索引。它在很多场景下效果太好了，以至于我们常常忘了别的优化办法。 所以索引大概是仅次于表、我们创建得最多的数据库对象。 这一章以一款全球玩家同场竞技的多人在线游戏为例，学习何时、如何使用各种索引，让玩家即使在高峰期也能流畅游戏。

本章目标

  • 理解索引为什么快：O(N) 与 O(log N) 的差别，B-tree 长什么样
  • 分清索引的两种分类：“索引什么”和“怎么索引”
  • 学会用 EXPLAIN 读懂执行计划，认识 Seq Scan、Index Scan、Index Only Scan、Bitmap Scan
  • 会建单列（B-tree / 哈希）、复合、覆盖、部分、表达式索引，并知道它们的坑
  • 警惕过度索引

索引为什么这么受欢迎

假设一张表有 100 行，要找 ID 等于 5 的那一行。没有索引时，Postgres 只能做顺序扫描（全表扫描）， 从头到尾逐行检查，最坏要看完全部 N 行，复杂度 O(N)。100 行最多看 100 次；可如果表涨到几百万行呢？

索引是一种把被索引的值按顺序存储的数据结构，用来加速数据访问。 Postgres 支持很多种索引，默认的通用类型是 B-tree（平衡树）。假设 ID 列上有一个 B-tree 索引，它大概长这样：

  • 根节点指向分支节点，分支节点指向叶子节点，叶子节点里存着指向表中真实行的引用（tr）。
  • 上层节点指向下层节点，表示下层节点里的条目都 ≤ 指针出发的那个条目。比如根节点的 10 指向分支 1（6 和 10），分支 1 的 6 指向叶子 1（1、4、5、6）。
  • 叶子节点之间按顺序链成链表，所以不用回到树顶就能顺序遍历 —— 这让范围查询和有序读取特别快。

在索引中搜索的复杂度是 O(logbN)，N 是条目数，b 是分支因子（每个分支节点平均有多少条目）。 分支因子为 10 时：

这就是索引如此受欢迎的原因：从几行涨到几百万行，通过索引查找的性能几乎不变。

Postgres 的索引类型

深入 Postgres 索引时，你会遇到一大堆术语：单列、复合、部分、函数，B-tree、HNSW……没有分类很容易乱。 把它们分成两大类就清楚了：

不写 USING 时默认 B-tree：

-- 在 tableA 的 columnA 上建单列索引，默认 B-tree
CREATE INDEX new_index_name ON tableA(columnA);

-- 指定用 GIN（通用倒排索引），常用于数组、JSON、全文搜索
CREATE INDEX new_index_name ON tableA USING GIN (columnA);

加载多人游戏数据集

数据集只有一张表，但足够我们把“索引什么”这一类全部讲完：

CREATE TABLE game.player_stats (
    player_id BIGINT PRIMARY KEY,              -- 玩家 ID
    username TEXT NOT NULL UNIQUE,             -- 用户名
    level INTEGER NOT NULL CHECK (level BETWEEN 1 AND 10),  -- 等级 1~10
    score INTEGER DEFAULT 0,                   -- 生涯总积分，同等级内排名用
    champion_title TEXT,                       -- 冠军头衔，只有极少数人有
    join_date DATE NOT NULL,                   -- 注册日期
    last_active TIMESTAMP,                     -- 最后活跃时间
    region TEXT CHECK (region IN ('NA', 'EMEA', 'APAC')),   -- 地区
    play_time INTERVAL DEFAULT '0 seconds',    -- 总游戏时长
    win_count INTEGER DEFAULT 0,               -- 胜场
    loss_count INTEGER DEFAULT 0               -- 负场
);

NA = 北美，EMEA = 欧洲、中东和非洲，APAC = 亚太。INTERVAL 是表示“一段时长”的类型，比如 '50 hours'。

学会使用 EXPLAIN

有慢查询时，先用 EXPLAIN，再决定要不要建索引。 它返回 Postgres 查询规划器为这条查询生成的执行计划，让你看清现在是怎么执行的、到底需不需要索引。

比如统计胜场超过 100 的玩家数（结果是 8061）。在查询前加上 EXPLAIN：

EXPLAIN
SELECT count(*)
FROM game.player_stats
WHERE win_count > 100;

                              QUERY PLAN
-----------------------------------------------------------------------
 Aggregate (cost=282.18..282.19 rows=1 width=8)
   -> Seq Scan on player_stats (cost=0.00..262.00 rows=8070 width=0)
         Filter: (win_count > 100)
(3 rows)

Seq Scan 表示对 player_stats 做了全表顺序扫描：访问每一行，检查 win_count > 100。 原因很简单：win_count 列上还没有索引。

主键自带索引

再看另一个场景：每位玩家的个人面板要显示自己的积分和等级：

EXPLAIN
SELECT username, level, score
FROM game.player_stats
WHERE player_id = 250;

                         QUERY PLAN
--------------------------------------------------------------
 Index Scan using player_stats_pkey on player_stats
   (cost=0.29..8.30 rows=1 width=18)
   Index Cond: (player_id = 250)
(2 rows)

假设监控显示过去半小时个人面板加载变慢了，我们先检查这条查询。计划里是 Index Scan —— 已经在用索引了。 这个 player_stats_pkey 是主键自动创建的索引： 

SELECT indexname, indexdef
FROM pg_indexes
WHERE schemaname = 'game'
  AND tablename = 'player_stats'
  AND indexdef LIKE '%player_id%';

     indexname     |                    indexdef
-------------------+-------------------------------------------------
 player_stats_pkey | CREATE UNIQUE INDEX player_stats_pkey
                   | ON game.player_stats USING btree (player_id)
(1 row)

EXPLAIN ANALYZE：真的跑一遍

EXPLAIN 只显示计划，并不真正执行。要看实际耗时，用 EXPLAIN ANALYZE：

EXPLAIN ANALYZE
SELECT username, level, score
FROM game.player_stats
WHERE player_id = 250;

                            QUERY PLAN
-----------------------------------------------------------------
 Index Scan using player_stats_pkey on player_stats
   (cost=0.29..8.30 rows=1 width=18)
   (actual time=0.046..0.049 rows=1 loops=1)
   Index Cond: (player_id = 250)
 Planning Time: 0.119 ms
 Execution Time: 0.077 ms
(4 rows)
  • Planning Time：规划器挑选最优计划花的时间。
  • Execution Time：按选定计划执行花的时间。
  • 查询总耗时 = 两者之和。
💡 多跑几次

用 EXPLAIN ANALYZE 执行几次，直到 Planning Time 和 Execution Time 稳定下来。头几次可能偏慢，因为数据还没进缓存，规划器也还没选定最优计划。

⚠ ANALYZE 会真的执行

EXPLAIN (analyze) UPDATE … 不只是返回计划，还会真的修改数据！对写操作用 ANALYZE 时，可以包在 BEGIN; … ROLLBACK; 里。

EXPLAIN 的选项：看看数据是否来自内存

EXPLAIN 支持在括号里传选项：EXPLAIN ( option [, ...] ) statement。查询变慢不一定是计划不好或缺索引，也可能是内存不够、频繁读磁盘。加上 buffers on 就能看到：

EXPLAIN (analyze, buffers on)
SELECT username, level, score
FROM game.player_stats
WHERE player_id = 250;

 Index Scan using player_stats_pkey on player_stats
   (cost=0.29..8.30 rows=1 width=18)
   (actual time=0.042..0.044 rows=1 loops=1)
   Index Cond: (player_id = 250)
   Buffers: shared hit=3
 Planning Time: 0.119 ms
 Execution Time: 0.076 ms

Buffers: shared hit=3：Postgres 从共享缓冲区（预先分配、用来缓存表和索引数据的内存）读了 3 个页，完全没碰磁盘。 如果显示 shared hit=3 read=4，就是 3 页来自内存、4 页要从磁盘读。

ⓘ 写法说明
  • EXPLAIN ANALYZE 是 EXPLAIN (analyze) 的简写，但简写不支持再加别的选项。
  • 本书大多用 EXPLAIN (analyze, costs off)：去掉 cost 估算，输出更紧凑，适合放进书里。这并不是“最佳实践”，只是方便阅读。
  • 更多选项见官方文档：sql-explain。

结论：这条查询已经走索引、数据都在内存里、耗时合理 —— 它不是面板变慢的元凶，得去应用栈的其他地方继续排查。EXPLAIN 帮我们排除了一个嫌疑。

几种扫描方式一览

本章会反复遇到下面这几种访问方法，先建立直观印象：

单列索引

主键上的索引就是 Postgres 自动创建的单列索引。下面学习自己创建单列索引，并比较 B-tree 和哈希索引的区别。

单列 B-tree 索引

目前游戏里有 10,000 名玩家。分支因子取 10，B-tree 找到某个玩家需要 log1010,000 = 4 次查找； 就算游戏爆火，玩家涨到一百万，也只需要 6 次。

ⓘ 为什么 B-tree 是默认类型

它支持的数据类型很广，而且既能做等值查找（=），也能做范围查询（>、>=、<、<=、BETWEEN），还能直接提供有序结果。

我们要做一个实时的积分排行榜。先看按积分过滤时 Postgres 怎么执行（积分在 5000~6000 之间的有 970 人）：

EXPLAIN (analyze, costs off)
SELECT count(*) FROM game.player_stats
WHERE score BETWEEN 5000 AND 6000;

                                 QUERY PLAN
----------------------------------------------------------------------------
 Aggregate (actual time=1.702..1.703 rows=1 loops=1)
   -> Seq Scan on player_stats (actual time=0.762..1.615 rows=970 loops=1)
         Filter: ((score >= 5000) AND (score <= 6000))
         Rows Removed by Filter: 9030
 Planning Time: 0.246 ms
 Execution Time: 1.753 ms

全表扫描，检查了每一行，970 行符合，9030 行白读了。现在只有一万行，1 毫秒多一点，没什么问题； 但玩家越来越多，耗时会线性增长。在 score 上建索引： 

CREATE INDEX idx_score
ON game.player_stats(score DESC);

idx_score 是我们起的名字，DESC 让索引按积分从高到低排列。虽然没写，它默认就是 B-tree：

SELECT indexname, indexdef
FROM pg_indexes
WHERE schemaname = 'game'
  AND tablename = 'player_stats'
  AND indexdef LIKE '%idx_score%';

 indexname |                   indexdef
-----------+----------------------------------------------
 idx_score | CREATE INDEX idx_score ON game.player_stats
           |    USING btree (score DESC)
(1 row)

再看执行计划：

                          QUERY PLAN
--------------------------------------------------------------
 Aggregate (actual time=0.303..0.303 rows=1 loops=1)
   -> Index Only Scan using idx_score on player_stats
        (actual time=0.078..0.198 rows=970 loops=1)
         Index Cond: ((score >= 5000) AND (score <= 6000))
         Heap Fetches: 0
 Planning Time: 0.164 ms
 Execution Time: 0.350 ms

这次是 Index Only Scan：查询只需要计数，索引里已经有全部所需信息，根本不用访问表（Heap Fetches: 0，heap 指表本身）。 耗时从 1.75 ms 降到 0.35 ms，快了 5 倍。（你机器上的数字会不同，取决于数据量、资源和运行状况。）

💡 建完索引后跑一下 ANALYZE

生产环境里，建完索引最好执行一次 ANALYZE 表名;。新索引建好后，规划器可能还在用旧的统计信息，不一定马上用上新索引。ANALYZE 会更新表的统计信息，让规划器充分利用新索引。

CREATE INDEX on tableA(columnB);
ANALYZE tableA;

现在可以生成前五名排行榜了：

SELECT username, score, level
FROM game.player_stats
ORDER BY score DESC
LIMIT 5;

    username    | score | level
----------------+-------+-------
 kfowler        | 10000 |    10
 tvillegas      | 10000 |    10
 ashley18       | 10000 |    10
 brookecampbell | 10000 |    10
 harrisoscar    |  9999 |    10
(5 rows)

 Limit (actual time=0.044..0.047 rows=5 loops=1)
   -> Index Scan using idx_score on player_stats
        (actual time=0.042..0.044 rows=5 loops=1)
 Planning Time: 0.311 ms
 Execution Time: 0.105 ms

索引本身已经按积分降序排好，Postgres 沿着索引读出前 5 条就停，连排序都省了。 有意思的是规划时间（0.311 ms）比执行时间（0.105 ms）还长 —— 规划器需要时间评估可用索引和统计信息。

★ 索引也有写入成本

索引也能加速修改数据：比如按 player_id 更新某人的积分，主键索引能帮你快速定位那一行。 但因为更新改了 score，Postgres 还要同时更新 idx_score 索引，这会让更新稍微变慢一点。

单列哈希索引

哈希索引和编程语言里的哈希表（hash map）原理一样：对列值计算哈希，映射到某个桶（bucket）。 计算和查找都是 O(1) 常数时间 —— 表从几千行涨到几百万行，检查某个值是否存在的耗时基本不变。

哈希索引只支持单列，只能用于等值（=）比较。范围查询用不了，得用 B-tree。

游戏里有五个可转让的冠军头衔：Airforce Warlord、Naval Warlord、Land Warlord、Cyber Warlord、Space Warlord。几千名玩家里只有五人持有头衔。找 Naval Warlord 是谁：

EXPLAIN (analyze, costs off)
SELECT username, score, level
FROM game.player_stats
WHERE champion_title = 'Naval Warlord';

                             QUERY PLAN
--------------------------------------------------------------------
 Seq Scan on player_stats (actual time=0.064..1.429 rows=1 loops=1)
   Filter: (champion_title = 'Naval Warlord'::text)
   Rows Removed by Filter: 9999
 Planning Time: 0.154 ms
 Execution Time: 1.463 ms

为了找一行，扫了全表、过滤掉 9999 行（这一列没有 UNIQUE 约束，所以也没有自动创建的 B-tree）。 冠军很少，而且只用 = 和 IN 查找 —— 哈希索引正合适： 

CREATE INDEX idx_champion_title
ON game.player_stats
USING hash(champion_title);

 Index Scan using idx_champion_title on player_stats
   (actual time=0.037..0.038 rows=1 loops=1)
   Index Cond: (champion_title = 'Naval Warlord'::text)
 Planning Time: 0.151 ms
 Execution Time: 0.073 ms

用 IN 一次查出全部五位冠军，也能用上这个索引：

SELECT username, champion_title, score, level
FROM game.player_stats
WHERE champion_title IN (
  'Airforce Warlord', 'Naval Warlord',
  'Land Warlord', 'Cyber Warlord',
  'Space Warlord');

   username   |  champion_title  | score | level
--------------+------------------+-------+-------

(5 rows)

   Recheck Cond: (champion_title = ANY ('{"Airforce Warlord",...}'::text[]))
   Heap Blocks: exact=4
   -> Bitmap Index Scan on idx_champion_title
        (actual time=0.047..0.047 rows=5 loops=1)
         Index Cond: (champion_title = ANY ('{"Airforce Warlord",...}'::text[]))
 Planning Time: 0.242 ms
 Execution Time: 0.166 ms

位图扫描（bitmap scan）是怎么回事

这次用的是位图索引扫描，它总是分两个阶段：

  1. Bitmap Index Scan：在索引里找出所有匹配的条目。每找到一个，不立刻回表取数据，而是在一个位图结构里标记“这一行待会儿要读”—— 相当于为“批量读取”做准备。
  2. Bitmap Heap Scan：拿着位图访问表，只读取被标记的行。表只被访问一次，而不是每找到一个索引条目就回表一次。
◆ 位图中的 exact 与 lossy

如果匹配的行很多、位图开始吃内存，Postgres 就改为只记录整页的位置，位图变成有损的（lossy）。 有些索引类型（比如第 9 章的 BRIN）本来就只记录页。对有损的页，Bitmap Heap Scan 阶段要重新检查页内每一行。 上例中 Heap Blocks: exact=4 表示访问了 4 页，而且准确知道每页要取哪几行。

复合索引

复合索引（也叫多列索引）建在多个列上。目前 Postgres 支持用 B-tree、GIN、GiST、BRIN 或 bloom 来建复合索引。 原理很直接：对于 (region, score) 上的索引，先按 region 排序，同一 region 内再按 score 排序。

★ 前导列

第一列叫前导列（leading column），查询里必须用到它，Postgres 才会考虑这个索引。 如果 WHERE 里只有 score 没有 region，这个索引通常用不上 —— 因为它首先是按 region 排的。 就像电话簿先按姓、再按名排序：知道姓好查，只知道名就只能从头翻。

有两条查询在游戏里执行得非常频繁，都需要索引。同时我们也希望索引尽量少，因为每个索引都需要维护：

SELECT DISTINCT ON (region)
username, region, score, win_count
FROM game.player_stats
ORDER BY region, score DESC, win_count DESC;
ⓘ DISTINCT ON

DISTINCT ON (region) 是 Postgres 特有的写法：对每个不同的 region，只返回按 ORDER BY 排序后的第一行。这里就是每个地区积分最高（积分相同时胜场最多）的玩家。

SELECT username, region, score, win_count
FROM game.player_stats
WHERE region = 'NA' and score > 5000 and win_count > 10
ORDER BY score DESC, win_count DESC;

   Presorted Key: score

   Sort Key: score DESC, win_count DESC
   -> Seq Scan on player_stats (actual time=0.028..2.031 rows=2916 loops=1)

★ 有索引 ≠ 一定用索引

积分超过 1000 的玩家太多了，用索引会返回大量记录再逐个回表，规划器判断这还不如直接全表扫描。 索引在“只需要表中一小部分数据”时最有效。

可以再给 region 建一个单列索引：

CREATE INDEX idx_region ON game.player_stats (region);

 Sort (actual time=1.880..1.995 rows=2916 loops=1)
   Sort Key: score DESC, win_count DESC
   -> Bitmap Heap Scan on player_stats (actual time=0.128..1.388 rows=2916 loops=1)
         Recheck Cond: (region = 'NA'::text)
         Filter: ((score > 1000) AND (win_count > 10))
         Rows Removed by Filter: 391
         Heap Blocks: exact=137
         -> Bitmap Index Scan on idx_region (actual time=0.098..0.098 rows=3307 loops=1)
               Index Cond: (region = 'NA'::text)
 Execution Time: 2.112 ms

比全表扫描快了。但清单 4.6（每个地区的头号玩家）还是用不上任何现有的单列索引：

 Unique (actual time=13.148..14.314 rows=3 loops=1)
   -> Sort (actual time=13.145..13.591 rows=10000 loops=1)
         Sort Key: region, score DESC, win_count DESC
         Sort Method: quicksort Memory: 881kB
         -> Seq Scan on player_stats (actual time=0.065..1.969 rows=10000 loops=1)
 Planning Time: 0.183 ms
 Execution Time: 14.357 ms

为了最后找出 3 个人，读了全部 10,000 行再排序。与其为每个查询各建一个单列索引，不如建一个复合索引同时服务两条查询。先删掉 idx_region：

DROP INDEX game.idx_region;

创建复合索引

CREATE INDEX idx_region_score_win_count
ON game.player_stats (region, score DESC, win_count DESC);

它同样默认用 B-tree（可以用 pg_indexes 确认：USING btree (region, score DESC, win_count DESC)）。再看两条查询的执行计划。清单 4.7（score > 1000 版本）：

 Sort (actual time=2.517..2.682 rows=2916 loops=1)
   Sort Key: score DESC, win_count DESC
   -> Bitmap Heap Scan on player_stats (actual time=0.472..1.812 rows=2916 loops=1)
         Recheck Cond: ((region = 'NA'::text) AND (score > 1000) AND (win_count > 10))
         Heap Blocks: exact=124
         -> Bitmap Index Scan on idx_region_score_win_count
              (actual time=0.434..0.434 rows=2916 loops=1)
               Index Cond: ((region = 'NA'::text) AND (score > 1000) AND (win_count > 10))
 Execution Time: 2.844 ms

和单列 region 索引一样高效。而对清单 4.6 的效果就显著多了：

 Result (actual time=0.038..3.994 rows=3 loops=1)
   -> Unique (actual time=0.034..3.984 rows=3 loops=1)
         -> Index Scan using idx_region_score_win_count on player_stats
              (actual time=0.032..2.698 rows=10000 loops=1)
 Planning Time: 0.147 ms
 Execution Time: 4.038 ms

没有 Sort 步骤了 —— 索引里 score 和 win_count 已经按降序排好。一个复合索引，同时优化了两条查询。

复合索引的注意事项

坑一：列的顺序决定了 ORDER BY 的写法。现在每个地区的排行是先比积分、再比胜场。如果改成先比胜场、再比积分：

SELECT DISTINCT ON (region)
username, region, score, win_count
FROM game.player_stats
ORDER BY region, win_count DESC, score DESC;

 username  | region | score | win_count
-----------+--------+-------+-----------
 foxdavid  | APAC   |  9694 |       500
 rcastillo | EMEA   |  9772 |       500
 kfowler   | NA     | 10000 |       500
(3 rows)

 Unique (actual time=17.596..19.245 rows=3 loops=1)
   -> Sort (actual time=17.593..18.300 rows=10000 loops=1)
         Sort Key: region, win_count DESC, score DESC
         -> Seq Scan on player_stats (actual time=0.025..2.282 rows=10000 loops=1)
 Execution Time: 19.287 ms

结果变了是意料之中的；意料之外的是 Postgres 用不上复合索引了：排序顺序 region, win_count, score 和索引定义 region, score, win_count 不一致。

坑二：只用了部分列时。用复合索引里的一部分列过滤，能不能用上索引？

-- ✓ 只用前导列：Index Only Scan，Index Cond: (region = 'EMEA')
SELECT count(*) FROM game.player_stats WHERE region = 'EMEA';

-- ✓ 前两列：Index Only Scan，Index Cond: (region = 'EMEA' AND score > 1000)
SELECT count(*) FROM game.player_stats WHERE region = 'EMEA' and score > 1000;

-- ✗ 缺前导列 region：Seq Scan
SELECT count(*) FROM game.player_stats WHERE score > 1000 and win_count > 30;

-- ✓ 第一列 + 第三列（跳过 score）：仍然用了 Index Only Scan
SELECT count(*) FROM game.player_stats WHERE region = 'EMEA' and win_count > 30;

最后一种情况能用上，是因为 Postgres 可以先快速定位 region = EMEA 的那一段索引，再在这段里找满足 win_count > 30 的条目，仍比全表扫描划算。 但这不适用于所有复合索引：一般来说，如果查询跳过了前导列或中间列，在 Postgres 17 及更早版本里用上索引的几率会降低。 Postgres 18 起支持 B-tree 复合索引的 skip scan，跳过前导列也能在更多场景下用索引。

覆盖索引

覆盖索引（covering index）额外存储表里的一些列，让数据库能直接从索引取值、不用回表。额外的列用 INCLUDE 添加： 

CREATE INDEX index_name ON table_name(columnA)
INCLUDE(columnB, columnC [, additional_columns]);

索引按 columnA 构建和排序；columnB、columnC 不参与排序，只是“顺便存着”。 比如 SELECT columnB FROM table_name WHERE columnA > 50 ORDER BY columnC; 就完全不需要访问表。 代价是：这些列被修改时，Postgres 也要更新索引，写入会变慢一些。

回到游戏。清单 4.7（score > 5000 版本）现在的计划是：

 Sort (actual time=1.574..1.662 rows=1580 loops=1)
   Sort Key: score DESC, win_count DESC
   -> Bitmap Heap Scan on player_stats (actual time=0.249..1.005 rows=1580 loops=1)
         Recheck Cond: ((region = 'NA'::text) AND (score > 5000) AND (win_count > 10))
         Heap Blocks: exact=68
         -> Bitmap Index Scan on idx_region_score_win_count
              (actual time=0.225..0.225 rows=1580 loops=1)
 Execution Time: 1.856 ms

它还要访问表里的 68 个页（Heap Blocks: exact=68），原因只有一个：查询要返回 username，而它不在索引里。 这是一条执行非常频繁的“热”查询，值得进一步优化。先删掉旧的复合索引，避免两个相似的索引并存，再建一个带上 username 的覆盖索引： 

DROP INDEX game.idx_region_score_win_count;

CREATE INDEX idx_composite_covering_index
ON game.player_stats (region, score DESC, win_count DESC)
INCLUDE (username);

 Index Only Scan using idx_composite_covering_index on player_stats
   (actual time=0.076..0.497 rows=1580 loops=1)
   Index Cond: ((region = 'NA'::text) AND (score > 5000) AND (win_count > 10))
   Heap Fetches: 0
 Planning Time: 0.320 ms
 Execution Time: 0.602 ms

这次是 Index Only Scan，完全不访问表。0.6 ms，比之前的 1.8 ms 快了 3 倍。 而且玩家很少改用户名，把 username 放进覆盖索引对写入的影响微乎其微。

💡 什么列适合 INCLUDE

适合：查询经常要返回、但很少被修改、不需要参与过滤或排序的列。不适合：频繁更新的列、很大的列（会让索引膨胀）。

部分索引

部分索引（partial index），也叫过滤索引，只为表中满足某个条件的子集建立索引。条件写在 WHERE 里，可以很简单也可以涉及多列： 

CREATE INDEX partial_index_name ON table_name(columnA) WHERE condition;

它适合“表很大，但应用总是只查其中一小块”的场景。好处是索引更小，表更新也更快（不满足条件的行变动时，不用维护索引），更省内存和磁盘。

游戏想追踪新手和休闲玩家（总游戏时长不超过 50 小时的人）并给他们发奖励，研究他们为什么流失。一万名玩家里只有 74 位休闲玩家，不到 1%： 

SELECT count(*) FROM game.player_stats WHERE play_time <= '50 hours';
-- 74

SELECT username, play_time, score, last_active
FROM game.player_stats
WHERE play_time <= '50 hours'
ORDER BY play_time;

    username     | play_time | score |        last_active
-----------------+-----------+-------+----------------------------
 justinrodriguez | 04:00:00  |    34 | 2025-07-07 03:29:23.05813
 clifford28      | 04:00:00  |    16 | 2023-06-17 03:29:22.068583
 robinsonanne    | 05:00:00  |    57 | 2024-03-20 03:29:22.274161
 pattonkristen   | 07:00:00  |    25 | 2025-03-08 03:29:21.133161
 elizabethrhodes | 08:00:00  |    76 | 2025-05-08 03:29:22.559829

 Sort (actual time=2.125..2.129 rows=74 loops=1)
   Sort Key: play_time
   -> Seq Scan on player_stats (actual time=2.015..2.085 rows=74 loops=1)
         Filter: (play_time <= '50:00:00'::interval)
         Rows Removed by Filter: 9926
 Execution Time: 2.168 ms

全表扫描 + 排序。耗时现在还能接受，但会随玩家数线性增长。建一个只覆盖休闲玩家的部分索引：

CREATE INDEX idx_occasional_players
ON game.player_stats (play_time)
WHERE play_time <= '50 hours';

 Index Scan using idx_occasional_players on player_stats
   (actual time=0.036..0.128 rows=74 loops=1)
 Planning Time: 0.334 ms
 Execution Time: 0.168 ms

从 2 ms 降到 0.1 ms 左右，快了 20 倍；而且这个索引只有 74 个条目，比给整张表建 play_time 索引小得多。

⚠ 条件必须被索引条件“包含”

只要查询条件是 play_time <= '50 hours' 或者更窄，Postgres 就会考虑这个索引。哪怕只超出 1 秒：

EXPLAIN (analyze, costs off)
SELECT username, play_time, score, last_active
FROM game.player_stats
WHERE play_time <= '50 hours 1 second'
ORDER BY play_time;
-- -> Seq Scan on player_stats ... Filter: (play_time <= '50:00:01'::interval)

部分索引里没有这些可能存在的行，Postgres 只能退回全表扫描。

函数索引与表达式索引

函数索引（也叫表达式索引）为“对一列或多列套用函数或表达式后的结果”建立索引： 

CREATE INDEX functional_index_name
ON table_name(function_or_expression(columnA [, additional_columns]));

函数可以是内置的（比如 lower(text)），也可以是你自己定义的函数或表达式。 只要查询的 WHERE 或 ORDER BY 里出现了完全相同的表达式，Postgres 就会考虑用这个索引。

游戏要按胜负差（胜场 − 负场）筛选玩家：

SELECT username, win_count, loss_count, (win_count - loss_count) as margin
FROM game.player_stats
WHERE (win_count - loss_count) BETWEEN 300 and 450
ORDER BY margin DESC;

 Sort (actual time=2.387..2.459 rows=731 loops=1)
   Sort Key: ((win_count - loss_count)) DESC
   -> Seq Scan on player_stats (actual time=0.079..2.188 rows=731 loops=1)
         Filter: (((win_count - loss_count) >= 300) AND ((win_count - loss_count) <= 450))
         Rows Removed by Filter: 9269
 Execution Time: 2.524 ms

全表扫描，对每一行都算一遍 win_count - loss_count。即使 win_count 和 loss_count 上各有索引也没用 —— 索引里存的是原始列值，不是差值。 这条查询很常用，那就为这个表达式建索引： 

CREATE INDEX idx_perf_margin
ON game.player_stats ((win_count - loss_count));
ⓘ 注意双层括号

表达式索引要把表达式再包一层括号：((win_count - loss_count))。只有单个函数调用（如 lower(email)）时可以省掉外层括号。

 Sort (actual time=1.029..1.090 rows=731 loops=1)
   Sort Key: ((win_count - loss_count)) DESC
   -> Bitmap Heap Scan on player_stats (actual time=0.093..0.853 rows=731 loops=1)
         Recheck Cond: (((win_count - loss_count) >= 300) AND ((win_count - loss_count) <= 450))
         Heap Blocks: exact=136
         -> Bitmap Index Scan on idx_perf_margin (actual time=0.061..0.061 rows=731 loops=1)
               Index Cond: (((win_count - loss_count) >= 300) AND ((win_count - loss_count) <= 450))
 Execution Time: 1.200 ms

已经比全表扫描快了一倍，玩家越多差距越大。

当心过度索引

本章我们给 player_stats 加了不少索引，现在一共有七个：

SELECT count(*) FROM pg_indexes
WHERE schemaname = 'game' AND tablename = 'player_stats';
-- 7

学习时这没问题，但在实际项目里，这就是典型的过度索引（over-indexing）：一张表索引太多，说明应该重新审视索引策略了。

  • 每个索引都要维护：被索引的列在表里一改，索引结构就要跟着更新，才能保持一致、继续提供 O(log N) 等性能。索引越多、表更新越频繁，开销越大。
  • 索引越多，规划器在规划阶段要花越多时间去挑选最优计划。

附录 A 会更详细地讨论过度索引和索引不足。

小结

  • 索引通过只访问被索引数据的一小部分来加速查询，很多索引的复杂度是 O(logbN)。
  • 索引有两种分类：按范围/用途（索引什么）和按数据结构/访问方法（怎么索引）。默认数据结构是 B-tree。
  • EXPLAIN 让我们看清执行计划，从而选择最有效的优化方式；EXPLAIN ANALYZE 会真正执行并给出实际耗时。
  • 单列和复合索引优化按一列或多列过滤、排序的查询；复合索引要注意列顺序和前导列。
  • 哈希索引只适合等值查找。
  • 覆盖索引把额外的列存进索引，减少回表。
  • 部分索引只为数据子集建索引。
  • 函数/表达式索引为计算结果建索引。
  • 索引不是越多越好，警惕过度索引。
