Postgres 与 JSON

Postgres 早在 2012 年就开始支持 JSON，之后持续改进。如今它的 JSON 支持已经成熟全面，完全可以当作文档数据库来用。 这一章我们为一家在全国有几百家门店的披萨连锁店开发应用：把顾客订单以 JSON 存储，然后在出餐和分析口味偏好时查询、修改、索引这些数据。

本章目标

  • 分清 text、json、jsonb 三种存法，知道默认选 jsonb
  • 知道什么时候该用 JSON、什么时候用关系列（混合模式）
  • 熟练使用 ->、->>、?、@> 和 JSON path 表达式查询 JSON
  • 用 jsonb_set 和 #- 原地修改 JSON
  • 用 B-tree 表达式索引和两种 GIN 索引加速 JSON 查询

存储 JSON 数据

顾客在手机或网页上下单后，后端收到一份 JSON 格式的订单。比如一个中号玛格丽特披萨：

{
    "size": "medium",
    "type": "margherita",
    "crust": "regular",
    "sauce": "marinara",
    "toppings": {
      "cheese": [
         {"mozzarella": "regular"}
      ],
      "veggies": [
         {"tomato": "light"}
      ]
    }
}

我们打算把这些 JSON 原样存进数据库，由应用层决定 JSON 的结构：顾客在界面上挑选、定制披萨，应用把订单组装成 JSON，存进 Postgres。 问题是：用什么类型来存？

  • text：任何 JSON 都是一段文本，当然能存进 text 列。如果只需要存和取，这样就够了；但如果要在数据库里检查某个字段的值、或操作 JSON 结构，就不行了。
  • json：以文本格式存储，保留原始结构，不做任何转换，所以写入快、原样返回。但每次访问字段都要重新解析，读得慢。
  • jsonb：写入时解析成内部的二进制格式，去掉空白和重复键，可能为了查找效率重排键的顺序。写入稍慢，取回来的结构可能和原来不完全一样；但搜索快得多，还能用 GIN（通用倒排索引）加速，函数和运算符也更丰富。

结论：除非你必须保留原始 JSON 的键顺序，否则 jsonb 就是默认选择。披萨应用不关心键顺序，所以用 jsonb。

加载披萨订单数据集

CREATE TABLE pizzeria.order_items (
    order_id INT NOT NULL,          -- 订单号
    order_item_id INT NOT NULL,     -- 订单里的第几个披萨
    pizza JSONB NOT NULL,           -- 披萨详情（JSON）
    price numeric(5,2) NOT NULL,    -- 这个披萨的价格
    PRIMARY KEY (order_id, order_item_id)
);

ⓘ jsonb_pretty()

jsonb_pretty(jsonb) 只是让 psql 里的输出更好读（行尾的 + 是 psql 表示换行的符号）。返回给应用时没必要用它，直接 SELECT pizza 得到的是紧凑的一行。

JSON 在 Postgres 里：把握平衡

虽然 Postgres 的 JSON 支持很完整，但不要像纯文档数据库那样把所有数据都塞进 JSON。 Postgres 有丰富的类型，你应该在 JSON 的灵活性和经典关系类型（int、text、date…，数据库对它们有大量内置优化）的效率之间找平衡。

📁

数据静态或很少更新

配置、元数据、顾客偏好、会话历史。

🕳

数据稀疏

大量零、空值、占位符，比如功能开关、几十个可选项的用户设置。

🧰

需要灵活的结构

难以规范化的数据：第三方 API 响应、遥测事件、半结构化文档。

而如果涉及更新、连接、聚合、过滤的操作对性能要求很高，就该用关系类型和规范化模型，或者混合方式：JSON 和关系列并存。

如果用传统的规范化模型，披萨的每个部分（类型、饼底、酱料、尺寸、配料）都要拆进独立的列甚至独立的表，大致是这样：

-- 披萨的核心属性
CREATE TABLE pizzeria.pizzas (
    id SERIAL PRIMARY KEY,
    type TEXT NOT NULL,
    crust TEXT NOT NULL,
    sauce TEXT NOT NULL,
    size TEXT NOT NULL
);

-- 把披萨关联到订单
CREATE TABLE pizzeria.order_items (
    order_id INT NOT NULL,
    order_item_id INT NOT NULL,
    pizza_id INT REFERENCES pizzeria.pizzas(id),
    price NUMERIC(5,2) NOT NULL,
    PRIMARY KEY (order_id, order_item_id)
);

-- 每种配料类别一张表
CREATE TABLE pizzeria.pizza_cheeses (
    pizza_id INT REFERENCES pizzeria.pizzas(id),
    cheese TEXT NOT NULL,
    amount TEXT NOT NULL,
    PRIMARY KEY (pizza_id, cheese)
);
-- pizza_veggies、pizza_meats 同理……

对我们这个场景，它至少有三个缺点：

  • 写入开销：加一个披萨要在事务里更新好几张表。两种肉、三种奶酪、两种蔬菜，就要插入 7 条配料记录。
  • 读取开销：给厨房或顾客展示配方前，要把好几张表 JOIN 起来还原。
  • 转换开销：前端本来就用 JSON 处理配方，每次读写都要在 JSON 和规范化模型之间来回转换。

查询 JSON 数据

给厨房或顾客展示订单时，最简单的做法就是把整个 JSON 取出来：

SELECT pizza
FROM pizzeria.order_items
WHERE order_id = 100;

                                     pizza
--------------------------------------------------------------------------
 {"size": "small", "type": "margherita", "crust": "thin",
  "sauce": "marinara", "toppings": {"cheese": [{"mozzarella": "regular"}],
  "veggies": [{"tomato": "light"}]}}
 {"size": "small", "type": "custom", "crust": "gluten_free",
  "sauce": "pesto", "toppings": {"meats": [{"bacon": "light"}],
  "cheese": [{"mozzarella": "regular"}], "veggies": [{"onion": "light"}]}}
 {"size": "extra_large", "type": "pepperoni", "crust": "thin",
  "sauce": "marinara", "toppings": {"meats": [{"salami": "regular"}],
  "cheese": [{"mozzarella": "regular"}]}}
(3 rows)

但应用常常只需要某几个字段（比如饼底类型、配料清单），或者要按条件筛选（比如接下来五个需要马苏里拉奶酪的订单）。 这时就要用 Postgres 的 JSON 运算符和函数：

用 -> 和 ->> 取字段

两者都按键名取字段，区别在于返回类型：-> 返回 JSON，->> 返回 text。键名要用单引号括起来。

SELECT
    order_id, order_item_id,
    pizza->'size' as pizza_size,
    pizza->>'crust' as pizza_crust
FROM pizzeria.order_items
WHERE order_id = 100;

 order_id | order_item_id |  pizza_size   | pizza_crust
----------+---------------+---------------+-------------
      100 |             1 | "small"       | thin
      100 |             2 | "small"       | gluten_free
      100 |             3 | "extra_large" | thin
(3 rows)

注意 pizza_size 带双引号，pizza_crust 不带：-> 返回的是 JSON 字符串，按 JSON 规范文本值必须带双引号； ->> 把它转换成了 Postgres 的 text 类型，就没有引号了。这个差别在 WHERE 里尤其要注意： 

SELECT
    order_id, order_item_id,
    pizza->'size' as pizza_size,
    pizza->>'crust' as pizza_crust
FROM pizzeria.order_items
WHERE
    order_id = 100 AND
    pizza->'size' = '"small"' AND pizza->>'crust' = 'gluten_free';
⚠ 和 JSON 比较要带双引号

pizza->'size' 是 jsonb，所以要和 JSON 字符串 '"small"' 比较。写成 pizza->'size' = 'small' 会报错：

DETAIL: Token "small" is invalid.
CONTEXT: JSON data, line 1: small

经验法则：要拿来和普通字符串比较，就用 ->>。

链式调用，深入嵌套结构

运算符可以串起来，一层层往里走。比如查订单里每个披萨要加的蔬菜：

SELECT
    order_id, order_item_id,
    pizza->'toppings'->'veggies' as veggies_toppings
FROM pizzeria.order_items
WHERE order_id = 100;

 order_id | order_item_id |   veggies_toppings
----------+---------------+-----------------------
      100 |             1 | [{"tomato": "light"}]
      100 |             2 | [{"onion": "light"}]
      100 |             3 |
(3 rows)

第三个披萨顾客没选蔬菜，所以是空的。结果是数组（[]）。要取数组里的某个元素，传它的下标（从 0 开始）：

SELECT
    order_id, order_item_id,
    pizza->'toppings'->'veggies'->0 as veggies_toppings
FROM pizzeria.order_items
WHERE order_id = 100;
-- 结果不再带 [ ]：{"tomato": "light"}、{"onion": "light"}

-> 和 ->> 可以混用：先用 -> 一路走到目标，最后一步用 ->> 取出文本：

SELECT
    order_id, order_item_id,
    pizza->'toppings'->'veggies'->0->>'onion' as onions_amount
FROM pizzeria.order_items
WHERE order_id = 100;

 order_id | order_item_id | onions_amount
----------+---------------+---------------
      100 |             1 |
      100 |             2 | light
      100 |             3 |
(3 rows)

用 ? 检查键是否存在

? 运算符检查 JSON 里是否存在某个键，只支持 jsonb。厨师要去仓库拿食材，想知道排队中的订单需要哪些肉：

SELECT
    order_id, order_item_id,
    pizza->'toppings'->'meats' as meats
FROM pizzeria.order_items
WHERE pizza->'toppings' ? 'meats'
ORDER BY order_id LIMIT 5;

 order_id | order_item_id |          meats
----------+---------------+--------------------------
        1 |             1 | [{"salami": "regular"}]
        1 |             2 | [{"chicken": "regular"}]
        2 |             1 | [{"salami": "regular"}]
        3 |             1 | [{"salami": "regular"}]
        5 |             1 | [{"salami": "regular"}]
(5 rows)

厨师回来说意大利香肠（sausage）快用完了，要联系点了香肠的顾客商量换别的。香肠在 meats 数组里的某个对象中，需要先把数组展开：

SELECT
    order_id, order_item_id,
    pizza->'toppings'->'meats' AS meats
FROM pizzeria.order_items
WHERE EXISTS (
    SELECT 1
    FROM jsonb_array_elements(pizza->'toppings'->'meats') AS meats
    WHERE meats ? 'sausage'
)
ORDER BY order_id LIMIT 5;
  • jsonb_array_elements(…) 把 meats 数组展开成一行一个 JSON 对象。
  • WHERE meats ? 'sausage' 只保留包含 sausage 键的对象。
  • 子查询不需要返回具体值，只要有一行就说明“存在”，所以写 SELECT 1。
 order_id | order_item_id |         meats
----------+---------------+------------------------
       20 |             5 | [{"sausage": "light"}]
       26 |             5 | [{"sausage": "extra"}]
       34 |             2 | [{"sausage": "extra"}]
       37 |             2 | [{"sausage": "extra"}]
       47 |             1 | [{"sausage": "extra"}]
(5 rows)

（后面会用 JSON path 表达式把这个子查询改写得更简洁。）

用 @> 比较对象（包含）

包含运算符 @> 检查左边的 JSON 是否在结构上“包含”右边的 JSON，也只支持 jsonb。 市场团队做了一个推广无麸质饼底的活动，想知道效果如何： 

SELECT count(*)
FROM pizzeria.order_items
WHERE pizza @> '{"crust": "gluten_free"}';
-- 749

其中有多少是自定义配方？再加一个条件 —— 两个字段都在顶层，写在同一个对象里就行：

SELECT count(*)
FROM pizzeria.order_items
WHERE pizza @> '{"crust": "gluten_free", "type": "custom"}';
-- 148

再看其中要“多加番茄”的。番茄在 toppings → veggies 数组里，右边的 JSON 也照着这个层级写：

SELECT count(*)
FROM pizzeria.order_items
WHERE pizza @> '{"crust": "gluten_free",
"type": "custom", "toppings": {"veggies": [{"tomato": "extra"}]}}';
-- 7
💡 -> 和 @> 搭配，更好读
SELECT count(*)
FROM pizzeria.order_items
WHERE pizza @> '{"crust": "gluten_free", "type": "custom"}' AND
     pizza->'toppings'->'veggies' @> '[{"tomato": "extra"}]';

先用 -> 走到 veggies 数组，再用 @> 检查数组里是否有 {"tomato": "extra"}。

JSON path 表达式

除了基础运算符，Postgres 还有一个强大的路径引擎，能执行 SQL/JSON path 语言写的表达式。 它特别适合从多层结构或对象数组里取数据，一个简单的路径表达式往往能省掉子查询。比如清单 5.5 找香肠订单的子查询，可以改写成： 

SELECT
    order_id, order_item_id,
    pizza->'toppings'->'meats' AS meats
FROM pizzeria.order_items
WHERE jsonb_path_exists(pizza, '$.toppings.meats[*] ? (exists(@.sausage))')
ORDER BY order_id LIMIT 5;

看不懂 $、@ 没关系，先看路径语言的基本元素，再从简单的例子学起：

每天营业结束后，应用要给管理层发一份报告。第一部分：最受欢迎的披萨类型。

SELECT
    count(*) as total_cnt,
    jsonb_path_query(pizza,'$.type') as pizza_type
FROM pizzeria.order_items
GROUP BY pizza_type ORDER BY total_cnt DESC;

 total_cnt |   pizza_type
-----------+----------------
       646 | "pepperoni"
       585 | "three cheese"
       582 | "veggie"
       563 | "custom"
       562 | "margherita"
(5 rows)

jsonb_path_query 对每行的 pizza 执行路径表达式：$ 指 pizza 对象本身，.type 取它的 type 字段。

路径表达式处理数组时尤其好用。报告的下一部分：最受欢迎的奶酪。

SELECT
    count(*) as total_cnt,
    jsonb_object_keys(
        jsonb_path_query(pizza, '$.toppings.cheese[*]')
    ) as cheese_topping
FROM pizzeria.order_items
GROUP BY cheese_topping ORDER BY total_cnt DESC;
  • $.toppings.cheese 走到奶酪数组，[*] 取出数组里的所有对象，比如 {"cheddar": "regular"}。
  • jsonb_object_keys 取出这些对象的键 —— 也就是奶酪的名字。
 total_cnt | cheese_topping
-----------+----------------
      2575 | mozzarella
       771 | cheddar
       762 | parmesan
(3 rows)

路径表达式还能带过滤器，以 ? 开头、条件写在括号里，作用类似 SQL 的 WHERE。报告的下一部分：用到帕玛森奶酪的披萨有哪些类型？

SELECT
    count(*) AS total_cnt,
    pizza->'type' as pizza_type
FROM pizzeria.order_items
WHERE jsonb_path_exists(pizza,
        '$.toppings.cheese[*] ? (exists(@.parmesan))')
GROUP BY pizza_type
ORDER BY total_cnt DESC;

 total_cnt |   pizza_type
-----------+----------------
       585 | "three cheese"
       177 | "custom"
(2 rows)

jsonb_path_exists 检查路径表达式能否求出任何值，能就返回 true，这一行就被保留。 @ 代表数组里当前正被检查的那个奶酪对象，@.parmesan 取它的 parmesan 字段，exists(…) 判断这个字段是否存在。

过滤器还可以串联，后一个过滤器作用在前一个的结果上。报告的最后一部分：自定义披萨里要“多加帕玛森”的有多少？

SELECT count(*)
FROM pizzeria.order_items
WHERE jsonb_path_exists(
    pizza,
    '$ ? (@.type == "custom") .toppings.cheese[*].parmesan ? (@ == "extra")'
);
-- 64

修改 JSON 数据

最简单的修改方式：把 JSON 读到应用层，改好，再整个写回去：

SELECT pizza
FROM pizzeria.order_items
WHERE order_id = $1 and order_item_id = $2;

-- 应用修改后：
UPDATE pizzeria.order_items
SET pizza = new_pizza_order_json
WHERE order_id = $1 and order_item_id = $2;
ⓘ $1、$2 是什么

这是参数占位符：应用用预编译语句（prepared statement）执行 SQL 时，把实际值作为参数传进来。这样也能防止 SQL 注入。

但最简单的未必最高效。如果 JSON 结构很复杂、而你只改一个字段，直接在数据库里改更划算，不用在应用和数据库之间来回搬整个对象。 Postgres 提供 jsonb_set 函数修改字段，#- 运算符删除字段。来看一个顾客反复改单的故事。当前订单： 

{
    "size": "extra_large",
    "type": "custom",
    "crust": "stuffed",
    "sauce": "alfredo",
    "toppings": {
        "meats":   [ {"sausage": "light"} ],
        "cheese":  [ {"parmesan": "regular"} ],
        "veggies": [ {"tomato": "light"} ]
    }
}

五分钟后顾客回到 App（幸好厨房还没开始做），把饼底从芝心（stuffed）改成普通（regular）：

UPDATE pizzeria.order_items
SET pizza = jsonb_set(pizza,'{crust}', '"regular"', false)
WHERE order_id = 20 and order_item_id = 5;
参数含义本例
① 原 JSON要修改的 JSON 对象pizza
② 路径目标字段的路径，格式 {a,b,c}：a 下面的 b 下面的 c'{crust}'
③ 新值要设置的新值，必须是合法的 JSON（字符串要带双引号）'"regular"'
④ 缺失时创建？目标字段不存在时：true 就新增，false 就不管false（crust 一定存在）

保存后顾客又发现番茄选成了“少量”，改成“多加番茄”并加上菠菜。这次路径指向嵌套的 veggies 数组，直接替换整个数组：

UPDATE pizzeria.order_items
SET pizza = jsonb_set(
    pizza,
    '{toppings,veggies}',
   '[{"tomato":"extra"}, {"spinach":"regular"}]',
   false
)
WHERE order_id = 20 and order_item_id = 5;
💡 路径里可以写数组下标

知道元素在数组里的位置时，可以直接写进路径：'{toppings,veggies,0,tomato}' 定位到 veggies 数组第一个元素的 tomato 字段，再设成 '"extra"'。

顾客正要放下手机，孩子发现他又点了香肠，建议去掉肉。爸爸做了最后一次修改：

UPDATE pizzeria.order_items
SET pizza = pizza #- '{toppings,meats}'
WHERE order_id = 20 AND order_item_id = 5;
💡 在数据库里构造 JSON

除了查询和修改，Postgres 还能从零生成 JSON：json_build_object、row_to_json、jsonb_agg 等。想在数据库层直接产出 JSON（比如 API 响应）时很有用。详见官方文档。

为 JSON 数据建索引

B-tree 表达式索引

应用里好几个组件都要统计某种类型的披萨数量：

EXPLAIN (analyze, costs off)
SELECT count(*)
FROM pizzeria.order_items
WHERE pizza ->> 'type' = 'custom';

 Aggregate (actual time=1.135..1.136 rows=1 loops=1)
   -> Seq Scan on order_items (actual time=0.034..1.062 rows=563 loops=1)
         Filter: ((pizza ->> 'type'::text) = 'custom'::text)
         Rows Removed by Filter: 2375
 Planning Time: 0.174 ms
 Execution Time: 1.185 ms

全表扫描。用第 4 章学的表达式索引，为 pizza ->> 'type' 建索引：

CREATE INDEX idx_pizza_type
ON pizzeria.order_items ((pizza ->> 'type'));

 Aggregate (actual time=0.299..0.300 rows=1 loops=1)
   -> Bitmap Heap Scan on order_items (actual time=0.170..0.257 rows=563 loops=1)
         Recheck Cond: ((pizza ->> 'type'::text) = 'custom'::text)
         Heap Blocks: exact=101
         -> Bitmap Index Scan on idx_pizza_type (actual time=0.068..0.068 rows=563 loops=1)
               Index Cond: ((pizza ->> 'type'::text) = 'custom'::text)
 Planning Time: 0.164 ms
 Execution Time: 0.376 ms

快了近 4 倍。但表达式索引有个代价：它只匹配建索引时写的那个表达式，稍有不同就用不上：

-- 换成 -> 运算符：索引用不上了，退回 Seq Scan
SELECT count(*) FROM pizzeria.order_items WHERE pizza -> 'type' = '"custom"';

-- 换一个字段 size：没有对应的索引，Seq Scan
SELECT count(*) FROM pizzeria.order_items WHERE pizza ->> 'size' = 'large';

可以规定开发团队一律写 pizza ->> 'type'，也可以再给 size 建一个表达式索引。但 JSON 里要查的字段一多，这种做法就扩展不了 —— 索引越多，维护越慢。

为什么我们非要用表达式索引，而不是直接给整个 pizza 列建一个索引？先看看 idx_pizza_type 的定义：

SELECT indexname, indexdef
FROM pg_indexes
WHERE schemaname = 'pizzeria'
  AND tablename = 'order_items'
  AND indexdef LIKE '%idx_pizza_type%';

   indexname    |                      indexdef
----------------+----------------------------------------------------
 idx_pizza_type | CREATE INDEX idx_pizza_type
                |   ON pizzeria.order_items
                |   USING btree (((pizza ->> 'type'::text)))
(1 row)

它用的是默认的 B-tree。如果直接用 B-tree 给整个 pizza 列建索引，它会把整个 JSON 当成一个值来索引： ->>、@> 这些运算符都用不上它，你只能拿一个一模一样的完整 JSON（连空格都一样）去做 = 比较 —— 毫无意义。 B-tree 不是唯一的选择，GIN 更适合 JSON。

GIN 索引

用 GIN 作为底层数据结构，只需在 JSON 列上建一个普通的单列索引，就能高效搜索整个嵌套结构。 Postgres 为 JSON 提供两种 GIN 索引，存储方式不同，支持的运算符类（operator class）也不同：

  • 默认 GIN（jsonb_ops）：把 JSON 里所有的键、值、数组元素都拆出来，各自作为独立的索引条目。
  • jsonb_path_ops：只索引从根到每个值的路径，并且存的是路径的哈希值。

默认 GIN 索引

以这份“三重奶酪”订单为例：

{
 "size": "large", "type": "three cheese", "crust": "thin", "sauce": "marinara",
 "toppings": { "cheese": [ {"cheddar": "regular"}, {"mozzarella": "extra"}, {"parmesan": "light"} ] }
}

默认 GIN 索引会把它拆成以下条目，每个条目都指向存着这份订单的那一行：

  • 键：size、type、crust、sauce、toppings、cheese、cheddar、mozzarella、parmesan
  • 值：large、three cheese、thin、marinara、regular、extra、light
ⓘ 为什么叫“倒排索引”

普通的思路是“一行 → 包含哪些词”；倒排索引反过来，“一个词 → 出现在哪些行”。就像书末的索引页：查“MVCC”，告诉你在第 39、42 页。第 6 章的全文搜索也用 GIN，原理一样。

CREATE INDEX idx_pizza_orders_gin
ON pizzeria.order_items
USING GIN(pizza);

统计自定义披萨的数量，这次用 @>：

EXPLAIN (analyze, costs off)
SELECT count(*)
FROM pizzeria.order_items
WHERE pizza @> '{"type": "custom"}';

 Aggregate (actual time=0.784..0.785 rows=1 loops=1)
   -> Bitmap Heap Scan on order_items (actual time=0.139..0.747 rows=563 loops=1)
         Recheck Cond: (pizza @> '{"type": "custom"}'::jsonb)
         Heap Blocks: exact=101
         -> Bitmap Index Scan on idx_pizza_orders_gin
              (actual time=0.109..0.110 rows=563 loops=1)
               Index Cond: (pizza @> '{"type": "custom"}'::jsonb)
 Planning Time: 1.444 ms
 Execution Time: 0.830 ms

GIN 查询总是走 Bitmap Index Scan，因为索引里只存了零散的键和值，而不是完整的 JSON：

  1. Postgres 分析 Index Cond，拆出要找的条目：type 和 custom。
  2. 在 GIN 索引里找到这两个条目，生成位图：标记出 JSON 里含有 type 或 custom 的行。
  3. Bitmap Heap Scan 逐一检查这些行（Recheck），只保留真正满足 {"type": "custom"} 的 —— type 必须是顶层键、custom 是它的值。这样能排除 {"custom": "type"} 这种结构反过来的行。

同一个索引能服务各种键和值的查询，包括多个条件组合、嵌套数组：

-- 小号 + 青酱：照样用 idx_pizza_orders_gin
SELECT count(*) FROM pizzeria.order_items
WHERE pizza @> '{"sauce": "pesto"}' and pizza @> '{"size": "small"}';

-- 嵌套数组：常规用量的切达奶酪
SELECT count(*) FROM pizzeria.order_items
WHERE pizza @> '{"toppings":{"cheese":[{"cheddar":"regular"}]}}';

 Aggregate (actual time=1.290..1.291 rows=1 loops=1)
   -> Bitmap Heap Scan on order_items (actual time=0.284..1.243 rows=638 loops=1)
         Recheck Cond: (pizza @> '{"toppings": {"cheese": [{"cheddar": "regular"}]}}'::jsonb)
         Rows Removed by Index Recheck: 90
         Heap Blocks: exact=101
         -> Bitmap Index Scan on idx_pizza_orders_gin (actual time=0.248..0.248 rows=728 loops=1)
 Execution Time: 1.351 ms

条件看起来复杂，但 Postgres 只是拆出 toppings、cheese、cheddar、regular 四个条目去索引里找，再回表核实层级和顺序是否完全匹配。 Rows Removed by Index Recheck: 90 就是“四个词都有、但位置对不上”被剔除的行。 一个 GIN 索引，足以支撑对嵌套 JSON 的各种快速查询。

非默认 GIN 索引：jsonb_path_ops

同一份三重奶酪订单，用 jsonb_path_ops 建索引时，会生成 7 条路径：

  • 4 条从顶层键到值的路径：size.large、type.three cheese、crust.thin、sauce.marinara
  • 3 条从 toppings 到嵌套数组里每个值的路径：toppings.cheese.cheddar.regular、toppings.cheese.mozzarella.extra、toppings.cheese.parmesan.light

而且存的不是文本，而是对每条路径算出的哈希值：定长整数比变长文本更小、比较更快。

CREATE INDEX idx_pizza_orders_paths_ops_gin
ON pizzeria.order_items
USING GIN (pizza jsonb_path_ops);

再执行同一个 @> '{"type": "custom"}' 查询，Postgres 选择了新的索引：

 Aggregate (actual time=0.681..0.682 rows=1 loops=1)
   -> Bitmap Heap Scan on order_items (actual time=0.106..0.644 rows=563 loops=1)
         Recheck Cond: (pizza @> '{"type": "custom"}'::jsonb)
         Heap Blocks: exact=101
         -> Bitmap Index Scan on idx_pizza_orders_paths_ops_gin
              (actual time=0.070..0.070 rows=563 loops=1)
               Index Cond: (pizza @> '{"type": "custom"}'::jsonb)
 Planning Time: 0.544 ms
 Execution Time: 0.736 ms
  1. 把 Index Cond 转换成路径 type.custom，算出哈希值。
  2. 用哈希值在 GIN 索引里做 Bitmap Index Scan，把可能匹配的行加入位图。
  3. Bitmap Heap Scan 回表核实，只保留真正满足条件的行 —— 这一步也处理了哈希碰撞（别的路径碰巧算出了同样的哈希值）。

对 @> 查询，Postgres 更偏爱 jsonb_path_ops 索引，因为定长整数的查找比变长文本快。而且它通常更小：

SELECT
    c.relname AS index_name,
    pg_size_pretty(pg_relation_size(c.oid)) AS index_size
FROM pg_class c
JOIN pg_index i ON c.oid = i.indexrelid
WHERE c.relname IN ('idx_pizza_orders_paths_ops_gin',
                    'idx_pizza_orders_gin');

           index_name           | index_size
--------------------------------+------------
 idx_pizza_orders_gin           | 112 kB
 idx_pizza_orders_paths_ops_gin | 56 kB
(2 rows)

只有一半大。代价是灵活性：它不单独存键，所以不支持 ? 这类“键是否存在”的运算符。比如找所有带“特殊说明”的订单：

EXPLAIN (analyze, costs off)
SELECT count(*)
FROM pizzeria.order_items
WHERE pizza ? 'special_instructions';

 Aggregate (actual time=0.095..0.096 rows=1 loops=1)
   -> Bitmap Heap Scan on order_items (actual time=0.089..0.089 rows=0 loops=1)
         Recheck Cond: (pizza ? 'special_instructions'::text)
         -> Bitmap Index Scan on idx_pizza_orders_gin (actual time=0.077..0.077 rows=0 loops=1)
               Index Cond: (pizza ? 'special_instructions'::text)
 Execution Time: 0.150 ms

这次 Postgres 只能选默认 GIN 索引。

小结

  • Postgres 2012 年开始支持 JSON，之后持续增强。
  • 有 json 和 jsonb 两种 JSON 类型，默认用 jsonb：二进制格式存储，查询更快，能用 GIN 索引。
  • 在 JSON 的灵活性和关系类型的效率之间找平衡，混合模式往往是好选择。
  • ->/->> 取值，? 判断键存在，@> 判断包含；SQL/JSON path 表达式能简洁地处理多层结构和数组。
  • jsonb_set 修改字段，#- 删除字段，不必整对象读写。
  • B-tree 表达式索引适合单个固定字段；两种 GIN 索引覆盖整个 JSON，jsonb_ops 更灵活，jsonb_path_ops 更小更快。
