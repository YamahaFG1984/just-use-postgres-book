备份、恢复与升级

“Just use Postgres”意味着越来越多的数据都放在这一个数据库里：业务表、JSON 文档、向量、时序、消息队列…… 这时备份就不再是可选项。这一页讲 Postgres 的几种备份方式、怎样把备份恢复回来，以及升级到新的大版本时要注意什么。

ⓘ 本页的命令都实际运行过

环境：Docker 里的 Postgres 17.2 和 18.1。例子用的是专题 3 的 rlstopic 数据库（50 万行、带角色和 RLS 策略），以及专题 5 的 apptopic 数据库。

本页目标

  • 分清逻辑备份、物理备份和持续归档（PITR）各自适合什么场景
  • 用 pg_dump 的几种格式备份，用 pg_restore 完整或部分恢复
  • 记得用 pg_dumpall --globals-only 备份角色
  • 在 Docker 环境下备份，避开数据卷的坑
  • 把 Postgres 从 17 升级到 18

三种备份方式

如果你用的是云厂商的托管 Postgres（RDS、Cloud SQL、Azure、Supabase、Neon 等），第三种通常已经内置了，在控制台里设置保留天数即可。 但 pg_dump 仍然值得掌握：迁移数据、复制一份到本地调试、升级大版本，都会用到它。

pg_dump：逻辑备份

三种输出格式

# 1. 纯 SQL 文本（默认）：一个能直接用 psql 执行的 .sql 文件
pg_dump -U postgres -f rls.sql rlstopic

# 2. 自定义格式 -Fc：压缩过的二进制文件，用 pg_restore 恢复（最常用）
pg_dump -U postgres -Fc -f rls.dump rlstopic

# 3. 目录格式 -Fd：每张表一个文件，可以用 -j 并行导出
pg_dump -U postgres -Fd -j 4 -f rls_dir rlstopic

du -sh rls.sql rls.dump rls_dir

12M	rls.sql
2.5M	rls.dump
2.5M	rls_dir
格式恢复用压缩选择性恢复并行什么时候用
纯 SQL（默认）psql -f✗（可自己 gzip）✗✗想看懂、想手改内容；很小的库
自定义 -Fcpg_restore✓✓恢复时 ✓默认选它
目录 -Fdpg_restore✓✓导出、恢复都 ✓大库，想用多核加速

★ pg_dump 不会挡住业务

pg_dump 在一个可重复读事务里读取所有表（专题 2），所以得到的是“某一时刻”完全一致的快照，备份期间应用照常读写。 它只拿很弱的共享锁，唯一会被它挡住的是 ALTER TABLE、DROP TABLE 这类改结构的操作。 不过它是一个长事务，备份大库期间会让 VACUUM 清理不了新产生的死元组（专题 4），尽量放在低峰期。

常用选项

pg_dump -h db.example.com -p 5432 -U postgres -Fc -f shop.dump shop   # 连远程库
pg_dump -U postgres -Fc -n sales -f sales.dump postgres                # 只备份 sales 模式
pg_dump -U postgres -Fc -t 'sales.orders*' -f orders.dump postgres     # 只备份某些表（支持通配符）
pg_dump -U postgres -Fc -T 'logs.*' -f nologs.dump postgres            # 排除某些表
pg_dump -U postgres --schema-only -f schema.sql postgres               # 只要表结构
pg_dump -U postgres --data-only -Fc -f data.dump postgres              # 只要数据

pg_restore：恢复

先看看备份里有什么

pg_restore -l apptopic.dump

221; 1259 17387 TABLE public accounts postgres
220; 1259 17377 TABLE public products postgres
219; 1259 17376 SEQUENCE public products_id_seq postgres
3378; 0 0 SEQUENCE OWNED BY public products_id_seq postgres
3216; 2604 17380 DEFAULT public products id postgres
3371; 0 17387 TABLE DATA public accounts postgres
3370; 0 17377 TABLE DATA public products postgres
3379; 0 0 SEQUENCE SET public products_id_seq postgres
3223; 2606 17394 CONSTRAINT public accounts accounts_pkey postgres
3221; 2606 17386 CONSTRAINT public products products_pkey postgres

备份是一个“目录”：表结构、数据、序列、约束、索引分别是独立的条目。pg_restore 会按正确的顺序执行它们：先建表，再导数据，最后建索引和约束（这样导数据更快）。

完整恢复

createdb -U postgres app_restored               # pg_restore 不会自己建库
pg_restore -U postgres -d app_restored apptopic.dump
psql -U postgres -d app_restored -c "SELECT count(*) FROM products"   # 4

想恢复到一个同名的库里、并且先删掉已有对象，可以加 --clean --if-exists；想让 pg_restore 自己建库，用 -C -d postgres（先连上 postgres 库，再按备份里的名字建库）。

坑：只恢复一张表会丢掉主键

createdb -U postgres only_products
pg_restore -U postgres -d only_products -t products apptopic.dump
psql -U postgres -d only_products -c "\d products"

                   Table "public.products"
 Column |     Type      | Collation | Nullable |   Default
--------+---------------+-----------+----------+--------------
 id     | integer       |           | not null |              ← 没有 nextval 默认值了
 name   | text          |           | not null |
 price  | numeric(10,2) |           | not null |
 stock  | integer       |           | not null | 0
 tags   | text[]        |           |          | '{}'::text[]
                                                               ← 也没有 Indexes: products_pkey

-t 只恢复表本身和它的数据，不包括主键、索引、序列这些单独的条目。需要精确控制时，用“目录清单”： 

pg_restore -l apptopic.dump | grep -E 'products' > list.txt   # 挑出和 products 相关的所有条目
#   TABLE、SEQUENCE、DEFAULT、TABLE DATA、SEQUENCE SET、CONSTRAINT products_pkey
pg_restore -U postgres -d only_products -L list.txt apptopic.dump   # 这次主键和序列都在了

要不要“遇错即停”

pg_restore 默认遇到错误继续执行，最后只给一个警告：

pg_restore: warning: errors ignored on restore: 7

这很容易被忽略，结果得到一个“少了点东西”的库。更安全的做法是加上：

pg_restore -U postgres -d rlstopic --single-transaction --exit-on-error rls.dump
# 任何一步出错，整个恢复回滚，库保持为空，退出码非 0

别忘了角色

pg_dump 只备份一个数据库里的东西。角色（用户）和它们的密码属于整个实例，不在任何一个数据库里，所以不在 pg_dump 的备份里。 把 rlstopic 恢复到一个全新的实例上： 

# 在全新的 Postgres 实例上
createdb -U postgres rlstopic
pg_restore -U postgres -d rlstopic --single-transaction --exit-on-error rls.dump
echo "exit=$?"

pg_restore: error: could not execute query: ERROR:  role "app_user" does not exist
Command was: CREATE POLICY hide_archived ON public.notes AS RESTRICTIVE FOR SELECT TO app_user USING ((NOT archived));
exit=1

策略、GRANT、表的所有者都引用了角色。解决办法是用 pg_dumpall --globals-only 把所有角色（以及表空间）单独导出：

# 在旧实例上
pg_dumpall -U postgres --globals-only -f globals.sql

# 在新实例上：先建角色，再恢复数据库
psql -U postgres -f globals.sql      # 会提示 role "postgres" already exists，可以忽略
createdb -U postgres rlstopic
pg_restore -U postgres -d rlstopic rls.dump        # exit=0

globals.sql 的内容大致是这样（密码是加密后的哈希）：

CREATE ROLE app_user;
ALTER ROLE app_user WITH NOSUPERUSER INHERIT NOCREATEROLE NOCREATEDB LOGIN NOREPLICATION NOBYPASSRLS
  PASSWORD 'SCRAM-SHA-256$4096:…';
CREATE ROLE reporter;
ALTER ROLE reporter WITH NOSUPERUSER INHERIT NOCREATEROLE NOCREATEDB LOGIN NOREPLICATION BYPASSRLS;
…
💡 只想要数据，不要权限

把生产库复制到本地调试时，往往不需要原来的角色。pg_restore --no-owner --no-privileges 会跳过所有 OWNER 和 GRANT，对象都归执行恢复的用户所有。但 RLS 策略里写的 TO app_user 仍然需要角色存在。

在 Docker 里备份

第 1 章的数据库跑在名为 postgres 的容器里。宿主机上不需要装任何 Postgres 工具，直接借用容器里的：

# 备份：容器里的 pg_dump 输出到标准输出，宿主机重定向到文件（不要加 -t，会破坏二进制输出）
docker exec postgres pg_dump -U postgres -Fc postgres > postgres-$(date +%F).dump
docker exec postgres pg_dumpall -U postgres --globals-only > globals.sql

# 恢复：-i 把宿主机文件喂给容器里的 pg_restore 的标准输入
docker exec postgres createdb -U postgres restored
docker exec -i postgres pg_restore -U postgres -d restored < postgres-2026-10-20.dump

直接打包数据卷

数据都在第 1 章创建的 postgres-volume 卷里，也可以把整个卷打包，这就是一种最简单的物理备份。但必须先停掉数据库：

docker stop postgres
docker run --rm -v postgres-volume:/data:ro -v "$PWD":/backup alpine:3.20 \
    tar czf /backup/pgdata.tgz -C /data .
docker start postgres
⚠ 不要在数据库运行时复制数据文件

数据库运行时，数据文件随时在变化，一部分修改还只在内存和 WAL 里。这时 tar / cp / 云盘快照得到的很可能是一份无法启动或者数据损坏的副本。 要在线做物理备份，用下面的 pg_basebackup。

物理备份与时间点恢复

pg_basebackup 通过复制协议，在数据库运行时得到一份一致的物理备份：

pg_basebackup -U postgres -D /backups/base -Ft -z -c fast
#   -Ft  打包成 tar     -z  gzip 压缩     -c fast  立即做检查点，不必等待
ls /backups/base

backup_manifest      ← 每个文件的校验和，可用 pg_verifybackup 校验
base.tar.gz          ← 数据文件
pg_wal.tar.gz        ← 备份期间产生的 WAL，恢复时需要

它解决了“大库备份太慢”的问题，但恢复出来的仍然是“备份那一刻”。Postgres 的每一个修改都会先写进 WAL（Write-Ahead Log，预写日志），再落到数据文件里，崩溃后就靠它恢复。 如果把 WAL 也持续地保存下来，就能从一份基础备份开始“重放”WAL，停在任何想要的时刻：

原理不复杂，但手工配置归档（archive_mode、archive_command）、管理保留策略、做恢复演练都很繁琐。 生产环境一般使用专门的工具：pgBackRest、Barman、WAL-G，它们负责基础备份、WAL 归档、压缩、加密、上传到对象存储和一键恢复。 用托管服务的话，这一切通常已经替你做好。

升级 Postgres

小版本 vs 大版本

小版本（17.2 → 17.6）大版本（17 → 18）
内容只修 bug 和安全漏洞新功能，内部存储格式可能变化
数据文件兼容，直接用不兼容，必须迁移
怎么升换新的二进制 / 镜像，重启即可dump + restore、pg_upgrade 或逻辑复制
多久一次大约每季度，应该及时跟上每年一个；每个大版本支持 5 年

用新的大版本镜像去打开旧版本的数据目录，Postgres 会直接拒绝启动：

FATAL:  database files are incompatible with server
DETAIL:  The data directory was initialized by PostgreSQL version 17,
         which is not compatible with this version 18.1 (Debian 18.1-1.pgdg13+2).

Docker 用户注意：18 的镜像改了数据目录

官方 postgres 镜像从 18 开始，把数据目录从 /var/lib/postgresql/data 改成了按版本区分的 /var/lib/postgresql/18/docker， 并建议把卷挂载到上一级 /var/lib/postgresql（这样新旧版本的目录可以放在同一个卷里，方便 pg_upgrade --link）。 如果沿用第 1 章 -v postgres-volume:/var/lib/postgresql/data 的写法去跑 postgres:18，容器会报错退出： 

Error: in 18+, these Docker images are configured to store database data in a
       format which is compatible with "pg_ctlcluster" (specifically, using
       major-version-specific directory names).  …
       Counter to that, there appears to be PostgreSQL data in:
         /var/lib/postgresql/data
       …
       The suggested container configuration for 18+ is to place a single mount
       at /var/lib/postgresql which will then place PostgreSQL data in a
       subdirectory, …

实测即使挂载的是一个空卷，也会这样报错。所以 18 及以后的版本，启动命令要写成：

docker run --name postgres18 -e POSTGRES_PASSWORD=password -p 5433:5432 \
    -v postgres18-volume:/var/lib/postgresql \
    -d postgres:18.1

方法一：dump + restore（最简单）

# 在 18 的容器里，用 18 版本的工具连接旧的 17 实例导出
docker exec -e PGPASSWORD=password postgres18 \
    pg_dumpall -h 旧实例地址 -U postgres --globals-only -f /tmp/globals.sql
docker exec -e PGPASSWORD=password postgres18 \
    pg_dump -h 旧实例地址 -U postgres -Fc -f /tmp/rls17.dump rlstopic

# 导入新实例
docker exec postgres18 psql -U postgres -q -f /tmp/globals.sql
docker exec postgres18 createdb -U postgres rlstopic
docker exec postgres18 pg_restore -U postgres -d rlstopic /tmp/rls17.dump
docker exec postgres18 psql -U postgres -d rlstopic -c "SELECT count(*) FROM notes"

两个容器怎么互相访问：可以把它们放进同一个 Docker 网络（docker network create，然后用容器名当主机名）， 或者在旧容器映射了 5432 端口时用 host.docker.internal（Docker Desktop）。

💡 用新版本的 pg_dump

pg_dump 能导出比它自己旧的服务器，反过来不行。跨版本迁移时，总是用目标版本（新版本）的 pg_dump 去连接旧服务器，就像上面在 18 的容器里执行那样。

方法二和三：数据量大的时候

  • pg_upgrade：直接把旧的数据目录转换成新版本的格式。--link 模式用硬链接而不是复制，几百 GB 的库也只需要几分钟停机。但它需要新旧两个版本的二进制同时存在，在 Docker 里操作比较繁琐（社区有 pgautoupgrade 之类的镜像帮你做）。
  • 逻辑复制：先建好新版本实例，用发布 / 订阅（CREATE PUBLICATION / CREATE SUBSCRIPTION）把数据持续同步过去，同步追上后再切换应用，停机时间可以缩短到秒级。步骤最多，适合不能停机的系统。
方法停机时间复杂度适合
dump + restore和数据量成正比低几十 GB 以内，可以安排维护窗口
pg_upgrade --link几分钟中大库，可以接受短暂停机
逻辑复制秒级高不能停机的系统
⚠ 升级前的检查清单
  • 先做一份完整备份，并确认能恢复。
  • 用到的扩展（pgvector、PostGIS、TimescaleDB、zhparser……）在新版本上都有可用的版本吗？
  • 读一遍新版本发行说明里的“Migration”部分，留意不兼容的改动。
  • 在新版本上跑一遍应用的测试。
  • 升级后执行 ANALYZE（或 vacuumdb --all --analyze-in-stages）。dump + restore 不会带上统计信息；pg_upgrade 在 18 之前也不会（18 起保留了大部分，但扩展统计信息仍需重建）。没有统计信息，规划器会选出很差的计划（第 4 章）。

备份的纪律

  • 自动化：用 cron 或调度系统每天执行备份脚本，失败要告警。
  • 演练恢复：定期把备份恢复到一台临时机器上，跑几个检查查询（行数、最新一条记录的时间），记录花了多久，这就是你真实的恢复时间。
  • 备份也是数据：备份文件里有全部数据和密码哈希，要和生产库同等对待：加密、限制访问。
  • 备份不是副本：主从复制会把 DROP TABLE 也忠实地同步过去，它防的是机器故障，防不了误操作。

小结

  • 逻辑备份（pg_dump）灵活、可跨版本；物理备份（pg_basebackup）适合大库；持续归档 + PITR 能恢复到任意时间点，生产环境用 pgBackRest 等工具或托管服务。
  • pg_dump 默认用 -Fc，它在一致的快照里导出，不阻塞读写。
  • pg_restore 不建库、默认遇错继续；用 --single-transaction --exit-on-error 更安全；-t 不会恢复主键和索引。
  • 角色不在 pg_dump 里，用 pg_dumpall --globals-only 单独备份，并且先恢复它。
  • Docker 里用 docker exec … pg_dump > 文件；打包数据卷前必须停库。
  • 大版本数据文件不兼容：用新版本的 pg_dump 导出再导入，或者 pg_upgrade、逻辑复制。18 的官方镜像要把卷挂在 /var/lib/postgresql。
  • 没有恢复过的备份不算备份。
