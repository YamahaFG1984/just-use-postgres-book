附录 B

什么时候别用 Postgres

和任何技术一样，Postgres 有长处也有短处：有些场景它大放异彩，有些负载它并不是最佳选择。 虽然这本书叫《Just Use Postgres!》，Postgres 社区的很多人也在推广它，但大家都明白：它既不是银弹，也不是能替代所有数据库的瑞士军刀。

为什么不列一张“弱点清单”

如果你期待这篇附录列出 Postgres 的一串弱点，作者恐怕要让你失望了。主要原因是：就算现在说“场景 X 别用 Postgres”，书出版一两年后这条建议可能就不成立了。 Postgres 和它的生态发展得太快，今天不支持的，不久之后可能轻松就能做到 —— 回顾本书，向量搜索、时序、消息队列，几年前都还不是人们会想到 Postgres 的场景。

但抛开技术和业务场景，作者在决定是否使用 Postgres 之前，总会考虑三个理由。它们能帮你做出更周全、更少偏见的决定。

三种情况下不用 Postgres

🧩

① 别的数据库就是更合适

另一个数据库能轻松支持这个场景，而改用 Postgres 很难或不可能。没必要过度设计，硬把 Postgres 塞进去，给自己和团队添麻烦。

🛡

② 现有方案运行良好

应用已经在用另一个数据库，并没有真正的替换需要。为了用 Postgres 而用 Postgres 毫无意义。它干得好、大家没意见，就别去破坏已经正常运转的东西 —— 哪怕它是付费产品、公司每年花一大笔钱，公司愿意付就让它付。

👥

③ 团队更熟悉别的数据库

如果 Postgres 和另一个数据库同样适合，那就利用团队已有的经验：你们可能交付得更快、犯错更少、处理线上问题更有把握。这也许还是你学点新东西、拓宽数据库视野的好机会。

作者的亲身经历

❝ 一个没有被替换掉的文档数据库

尽管 Postgres 是作者最喜欢、也是默认的数据库，他在把它引入项目之前，仍然会认真对待这三条理由。 有一次他加入一个项目，团队正在顺利地使用一个文档数据库：它对这个应用很合适，整个团队也用得非常顺手。 在他的帮助下，团队完全可以轻松地把它换成 Postgres —— 但他提都没提。 相反，他决定更深入地研究那个数据库，最后帮团队大幅优化了它的用法，把基础设施成本降到了原来的五分之一。

这正是第 1 章说的那句话的另一面：“Just use Postgres”是一个经验之谈，提醒你在往技术栈里加第二个数据库之前，先看看 Postgres 能不能搞定； 它不是一条要求你把一切都换成 Postgres 的教条。

后记：少一个系统，少一份负担

本书的后记由《High-Performance Java Persistence》的作者 Vlad Mihalcea 撰写，他的经历从另一个角度说明了“就用 Postgres”的价值：

  • 2008 年他第一次在一个物流企业应用里用 PostgreSQL（之前只用过 Oracle 和 SQL Server），就惊讶于 Postgres 8.3 的丰富特性：数组、枚举类型、全文搜索和 GIN 索引、几何类型和 GiST 索引、多值插入、NOWAIT……
  • 2011 年一个项目需要处理外部供应商的 JSON 文档：解析后存入关系表，同时还要保留原始 JSON 以便审计时追溯。当时的关系数据库还不支持在 JSON 里搜索，于是他们引入了 MongoDB。
  • 他的结论是：开发阶段加一个数据库很容易，在生产环境维护它很难 —— 监控、备份、升级、新人培训，还要仔细评估哪些特性影响性能。
  • 从 9.4 版开始 PostgreSQL 原生支持 JSON（jsonb），很多以前需要 NoSQL 数据库的项目从此可以“就用 Postgres”。运行的系统越少，可动的部件越少，系统越容易维持。“保持简单”不只适用于开发，对系统架构甚至更有价值。
  • 近年来在他的培训课上，越来越多的项目几乎只用 PostgreSQL。

  • 从没在项目里用过 Postgres？开始用它。第 1–4 章的内容足以支撑大多数事务型应用。
  • 已经用了很多年？试试把它用在本书介绍的另一个场景上：JSON、全文搜索、向量、时序、地理、队列……

    • Database Connection Pooling: Why It Matters? Essential OS-Level Insights —— 从操作系统层面看，没有连接池时应用和数据库之间发生了什么，以及连接池为什么能减少开关连接的开销。

💡 最后一句话

持续在 Postgres 上投入时间吧。考虑到它已经无处不在、普及速度又这么快，这份投入一定会有丰厚的回报。

小结

  • Postgres 不是银弹；“Just use Postgres”是建议，不是教条。
  • 技术上的弱点会随着 Postgres 和生态的快速演进而改变，所以不必背一张“弱点清单”。
  • 三种情况下别用 Postgres：别的数据库明显更适合；现有数据库运转良好、没有替换需求；团队对另一个同样合适的数据库更熟悉。
  • 系统越少，运维负担越轻 —— 在 Postgres 能胜任的前提下，少引入一个数据库就是赚到。

思考题

  1. 回顾你正在参与的项目：它用了几种数据存储？如果把其中某一个换成 Postgres，用三个问题（图 B-1）检验一下，值得吗？
  2. 挑本书中的一个场景（比如第 11 章的消息队列），列出在你的业务规模下，什么信号会让你决定“该换专用系统了”。
  3. 试着为你的团队写一页“数据库选型原则”，其中至少包含本附录的三条理由。
