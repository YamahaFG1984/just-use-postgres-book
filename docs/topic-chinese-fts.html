中文全文搜索

第 6 章用的都是英文。如果直接把那一套用在中文上，会发现搜什么都搜不到 —— 因为中文词与词之间没有空格，Postgres 内置的解析器根本不知道该在哪里切开。 这一页用 zhparser 扩展给 Postgres 装上中文分词，并对比 pg_trgm 和第 8 章的向量搜索，帮你选对方案。

ⓘ 本页的例子都实际运行过

所有输出均在 Postgres 17.2 + zhparser 2.4（SCWS 1.2.3）上实测得到。阅读前最好先读完第 6 章，本页沿用那里的概念：词素、tsvector、tsquery、全文搜索配置、GIN。

本页目标

  • 理解默认配置为什么处理不了中文
  • 构建带 zhparser 的 Postgres 镜像，创建中文全文搜索配置
  • 用中文完成第 6 章的全套操作：生成列、查询、排序、高亮、GIN 索引
  • 调优分词：自定义词典（以及它的一个大坑）、复合词拆分
  • 知道 pg_trgm 对中文的局限，会在全文搜索、模糊匹配、语义搜索之间选择

问题：默认配置不认识中文

拿第 6 章那句“5 explorers are traveling to a distant galaxy”的中文版试试：

SELECT to_tsvector('simple',  '五名探险家正在前往遥远的星系');
SELECT to_tsvector('english', '五名探险家正在前往遥远的星系');

           to_tsvector
----------------------------------
 '五名探险家正在前往遥远的星系':1
(1 row)

两种配置的结果一模一样：整句话被当成了一个词素。于是搜“星系”什么也搜不到 —— 词素里只有“五名探险家正在前往遥远的星系”这一个“词”。

Postgres 的全文搜索框架是可插拔的：解析器（parser）负责切词，字典负责规范化（回顾第 6 章图 6-4）。 所以中文的解法就是换一个懂中文的解析器。常见的选择有基于 SCWS 词典的 zhparser 和基于结巴分词的 pg_jieba。本页用 zhparser。

构建带 zhparser 的 Postgres

zhparser 不在官方镜像和 PGDG 软件源里，需要从源码编译（依赖 SCWS 分词库）。本书仓库的 extras/zhparser/Dockerfile 已经写好了： 

# Postgres 17 + zhparser（基于 SCWS 的中文分词扩展）
ARG PG_IMAGE=postgres:17.2

FROM ${PG_IMAGE} AS build
ARG SCWS_VERSION=1.2.3
ARG ZHPARSER_COMMIT=2e995c4df672563992b4d7a147b8fa2d0d4cda6c
RUN apt-get update \
 && apt-get install -y --no-install-recommends \
      build-essential ca-certificates git wget bzip2 \
      postgresql-server-dev-${PG_MAJOR} \
 && rm -rf /var/lib/apt/lists/*
WORKDIR /build
RUN wget -q -O - http://www.xunsearch.com/scws/down/scws-${SCWS_VERSION}.tar.bz2 | tar xjf - \
 && cd scws-${SCWS_VERSION} && ./configure && make && make install
RUN git clone https://github.com/amutu/zhparser.git \
 && cd zhparser && git checkout ${ZHPARSER_COMMIT} \
 && make && make install

FROM ${PG_IMAGE}
COPY --from=build /usr/local/lib/libscws.so* /usr/local/lib/
COPY --from=build /usr/lib/postgresql/${PG_MAJOR}/lib/zhparser.so /usr/lib/postgresql/${PG_MAJOR}/lib/
COPY --from=build /usr/share/postgresql/${PG_MAJOR}/extension/zhparser* /usr/share/postgresql/${PG_MAJOR}/extension/
COPY --from=build /usr/share/postgresql/${PG_MAJOR}/tsearch_data/dict.utf8.xdb \
                  /usr/share/postgresql/${PG_MAJOR}/tsearch_data/rules.utf8.ini \
                  /usr/share/postgresql/${PG_MAJOR}/tsearch_data/
RUN ldconfig
⚠ 不要在运行中的容器里直接 apt install 开发包

写这一页时我们踩过这个坑：在 postgres:17.2 容器里直接 apt install postgresql-server-dev-17，apt 会把服务器包顺带升级到软件源里最新的 17.x 小版本。 结果正在运行的 17.2 服务器加载 pg_trgm 时报错：could not load library ".../pg_trgm.so": undefined symbol: pg_mblen_unbounded。 多阶段构建把编译环境和运行环境彻底隔开，就不会出这种问题。

在仓库根目录构建并启动（先停掉占用 5432 端口的容器）：

docker build -t postgres-zhparser:17 extras/zhparser

docker volume create postgres-zh-volume
docker run --name postgres-zh \
    -e POSTGRES_USER=postgres -e POSTGRES_PASSWORD=password \
    -p 5432:5432 \
    -v postgres-zh-volume:/var/lib/postgresql/data \
    -d postgres-zhparser:17

docker exec -it postgres-zh psql -U postgres
ⓘ Apple Silicon

镜像是从源码编译的，postgres 官方镜像也是多架构的，所以理论上在 arm64 上直接 docker build 即可（本页在 amd64 上验证）。

创建中文全文搜索配置

CREATE EXTENSION zhparser;

-- 新建一个配置，用 zhparser 作解析器
CREATE TEXT SEARCH CONFIGURATION chinese (PARSER = zhparser);

-- 指定哪些词性要保留、交给哪个字典
ALTER TEXT SEARCH CONFIGURATION chinese
  ADD MAPPING FOR n,v,a,i,e,l,x WITH simple;

和第 6 章一样，配置 = 解析器 + 映射。zhparser 切出的每个词都带一个词性（token type），映射决定哪些词性要保留。没有映射的词性会被丢弃，相当于停用词。 \dFp+ zhparser 可以看到它支持的全部 26 种词性，节选：

代号词性例子本页是否保留
n名词 noun探险家、星系、地球✓
v动词 verb前往、穿越、寻找✓
a形容词 adjective遥远、巨大✓
i成语 idiom—✓
e感叹词 exclamation—✓
l习用语 tmp—✓
x未知词 unknown词典里没有的词、自定义词✓（原因见后文）
u助词 auxiliary的、了✗
m数词 numeral一、五✗
p c d r介词、连词、副词、代词在、和、很、我✗
w标点，。✗

★ 仔细看，分词切错了

“带着地球”被切成了 带 / 着地 / 球，“虫洞”被切成了 虫 / 洞，“为人类”被切成了 为人 / 类。 这是基于词典的分词的天然局限：遇到歧义或词典里没有的词就可能切错。后果是搜“虫洞”找不到《星际穿越》。下一节专门讲怎么调优。

查询：三种 tsquery 函数都能用

SELECT to_tsquery('chinese', '地球 & 家园');
SELECT plainto_tsquery('chinese', '寻找新的家园');
SELECT websearch_to_tsquery('chinese', '宇航员 -火星');

   to_tsquery
-----------------
 '地球' & '家园'

    plainto_tsquery
------------------------
 '寻找' & '新' & '家园'

 websearch_to_tsquery
----------------------
 '宇航员' & !'火星'

用户的搜索词也经过同样的中文分词，“的”被去掉了。websearch_to_tsquery 里的 -火星 变成了 NOT：

SELECT title FROM articles
WHERE tsv @@ websearch_to_tsquery('chinese', '宇航员 -火星');
-- 星际穿越（《火星救援》被排除）

SELECT title FROM articles
WHERE tsv @@ websearch_to_tsquery('chinese', '火星 or 三体');
-- 三体、火星救援

短语查询

SELECT phraseto_tsquery('chinese', '寻找新的家园');
-- '寻找' <-> '新' <-> '家园'

SELECT title FROM articles WHERE tsv @@ phraseto_tsquery('chinese', '寻找新的家园');
-- 流浪地球、星际穿越

SELECT title FROM articles WHERE tsv @@ phraseto_tsquery('chinese', '新的寻找家园');
-- (0 rows) 词序不对就不匹配
ⓘ 被丢弃的词不占位置

看上面的 tsvector：'寻找':16B '新':17B '家园':18B 是连续的 —— 被丢弃的“的”没有占用位置编号。这和第 6 章英文停用词“保留位置”的行为不同，所以“寻找新的家园”能被 寻找 <-> 新 <-> 家园 匹配上。

排序与高亮

SELECT id, title, ts_rank(tsv, q) AS rank
FROM articles, to_tsquery('chinese', '地球') q
WHERE tsv @@ q
ORDER BY rank DESC;

 id |  title   |    rank
----+----------+------------
  1 | 流浪地球 | 0.66871977
  2 | 三体     | 0.24317084
  5 | 星际穿越 | 0.24317084
(3 rows)

《流浪地球》片名（权重 A）里有“地球”，排在最前 —— 和第 6 章 ghost 的例子一模一样。高亮同样可用，用 HTML 的 <mark> 标签代替默认的 <b>：

SELECT title,
  ts_headline('chinese', body, to_tsquery('chinese', '家园'),
              'StartSel=<mark>, StopSel=</mark>')
FROM articles
WHERE tsv @@ to_tsquery('chinese', '家园');

  title   |                          ts_headline
----------+---------------------------------------------------------------
 流浪地球 | 巨大的推进器，带着地球逃离太阳系，寻找新的<mark>家园</mark>。
 星际穿越 | 穿越虫洞，在遥远的星系中为人类寻找新的<mark>家园</mark>。
(2 rows)
⚠ ts_headline 第一个参数别漏

ts_headline 会对原文重新分词，所以要显式传 'chinese'。不传就用默认配置（english），整句当成一个词，什么也高亮不出来。

GIN 索引

往表里再填 2 万行无关数据，对比有无索引：

INSERT INTO articles (title, body)
SELECT '填充' || g, md5(g::text) FROM generate_series(1, 20000) g;
ANALYZE articles;

EXPLAIN (analyze, costs off)
SELECT title FROM articles WHERE tsv @@ to_tsquery('chinese', '火星');

 Seq Scan on articles (actual time=0.020..7.385 rows=1 loops=1)
   Filter: (tsv @@ '''火星'''::tsquery)
   Rows Removed by Filter: 20005
 Execution Time: 7.399 ms

CREATE INDEX articles_tsv_gin ON articles USING GIN (tsv);

 Bitmap Heap Scan on articles (actual time=0.016..0.017 rows=1 loops=1)
   Recheck Cond: (tsv @@ '''火星'''::tsquery)
   Heap Blocks: exact=1
   ->  Bitmap Index Scan on articles_tsv_gin (actual time=0.010..0.010 rows=1 loops=1)
         Index Cond: (tsv @@ '''火星'''::tsquery)
 Execution Time: 0.040 ms

7.4 ms → 0.04 ms。一旦分好词，后面的一切（GIN、GiST、权重、ts_rank）都和英文完全一样。

调优分词

自定义词典

词典里没有“虫洞”，所以它被切成了两个单字。zhparser 2.x 提供了一张自定义词表 zhparser.zhprs_custom_word，往里加词，再调用同步函数： 

INSERT INTO zhparser.zhprs_custom_word VALUES ('虫洞');
SELECT sync_zhprs_custom_word();

新开一个会话（词典在会话启动时加载），再试：

SELECT to_tsvector('chinese', '一队宇航员穿越虫洞');

        to_tsvector
----------------------------
 '宇航员':2 '穿越':3 '队':1
(1 row)

“虫洞”不是被正确切出来了，而是整个消失了！用 ts_debug 查原因：

SELECT token, alias, description, lexemes
FROM ts_debug('chinese', '一队宇航员穿越虫洞');

 token  | alias |  description   | lexemes
--------+-------+----------------+----------
 一     | m     | numeral,数词   |
 队     | n     | noun,名词      | {队}
 宇航员 | n     | noun,名词      | {宇航员}
 穿越   | v     | verb,动词      | {穿越}
 虫洞   | x     | unknown,未知词 |
(5 rows)

自定义词的词性是 x（未知词）。如果配置里没映射 x，它就被当成停用词丢掉了。加上映射：

ALTER TEXT SEARCH CONFIGURATION chinese ADD MAPPING FOR x WITH simple;

SELECT to_tsvector('chinese', '一队宇航员穿越虫洞');

             to_tsvector
-------------------------------------
 '宇航员':2 '穿越':3 '虫洞':4 '队':1
(1 row)

修改词典后，已有数据要重算

词典只影响之后的分词。生成列里已经存好的 tsvector 不会自动变。好在存储型生成列在行被 UPDATE 时会重新计算，所以“原地更新”一下就行： 

UPDATE articles SET title = title;   -- 触发生成列重算

SELECT tsv FROM articles WHERE id = 5;
-- ... '虫洞':9B ...    之前的 '虫':9B '洞':10B 没有了

SELECT title FROM articles WHERE tsv @@ to_tsquery('chinese', '虫洞');
-- 星际穿越 ✓
💡 大表怎么办

整表 UPDATE 会改写每一行、产生大量死元组（见专题 4）。大表可以按主键分批更新，或者在低峰期执行，完成后跑一次 VACUUM。

复合词拆分：multi_short

搜“人民”能找到“中华人民共和国”吗？默认不能，因为它被当成一个完整的词：

SELECT to_tsvector('chinese', '中华人民共和国');
--  '中华人民共和国':1

SET zhparser.multi_short = on;     -- 长词再额外拆出短词
SELECT to_tsvector('chinese', '中华人民共和国');

                   to_tsvector
-------------------------------------------------
 '中华':2 '中华人民共和国':1 '人民':3 '共和国':4
(1 row)

长词保留，同时多出了“中华”“人民”“共和国”，召回率提高了。zhparser 的主要参数：

参数作用
zhparser.multi_short长词再拆出短词（最常用）
zhparser.multi_duality把单字组合成二元词
zhparser.multi_zmain / multi_zall拆出重要单字 / 全部单字
zhparser.seg_with_duality词典外的散字两两组合
zhparser.punctuation_ignore忽略标点
zhparser.dict_in_memory词典全部载入内存（更快，更占内存）
zhparser.extra_dicts额外的词典文件

SET 只对当前会话生效。要持久化，可以设在数据库级别（新连接生效）：

ALTER DATABASE postgres SET zhparser.multi_short = on;
⚠ 写入和查询要用同样的设置

如果写入时开了 multi_short、查询时没开（或反过来），两边切出来的词不一致，就会漏结果。所以要么设在数据库级别统一生效，要么写入和查询使用同一个连接配置。改设置后，同样要重算已有数据。

另一条路：pg_trgm 模糊匹配

不想装扩展？Postgres 自带的 pg_trgm 扩展（第 6 章提到过它可以做拼写纠错）能给 LIKE '%关键词%' 建索引。 它把字符串拆成三元组（连续三个字符）来比较，不需要分词，所以对中文也适用： 

CREATE EXTENSION pg_trgm;
CREATE INDEX articles_body_trgm ON articles USING GIN (body gin_trgm_ops);

EXPLAIN (analyze, costs off)
SELECT title FROM articles WHERE body LIKE '%宇航员%';

 Bitmap Heap Scan on articles (actual time=0.033..0.034 rows=2 loops=1)
   Recheck Cond: (body ~~ '%宇航员%'::text)
   ->  Bitmap Index Scan on articles_body_trgm (actual time=0.010..0.010 rows=2 loops=1)
         Index Cond: (body ~~ '%宇航员%'::text)
 Execution Time: 0.053 ms

三个字的“宇航员”走了索引。但换成两个字的“火星”：

EXPLAIN (analyze, costs off)
SELECT title FROM articles WHERE body LIKE '%火星%';

 Seq Scan on articles (actual time=0.011..3.839 rows=1 loops=1)
   Filter: (body ~~ '%火星%'::text)
   Rows Removed by Filter: 20005
 Execution Time: 3.846 ms
ⓘ 二元组方案

针对这个问题，社区有基于二元组（2-gram）的 pg_bigm 扩展，最初就是为日文、中文这类不分词的语言设计的，两个字的查询也能用索引。它同样需要自行编译安装，本页没有演示。

pg_trgm 也能算相似度，适合做“你是不是要找……”：

SELECT similarity('流浪地球', '流浪地球2');   -- 0.5714286
SELECT similarity('流浪地球', '地球流浪');    -- 0     三元组对顺序很敏感

SELECT title, similarity(title, '流浪的地球') AS sim
FROM articles WHERE title % '流浪的地球';     -- % 表示相似度超过阈值（默认 0.3）
--   流浪地球 | 0.375

怎么选

💡 混合搜索

实践中常把全文搜索和向量搜索结合：全文搜索保证“关键词一定命中”，向量搜索补充“意思相近”，再把两路结果的排名合并。它们都在同一个 Postgres 里，一条 SQL 就能写完。

小结

  • 默认的 simple / english 配置会把中文整句当成一个词素，必须换成懂中文的解析器。
  • zhparser 需要从源码编译，用多阶段 Dockerfile，不要在运行中的容器里装编译依赖。
  • 中文配置 = zhparser 解析器 + 词性映射到 simple 字典；建议把 x 也映射上。
  • 分好词之后，第 6 章的一切（生成列、权重、tsquery、ts_rank、ts_headline、GIN）都照常可用。
  • 用自定义词典修正分词，记得映射 x、新开会话、重算已有数据；multi_short 能提高复合词的召回率，写入和查询要保持一致。
  • pg_trgm 对两字以下的中文查询用不上索引，适合较长字符串的模糊匹配，不适合当中文搜索主力。

  3. 给 articles 加一个用户评论表，用触发器或生成列为评论建立中文 tsvector，实现“片名 A、简介 B、评论 C”三档权重。
    参考答案 
    CREATE TABLE comments (
  id serial PRIMARY KEY,
  article_id int NOT NULL REFERENCES articles ON DELETE CASCADE,
  content text NOT NULL
);
-- 生成列只能引用本行的列，评论在另一张表，所以用触发器维护一列
ALTER TABLE articles ADD COLUMN comments_tsv tsvector NOT NULL DEFAULT '';

CREATE OR REPLACE FUNCTION refresh_comments_tsv() RETURNS trigger AS $$
DECLARE aid int := coalesce(NEW.article_id, OLD.article_id);
BEGIN
  UPDATE articles a
  SET comments_tsv = setweight(to_tsvector('chinese',
        coalesce((SELECT string_agg(content, ' ') FROM comments c WHERE c.article_id = aid), '')), 'C')
  WHERE a.id = aid;
  RETURN NULL;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER comments_tsv_trg
AFTER INSERT OR UPDATE OR DELETE ON comments
FOR EACH ROW EXECUTE FUNCTION refresh_comments_tsv();

  4. 对 2 万行的表分别建 GIN（tsvector）和 GIN（gin_trgm_ops）索引，用 pg_relation_size 比较大小。
    参考答案 
    SELECT indexrelname, pg_size_pretty(pg_relation_size(indexrelid))
FROM pg_stat_user_indexes WHERE relname = 'articles';

        indexrelname    | pg_size_pretty
--------------------+----------------
 articles_body_trgm | 2896 kB
 articles_tsv_gin   | 7352 kB

    这里 tsvector 的 GIN 反而更大，是被填充数据“带偏”了：那 2 万行是 md5 字符串，zhparser 把每串切成十几个毫无规律的片段，一共产生了 104,048 个不同的词素，每个都要在 GIN 里占一个键； 而十六进制字符组成的三元组总共只有 4,842 种，GIN 的键很少、行列表压缩得很好。换成真实的中文文本，结论可能完全不同，这正说明索引大小要用自己的数据去测。
