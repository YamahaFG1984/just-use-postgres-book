第 11 章

用 Postgres 做消息队列

消息队列让服务和系统组件之间可以异步通信：一个服务（生产者）不直接调用另一个服务，而是把消息发到队列； 另一个服务（消费者）稍后读取并处理。队列一直保存着消息，直到它们被处理、删除。 常见用途有：用队列作为异步通信层来解耦应用、广播和交换事件、在多个工作进程之间分发任务。 这一章我们为车管所（DMV）开发一个访客登记和叫号系统，学习何时以及如何把 Postgres 当作消息队列。

本章目标

  • 判断什么时候适合用 Postgres 做消息队列
  • 基于普通表和 PL/pgSQL 函数实现一个自定义队列
  • 理解 FOR UPDATE SKIP LOCKED 如何让多个消费者并行取消息而不互相阻塞
  • 用 LISTEN/NOTIFY 通知消费者有新消息，并了解它的局限
  • 知道索引、分区、失败恢复等实现上的考量
  • 用 pgmq 扩展：发送、读取、可见性超时、归档

什么时候用 Postgres 做消息队列

任何消息队列至少要提供两项基本能力：一是能接收并保存生产者的消息，直到消费者需要（有的只存内存、速度快；有的持久化到磁盘，重启也不丢）；二是提供发布、读取、管理消息的 API。Postgres 这样支持它们：

  • 队列可以建在一张普通表上，每条消息一行。和其他表数据一样，Postgres 把消息持久化到磁盘以保证事务一致性和持久性，并按可用资源缓存在内存里。
  • 消息结构可以用丰富的数据类型定义：message_id、created_time 用 int8、timestamptz 这类严格类型，保证格式正确；真正的消息载荷用 json/jsonb，生产者可以发任意结构。
  • API 方面，最底层就是用 SQL 存取消息；往上可以封装成数据库函数（存储过程），或者某种语言的客户端库，底下依然是表和 SQL。
  • 数据库还有各种能力，保证消息量或生产者、消费者数量增长时，性能不会退化。

但 Postgres 毕竟不是专门的消息队列。用下面三条标准判断是否该用它：

  1. 需要用 Postgres 的事务把业务操作和它产生的消息原子地记录下来。 访客到车管所后在登记终端为某项业务（申请驾照、车辆注册等）签到，然后进入等候队列，轮到时被叫号。签到成功会产生一条“有新访客等待叫号”的消息。 如果你希望签到和入队在同一个事务里完成 —— 要么都成功，要么都失败 —— 就用 Postgres。 换成专用消息队列，应用就得自己保证：先在 Postgres 里签到，再把消息发到另一个队列；万一队列没记录下来，应用必须尽快处理，因为访客已经签到了、正等着被叫。
  2. 消息量 Postgres 轻松应付得了。 默认 Postgres 是单台服务器处理读写。如果它能在处理其他业务的同时消化应用产生和消费的消息量，就用它。 消费者太多、读请求压垮数据库时，可以加只读副本；生产者太多、写请求饱和时，要升级主机配置或迁移到分片/分布式 Postgres（如 CitusData 或 YugabyteDB）。 无论如何都要做基准和压力测试；如果优化工作量太大、配置太复杂，就考虑专用队列。 车管所的消息量很小，不用怎么优化；但如果是全球电商或社交网络这种规模，就要重新考虑了。
  3. 你已经在用 Postgres，不想再引入别的方案。 应用已经用 Postgres，现在要加个队列场景，先试 Postgres：合适的话架构不变，团队也不用学习、优化、维护一个新系统。 反过来，如果你没有（也不打算）把 Postgres 用于本书讲的其他场景，只想拿它当队列，就要慎重 —— 比如车管所的业务数据存在别的数据库里，那么只为队列引入 Postgres 未必是最优选择。

构建一个自定义消息队列

我们实现三个数据库函数：

函数作用
mq.enqueue(new_message JSON)把一条 JSON 消息加入队列
mq.dequeue(messages_cnt INT)从队头取出接下来的 messages_cnt 条消息。取出的消息对其他消费者不可见，但仍留在队列里，直到当前消费者调用 mark_completed
mq.mark_completed(message_ids BIGINT[], to_delete BOOLEAN DEFAULT FALSE)把指定 ID 的消息标记为已完成（处理成功）；to_delete 为 TRUE 时直接删除
ⓘ 用哪个容器

前几章的任何一个 Postgres 容器都可以：docker exec -it <container-name> psql -U postgres。

CREATE SCHEMA mq;

CREATE TYPE mq.status AS ENUM ('new', 'processing', 'completed');

CREATE TABLE mq.queue (
    id BIGSERIAL PRIMARY KEY,
    message JSON NOT NULL,
    created_at TIMESTAMPTZ DEFAULT NOW(),
    status mq.status NOT NULL DEFAULT 'new'
);
  • id：64 位自增整数，最多 2⁶³ 个 ID；用不了那么多可以用 32 位的 SERIAL。两者都依赖序列。如果大量生产者并发发消息，每个都要等序列生成下一个 ID，成为瓶颈时可以改用 UUID + gen_random_uuid()。
  • message：消息载荷。这里特意用 JSON 而不是 JSONB：队列只需要原样存下生产者的消息、稍后原样交给消费者。JSONB 会预处理（可能拖慢写入、还会重排键），它的好处在于在数据库里遍历、查询、修改 JSON（第 5 章），而队列只是“搬运”，不做转换。
  • created_at：入队时间，用来按先进先出（FIFO）顺序交给消费者。
  • status：消息状态。CREATE TYPE … AS ENUM 定义了一个只允许这三个值的枚举类型。

processing 状态在故障场景下也很有用：消费者取了消息、开始处理、然后挂了。应用可以定期检查在 processing 状态停留太久的消息，按自己定义的时间阈值把它们重置为 new。

入队函数

CREATE OR REPLACE FUNCTION mq.enqueue(new_message JSON)
RETURNS VOID AS $$
BEGIN
  INSERT INTO mq.queue (message)
  VALUES (new_message);
END;
$$ LANGUAGE plpgsql;

只插入消息本身，其他字段由 Postgres 自动填：id 取序列的下一个值，created_at 是当前时间，status 是 new。

出队函数

CREATE OR REPLACE FUNCTION mq.dequeue(messages_cnt INT)
RETURNS TABLE (msg_id BIGINT, message JSON, enqueued_at TIMESTAMPTZ) AS $$
BEGIN
  RETURN QUERY
  WITH new_messages AS (
     SELECT id FROM mq.queue
     WHERE status = 'new' ORDER BY created_at
     FOR UPDATE SKIP LOCKED
     LIMIT messages_cnt
  )
  UPDATE mq.queue q
  SET status = 'processing'
  FROM new_messages WHERE q.id = new_messages.id
  RETURNING q.id, q.message,
     date_trunc('seconds',q.created_at) AS created_at;
END;
$$ LANGUAGE plpgsql;
  1. 先算 CTE new_messages：找出状态为 new 的消息，按 created_at 升序（先来的在前），LIMIT 取最多 messages_cnt 条。
  2. UPDATE 把这些消息的状态改为 processing。
  3. RETURNING 返回被改的行，RETURN QUERY 把它们放进函数的结果集。created_at 用 date_trunc 截断到秒。（CTE 和 PL/pgSQL 复习见第 2、3 章。）

关键：FOR UPDATE SKIP LOCKED

FOR UPDATE 给 CTE 选出的每一条消息加上行级锁，保证只有当前这个消费者能处理它们。锁在执行 dequeue 的事务提交或回滚时才释放。 这个事务可以是显式的（dequeue 和其他业务逻辑放在同一个 BEGIN…COMMIT 里），也可以是调用函数时 Postgres 自动开启的隐式事务（函数结束即提交、释放锁）： 

BEGIN;
-- 执行一些业务逻辑
SELECT * FROM mq.dequeue(1);
-- 再执行一些业务逻辑
COMMIT;      -- 成功提交或失败回滚时，锁才释放

SKIP LOCKED 告诉 Postgres 跳过已经被其他事务锁住的行。多个消费者同时调用 dequeue 时，每个只拿到别人没在处理的消息，可以并行处理、互不阻塞，整体吞吐量更高。

SKIP LOCKED 和 FOR UPDATE、NOWAIT、lock_timeout 的对比，以及死锁和咨询锁，见专题 2。

标记完成函数

CREATE OR REPLACE FUNCTION mq.mark_completed(
  message_ids BIGINT[], to_delete BOOLEAN DEFAULT FALSE)
RETURNS VOID AS $$
BEGIN
  IF to_delete THEN
     DELETE FROM mq.queue
     WHERE id = ANY(message_ids);
  ELSE
     UPDATE mq.queue
     SET status = 'completed'
     WHERE id = ANY(message_ids);
  END IF;
END;
$$ LANGUAGE plpgsql;

消费者传入处理成功的消息 ID 数组。id = ANY(数组) 表示“id 等于数组中任意一个”。to_delete 为 TRUE 就删除，否则把状态改为 completed。

  "visitor": "Emily Carter"

★ 把入队放进更大的业务事务

enqueue 可以和其他业务操作放在同一个事务里，原子地执行 —— 这正是用 Postgres 做队列的第一条理由：

SELECT mq.enqueue('{
  "service": "car_registration",
  "visitor": "Emily Carter"
}'::json);
-- 再执行一些业务逻辑
COMMIT;

使用 LISTEN 和 NOTIFY

早高峰过后，车管所没那么忙了，等候区没人，办事员大多在忙别的事。但一有新访客签到，系统就会自动通知办事员。这可以用 Postgres 的 LISTEN 和 NOTIFY 实现： 

LISTEN channel_name              -- 把当前会话注册为该频道的监听者
NOTIFY channel_name, [payload]   -- 通知该频道的所有监听者；payload 可选，是一段文本

假设办事员登录电脑时，系统打开一个 Postgres 连接并监听 queue_new_message 频道。在你的 psql 里执行：

LISTEN queue_new_message;

然后修改 enqueue，每次有新访客入队就发一条通知：

CREATE OR REPLACE FUNCTION mq.enqueue(new_message JSON)
RETURNS VOID AS $$
BEGIN
  INSERT INTO mq.queue (message)
  VALUES (new_message);

  -- 通知监听者：有新消息了
  PERFORM pg_notify('queue_new_message', 'new_message');
END;
$$ LANGUAGE plpgsql;

pg_notify 函数和 NOTIFY 语句作用相同，但在函数和存储过程里更好用。PERFORM 是 PL/pgSQL 里“执行但丢弃结果”的写法。在同一个正在监听的 psql 连接里加一位访客试试：

SELECT mq.enqueue('{
  "service": "car_plate_renewal",
  "visitor": "Marta Jones"
}'::json);

Asynchronous notification "queue_new_message" with payload "new_message"
received from server process with PID 1699.

但现实中访客是从登记终端加入的，终端用的是另一个连接。用两个 psql 会话模拟：

  1. 保持第一个 psql（办事员的电脑）继续监听 queue_new_message。
  2. 在另一个终端窗口打开第二个 psql（登记终端）：docker exec -it postgres psql -U postgres，执行 enqueue 加入访客 Roland Deschain，函数会在频道上发通知。
  3. 回到第一个 psql —— 什么也没显示。执行任意一条 SQL，比如 SELECT 1;，通知随即打印出来。

实现上的考量

对车管所来说，这个自定义队列已经够用：写入速度取决于访客和终端数量，读取速度受办事员人数和空闲程度限制，都不高，只是早上高峰、傍晚清闲。但你的场景可能有更高的要求，下面几点值得注意。

LISTEN / NOTIFY 的两个局限

车管所正好可以这样做：终端和办事员的工作站都直连主节点，终端用这个连接签到并发通知，办事员用自己的连接接收通知；工作站上的其他查询通过连接池，把读请求路由到副本，减轻主节点负担。

索引

目前 mq.queue 只有主键索引：

SELECT indexname, indexdef
FROM pg_indexes
WHERE schemaname = 'mq' AND tablename = 'queue';
-- queue_pkey | CREATE UNIQUE INDEX queue_pkey ON mq.queue USING btree (id)

它能加速 mark_completed（按 ID 找行再更新或删除）。但 dequeue 每次都要全表扫描：created_at 上没有索引，取最早的消息得把表排序；status 上也没有索引，没法跳过非 new 的消息。 车管所每天下班队列就清空了，已完成的消息归档或删除，用不着更多索引。但写入和读取频率高得多时，可以考虑： 

-- 方案一：created_at 上的单列索引，取最早的消息不用排序
CREATE INDEX mq_created_at_index_btree
ON mq.queue (created_at);

-- 方案二：只包含 new 消息的部分索引，更小，还能跳过 processing/completed
CREATE INDEX mq_partial_index_btree
ON mq.queue (created_at, status)
WHERE status = 'new';

当然，如果你修改了队列的设计，也可以选别的、更贴合自己场景的索引策略。

分区

第 9 章用分区优化了时序负载。高吞吐的消息队列同样受益：写入速度很高时表会迅速膨胀，影响取消息和改状态的性能。 而且删掉的消息并不会立刻消失：被删除的行（死元组，dead tuple）仍留在表的物理结构里，直到被 Postgres 的 autovacuum 进程回收。为了跟上负载，可能得调整 vacuum 设置，让它更积极地清理（怎么调见专题 4）。

◆ UPDATE 也会产生死元组

把消息从 new 改成 processing 时同样会产生死元组：UPDATE 实际上是删掉旧版本、插入一个新版本（第 2 章的 MVCC）。旧版本留在表里，直到被 autovacuum 回收。 想看实际演示，可以看仓库 postgres_internals_videos.md 里的视频 “PostgreSQL Internals in Action: MVCC”。 队列这种“频繁插入、更新、删除”的表，是死元组的重灾区。

分区后消息分散在多个分区里，不用大量调优 vacuum 等设置也能支撑高吞吐。一种策略是按 created_at 做范围分区：

DROP TABLE mq.queue;

CREATE TABLE mq.queue (
    id BIGSERIAL,
    message JSON NOT NULL,
    created_at TIMESTAMPTZ DEFAULT NOW(),
    status mq.status NOT NULL DEFAULT 'new',
    PRIMARY KEY (id, created_at)      -- 分区表的主键必须包含分区键
) PARTITION BY RANGE (created_at);

CREATE TABLE mq.queue_2025_06_22 PARTITION OF mq.queue
FOR VALUES FROM ('2025-06-22 00:00:00') TO ('2025-06-23 00:00:00');

CREATE TABLE mq.queue_2025_06_23 PARTITION OF mq.queue
FOR VALUES FROM ('2025-06-23 00:00:00') TO ('2025-06-24 00:00:00');

CREATE TABLE mq.queue_default PARTITION OF mq.queue DEFAULT;

Postgres 会自动把 6 月 22 日的消息放进 queue_2025_06_22，23 日的放进 queue_2025_06_23，其他日期的进默认分区。三个队列函数照常操作父表 mq.queue，由数据库决定往哪个分区写、从哪个分区读。 假设今天是 6 月 23 日，所有新消息都在当天分区里透明地读写；像 queue_2025_06_22 这样存着过期消息的分区可以稍后删掉，减少资源占用。只保留一个或少数几个最新分区，Postgres 就能更高效地处理高吞吐的消息负载，而不用花大量时间调整数据库配置。

💡 自动化分区管理

可以组合使用 pg_partman（用后台进程自动创建和维护分区）和 pg_cron（按计划定时运行 pg_partman 的维护任务），自动创建新日期的分区、删除旧分区。分区策略也不止这一种：可以按 status 分区（new / processing / completed 各一个分区），也可以同时按时间和状态分区。

消息处理的失败恢复

车管所的场景里，办事员叫号后消息变成 processing；如果访客一分钟内没到窗口，消息就改回 new，把他放回队首；到了的话，消息一直保持 processing 直到办完、改成 completed。消息不会卡在 processing 状态。

但在别的场景，消费者取到消息、开始处理，然后可能挂掉。比如一个任务调度系统：生产者把任务入队，工作进程取出执行；工作进程中途崩溃，那些任务就永远停在 processing。 解决办法是引入超时机制：消息在 processing 状态最多停留一段时间，超时就重置为 new，让别的工作进程接手。可以用 pg_cron 在数据库里安排一个定期任务来做这件事： 

-- 示意：需要先安装 pg_cron 扩展，并给队列表加一个记录“开始处理时间”的列
SELECT cron.schedule('requeue-stuck', '* * * * *', $$
  UPDATE mq.queue SET status = 'new'
  WHERE status = 'processing'
    AND processing_started_at < now() - interval '5 minutes'
$$);

（这段是示意代码，书中只描述了思路。下一节的 pgmq 直接内置了这种机制：可见性超时。）

启动带 pgmq 的 Postgres

pgmq（Postgres Message Queue）扩展定位为一个轻量级消息队列，API 和 AWS SQS（Simple Queue Service）保持一致。 它把我们自己实现时操心的细节都封装好了，还支持队列分区、消息处理失败恢复等高级能力。

⚠ 先停掉之前的容器

用 docker ps --filter "name=postgres" --filter "publish=5432" 找到占用 5432 端口的容器，再 docker container stop <container-name>。

使用 pgmq

pgmq 提供了 40 多个函数，可以创建和管理队列、收发消息、按自定义保留策略归档等，都在 pgmq 模式下：

SELECT p.proname AS function_name,
  pg_catalog.pg_get_function_arguments(p.oid) AS arguments
FROM pg_catalog.pg_proc p
JOIN pg_catalog.pg_namespace n ON n.oid = p.pronamespace
WHERE n.nspname = 'pgmq';

    function_name   |                 arguments
--------------------+--------------------------------------------
 acquire_queue_lock | queue_name text
 format_table_name  | queue_name text, prefix text
 read               | queue_name text, vt integer, qty integer,
                    |   conditional jsonb DEFAULT '{}'::jsonb
 send               | queue_name text, msg jsonb,
                    |   delay timestamp with time zone
 send               | queue_name text, msg jsonb, headers jsonb,
                    |   delay integer

创建并使用访客队列

SELECT pgmq.create('visitors_queue');

每个队列背后都有一张自己的表，放在 pgmq 模式下，表名是 q_ 前缀加队列名：

\d pgmq.q_visitors_queue

                   Table "pgmq.q_visitors_queue"
   Column    |           Type           | Nullable |           Default
-------------+--------------------------+----------+------------------------------
 msg_id      | bigint                   | not null | generated always as identity
 read_ct     | integer                  | not null | 0
 enqueued_at | timestamp with time zone | not null | now()
 vt          | timestamp with time zone | not null |
 message     | jsonb                    |          |
 headers     | jsonb                    |          |
Indexes:
    "q_visitors_queue_pkey" PRIMARY KEY, btree (msg_id)
    "q_visitors_queue_vt_idx" btree (vt)

每条消息有唯一的 msg_id，载荷存在 jsonb 类型的 message 列。enqueued_at 是入队时间；vt 是可见性超时（visibility timeout）：如果消费者因故障等原因没在 vt 时间内处理完，之前取走的消息会重新出现在队列里。 headers 存可选的消息头，read_ct 记录消息被 pgmq.read 读过几次。扩展还默认建好了几个索引来加速访问。用 pgmq.send 把一位签到的访客加入等候队列： 

SELECT * FROM pgmq.send(
   queue_name => 'visitors_queue',
   msg =>'{"service": "car_registration", "visitor": "Olivia Morgan"}'
);

办事员准备接待下一位时，系统调用 pgmq.pop：取出下一条消息并立即删除：

SELECT msg_id, message, enqueued_at
FROM pgmq.pop('visitors_queue');

 msg_id |              message              |          enqueued_at
--------+-----------------------------------+-------------------------------
      1 | {"service": "car_registration",   | 2025-06-26 01:18:19.149045+00
        |  "visitor": "Olivia Morgan"}      |
(1 row)

在有新访客入队之前，再调用 pop 都会返回空结果。

可见性超时

除了 pop，pgmq 还提供 pgmq.read：取出消息但不立即删除：

pgmq.read(
  queue_name text, vt integer, qty integer,
  conditional jsonb DEFAULT '{}'::jsonb)
  • queue_name：队列名；qty：一次取几条；conditional（可选）：按 JSON 结构过滤消息。
  • vt：可见性超时（秒）。消息被一个消费者读取后，在这段时间内对其他消费者不可见。如果这个消费者没在超时之前删除或归档它，消息就重新可见，可以被别人处理。

可见性超时既能实现消费者故障时的失败恢复，也能实现特定的业务逻辑。比如：办事员叫号后，系统给访客两分钟时间走到窗口；两分钟没到，就自动把他放回等候列表，让办事员叫下一位。 Noah Bennett 来考驾照，终端把他加入队列： 

SELECT * FROM pgmq.send(
   queue_name => 'visitors_queue',
   msg => '{"service": "driving_license_exam", "visitor": "Noah Bennett"}'
);

过了一会儿，一位办事员空了，系统用两分钟（120 秒）的可见性超时取一位访客：

SELECT msg_id, message, enqueued_at
FROM pgmq.read(
   queue_name => 'visitors_queue',
   vt         => 120,
   qty        => 1
);

 msg_id |               message               |          enqueued_at
--------+-------------------------------------+-------------------------------
      2 | {"service": "driving_license_exam", | 2025-06-27 00:30:10.798186+00
        |  "visitor": "Noah Bennett"}         |
(1 row)

在接下来的两分钟里，Noah 的记录对其他办事员不可见 —— 期间再执行清单 11.10 会返回 0 行。

但 Noah 走到一边接电话，没在两分钟内到窗口。pgmq 让他的消息重新可见，相当于把他放回了等候列表。几分钟后他回来了，另一位办事员空了，系统再次执行清单 11.10，又叫到了 Noah。这次他准时到了窗口，办事员确认后，系统调用 pgmq.archive：

SELECT pgmq.archive(
   queue_name => 'visitors_queue',
   msg_id     => 2
);

SELECT msg_id, message FROM pgmq.a_visitors_queue;

 msg_id |                            message
--------+----------------------------------------------------------------
      2 | {"service": "driving_license_exam", "visitor": "Noah Bennett"}
(1 row)

archive 根据 msg_id 把消息从 q_visitors_queue 表移到 pgmq.a_visitors_queue —— pgmq 用来存放所有归档消息的表。之后再执行清单 11.10，就找不到 Noah 了。

ⓘ pgmq 与 LISTEN/NOTIFY

写书时 pgmq 还不支持 LISTEN/NOTIFY，计划在未来版本加入。详见 pgmq 仓库。

入队mq.enqueue(json)pgmq.send(queue, msg)（还支持延迟投递）
出队mq.dequeue(n)：改为 processingpgmq.read(queue, vt, qty) / pgmq.pop(queue)

小结

  • Postgres 可以作为消息队列，在生产者和消费者之间交换消息、事件和任务。判断标准：需要事务原子性、消息量撑得住、已经在用 Postgres。
  • 自定义队列可以建在普通表上，按自己的场景定制实现。
  • FOR UPDATE SKIP LOCKED 支持多个消费者并发取消息、互不阻塞。
  • LISTEN / NOTIFY（pg_notify）能在新消息入队时通知消费者，但不保存历史、只能在主节点订阅。
  • 实现时要考虑索引、分区（应对死元组和表膨胀）和消息处理的失败恢复。
  • pgmq 扩展提供开箱即用、API 与 AWS SQS 一致的消息队列，内置可见性超时和归档。

动手练习

  1. 开两个 psql 会话，都执行 BEGIN; SELECT * FROM mq.dequeue(1);（先不提交），确认两人拿到的是不同的消息。再把函数里的 SKIP LOCKED 去掉重做一次，观察第二个会话的表现。
    参考答案 
    -- 会话 A                                    -- 会话 B（随后执行）
BEGIN;                                       BEGIN;
SELECT msg_id, message FROM mq.dequeue(1);   SELECT msg_id, message FROM mq.dequeue(1);
--  1 | {"visitor" : 1}                      --  2 | {"visitor" : 2}      立刻返回，拿到下一条

    把函数里的 SKIP LOCKED 去掉（只留 FOR UPDATE）再做一次：

    会话 B：SELECT msg_id FROM mq.dequeue(1);
 msg_id
--------
      4
Time: 2005.405 ms     ← 一直卡住，直到会话 A 提交（实验里 A 3 秒后提交）

    没有 SKIP LOCKED 时，B 会排队等 A 释放行锁；A 提交后，那条消息已经不是 new 了，B 才继续找到下一条。消费者越多，排队越严重，多个消费者实际上变成了串行处理。

  2. 给 mq.queue 加一列 processing_started_at，修改 dequeue 在出队时写入当前时间，再写一条 SQL 把超过 1 分钟仍在 processing 的消息重置为 new。
    参考答案 
    ALTER TABLE mq.queue ADD COLUMN processing_started_at timestamptz;

CREATE OR REPLACE FUNCTION mq.dequeue(messages_cnt INT)
RETURNS TABLE (msg_id BIGINT, message JSON, enqueued_at TIMESTAMPTZ) AS $$
BEGIN
  RETURN QUERY
  WITH new_messages AS (
     SELECT id FROM mq.queue
     WHERE status = 'new' ORDER BY created_at
     FOR UPDATE SKIP LOCKED
     LIMIT messages_cnt
  )
  UPDATE mq.queue q
  SET status = 'processing',
      processing_started_at = now()          -- 新增：记下开始处理的时间
  FROM new_messages WHERE q.id = new_messages.id
  RETURNING q.id, q.message, date_trunc('seconds', q.created_at) AS created_at;
END;
$$ LANGUAGE plpgsql;

-- 处理超过 1 分钟还没完成的（消费者可能崩溃了），放回队列
UPDATE mq.queue
SET status = 'new', processing_started_at = NULL
WHERE status = 'processing'
  AND processing_started_at < now() - interval '1 minute'
RETURNING id;

    这条重置语句可以用 pg_cron 每分钟跑一次。这其实就是 pgmq 的“可见性超时”（vt）在做的事：超时没删除的消息会自动重新可见。

  3. 修改清单 11.5，让 pg_notify 的 payload 带上新消息的 id（提示：INSERT … RETURNING id INTO 变量）。
    参考答案 
    CREATE OR REPLACE FUNCTION mq.enqueue(new_message JSON)
RETURNS VOID AS $$
DECLARE
  new_id BIGINT;
BEGIN
  INSERT INTO mq.queue (message) VALUES (new_message)
  RETURNING id INTO new_id;

  PERFORM pg_notify('queue_new_message', new_id::text);   -- payload 只能是文本
END;
$$ LANGUAGE plpgsql;

LISTEN queue_new_message;
SELECT mq.enqueue('{"visitor": 99}');

    Asynchronous notification "queue_new_message" with payload "6" received from server process with PID 283.

    payload 最长约 8000 字节，所以一般只传 id，监听者收到后再按 id 查完整的消息。

  4. 用 pgmq.send 的 delay 参数发一条 30 秒后才可见的消息，验证在此之前 read 不到它。
    参考答案 
    SELECT pgmq.send(queue_name => 'visitors_queue', msg => '{"task": "later"}', delay => 30);

SELECT msg_id, read_ct, enqueued_at, vt FROM pgmq.q_visitors_queue;   -- vt = 入队时间 + 30 秒
SELECT * FROM pgmq.read('visitors_queue', 10, 1);   -- 30 秒内：(0 rows)
-- 等 30 秒后再读：
SELECT msg_id, read_ct, message FROM pgmq.read('visitors_queue', 10, 1);
--  msg_id | read_ct |      message
--       1 |       1 | {"task": "later"}

    delay 的原理就是把消息的 vt（可见时间）设到未来，read 只返回 vt 已过的消息。用它可以实现“30 分钟后提醒”这类延时任务。

  5. 反复 read 同一条消息（每次等 vt 过期），观察 read_ct 列的变化。想一想：怎样利用它实现“失败超过 3 次就移入死信队列”？
    参考答案 
    -- vt = 2 秒，每次等 vt 过期再读同一条消息
SELECT msg_id, read_ct FROM pgmq.read('visitors_queue', 2, 1);   -- read_ct = 2
SELECT msg_id, read_ct FROM pgmq.read('visitors_queue', 2, 1);   -- read_ct = 3
SELECT msg_id, read_ct FROM pgmq.read('visitors_queue', 2, 1);   -- read_ct = 4

    每被读一次 read_ct 加 1。消费者读到消息后先看 read_ct：超过 3 次说明它反复处理失败，就转进一个死信队列并从原队列删除（放在同一个事务里，保证不会丢也不会重复）：

    SELECT pgmq.create('visitors_queue_dlq');

BEGIN;
-- 假设刚读到的消息 msg_id = 1、read_ct = 5
SELECT pgmq.send('visitors_queue_dlq',
                 jsonb_build_object('original_id', 1, 'read_ct', 5, 'payload', '{"task": "later"}'::jsonb));
SELECT pgmq.delete('visitors_queue', 1);
COMMIT;

    之后可以单独查看、修复死信队列里的消息，而不会让一条“毒消息”一直卡住正常的处理。
