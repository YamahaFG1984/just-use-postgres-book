第 3 章

现代 SQL

SQL 诞生于 20 世纪 70 年代初，比第一台个人电脑 Altair 还早。但它和人类语言一样，一直在进化。 大多数人熟悉的仍是 1992 年的 SQL-92 标准，而在那之后，SQL 已经长出了很多让查询更短、更好读、更强大的新能力。 这一章我们以一个音乐流媒体服务为例，学习其中最实用的三样：CTE、递归查询和窗口函数。

本章目标

  • 知道“现代 SQL”指什么，为什么值得学
  • 用 WITH（CTE）把复杂查询拆成一步步可读的小块，包括修改数据的 CTE
  • 用 WITH RECURSIVE 遍历层级、链式数据
  • 用 OVER (PARTITION BY … ORDER BY …) 计算分组总计、累计值和排名

什么是现代 SQL

“现代 SQL”（modern SQL）这个说法是数据库专家 Markus Winand 提出的，他的网站 modern-sql.com 专门推广 SQL-92 之后加入标准的新能力。他这样描述：

❝ Markus Winand

从 1999 年起，SQL 就不再局限于关系模型了。那时 ISO/IEC 9075（“SQL 标准”）加入了数组、对象和递归查询。如今 SQL 标准的篇幅已经是 SQL-92 的五倍。换句话说：关系型 SQL 只占现代 SQL 的 20% 左右。

现代 SQL 带来的能力大致分两类：

  • 非结构化数据的类型：关系模型要求数据结构规整、拆成原子单元、互相关联（规范化）。但今天的 SQL 数据库支持数组、JSON、自定义复合类型，可以高效地存储和处理不那么规整的数据。
  • 应对现代工作负载的能力：SQL 一向以啰嗦著称，复杂查询尤甚。CTE 和窗口函数让复杂运算变得简洁可读；递归查询和属性图让层级、树形、图结构的处理变得简单。

既然这么好，为什么还没进入每个开发者的工具箱？至少有两个原因：

  • 知识的惯性：很多人多年前学会了 SQL-92，查询虽然啰嗦、低效，但任务也能完成，于是一直沿用老办法。
  • ORM 框架：有些开发者完全依赖 ORM 生成 SQL。但 ORM 是为通用场景设计的，它未必知道在你的场景里应该用高效的窗口函数，而不是笨重的自连接。

第 5、6 章还会继续学习现代 SQL 处理半结构化数据和文本的能力。

公用表表达式（CTE）

CTE（Common Table Expression，公用表表达式）能把又长又复杂的查询拆成一个个更小、更好管理的部分。 它用 WITH 子句定义： 

WITH cte_name AS (
    auxiliary_statement     -- 辅助语句
)
primary_statement           -- 主语句

WITH 定义了一个有名字的 CTE。辅助语句可以是普通的 SELECT，也可以是 INSERT/UPDATE/DELETE/MERGE； 它的执行结果可供后面的主语句使用。你可以把 CTE 想象成只在这条查询里存在的临时表或视图。

用 CTE 查询数据

需求：统计某段时间内最受欢迎的歌曲 —— 也就是被完整听完次数最多的歌。

WITH plays_cte AS (
    SELECT s.title, s.duration
    FROM streaming.plays p
    JOIN streaming.songs s ON p.song_id = s.id
    WHERE p.play_start_time::DATE BETWEEN '2024-09-15' AND '2024-09-16'
      AND p.play_duration = s.duration          -- 听完了
)
SELECT title, COUNT(*) AS play_count
FROM plays_cte
GROUP BY title
ORDER BY play_count DESC;

 title  | play_count
--------+------------
 Song D |          4
 Song A |          3
 Song G |          2
(3 rows)
ⓘ ::DATE 是什么

值::类型 是 Postgres 的类型转换简写，等价于标准写法 CAST(值 AS 类型)。这里把时间戳转成日期，丢掉时分秒，方便按日期比较。

◆ Postgres 会“折叠”CTE

根据查询的复杂度，Postgres 可能把 CTE 合并（fold）进主语句，或者把整个查询改写成更高效的形式。 比如清单 3.1 用 CTE 只是为了教学，其实写成一条 SELECT 也行 —— Postgres 能识别出来并自动优化。 可以用 EXPLAIN ANALYZE 看执行计划来验证（第 4 章详细讲 EXPLAIN）。

写得清楚的 CTE 也很好改。现在要找最不受欢迎的歌曲（推荐算法决定增删推荐时有用）：把条件改成“听了不到一半就切走”，再取最短的三首：

WITH plays_cte AS (
    SELECT s.title, s.duration, p.play_duration
    FROM streaming.plays p
    JOIN streaming.songs s ON p.song_id = s.id
    WHERE p.play_start_time::DATE BETWEEN '2024-09-15' AND '2024-09-16'
      AND p.play_duration < (s.duration / 2)    -- 没听到一半
)
SELECT title, MIN(play_duration) AS min_play_duration
FROM plays_cte
GROUP BY title
ORDER BY min_play_duration ASC LIMIT 3;

 title  | min_play_duration
--------+-------------------
 Song E |                32
 Song F |                78
 Song J |                91
(3 rows)

一个查询里用多个 CTE

一条查询可以定义多个 CTE，用逗号分隔，后面的 CTE 可以引用前面的。 上一个查询对刚发布的新歌有点不公平：也许只有一个人没听完。我们改成：至少有三个不同用户都没听完，才算“不受欢迎”。 

WITH plays_cte AS (
    SELECT s.title, s.duration, p.play_duration, p.user_id
    FROM streaming.plays p
    JOIN streaming.songs s ON p.song_id = s.id
    WHERE p.play_start_time::DATE BETWEEN '2024-09-15' AND '2024-09-16'
      AND p.play_duration < (s.duration / 2)
),
user_play_counts AS (
    SELECT title, duration, COUNT(DISTINCT user_id) AS user_count,
      MIN(play_duration) AS min_play_duration,
      COUNT(*) AS total_play_count
    FROM plays_cte
    GROUP BY title, duration
)
SELECT title, duration, min_play_duration, total_play_count
FROM user_play_counts
WHERE user_count >= 3
ORDER BY min_play_duration ASC
LIMIT 3;

 title  | duration | min_play_duration | total_play_count
--------+----------+-------------------+------------------
 Song E |      150 |                32 |                3
(1 row)

写成三步，执行就要三遍吗？

看起来 Postgres 要执行三个独立的 SELECT。改成子查询或者一条大 SELECT 会不会更快？答案是：看情况，要比较执行计划才知道。 但有一点可以肯定：Postgres 并不一定按你写的方式执行查询。SQL 只是描述“我想要什么结果”，具体怎么做由数据库决定。 在清单 3.3 前面加上 EXPLAIN (analyze, costs off, timing off) 再执行： 

                              QUERY PLAN
-------------------------------------------------------------------------
 Limit (actual rows=1 loops=1)
   -> Sort (actual rows=1 loops=1)
         Sort Key: user_play_counts.min_play_duration
         -> Subquery Scan on user_play_counts (actual rows=1 loops=1)
               -> GroupAggregate (actual rows=1 loops=1)
                     Group Key: s.title, s.duration
                     Filter: (count(DISTINCT p.user_id) >= 3)
                     Rows Removed by Filter: 5
                     -> Sort (actual rows=9 loops=1)
                           Sort Key: s.title, s.duration, p.user_id
                           -> Hash Join (actual rows=9 loops=1)
                                 Hash Cond: (s.id = p.song_id)
                                 Join Filter: (p.play_duration < (s.duration / 2))
                                 Rows Removed by Join Filter: 27
                                 -> Seq Scan on songs s (actual rows=10 loops=1)
                                 -> Hash (actual rows=36 loops=1)
                                       -> Seq Scan on plays p (actual rows=36 loops=1)
                                             Filter: (... BETWEEN 2024-09-15 AND 2024-09-16)

执行计划要从下往上、从里往外读：

  • Hash Join 阶段：连接 plays 和 songs，只保留满足条件的行。注意 plays_cte 根本没有单独出现 —— 它被折叠进了 user_play_counts。
  • GroupAggregate 阶段：没有二级索引，所以先排序、再分组，并应用“至少三位用户”的过滤。
  • Subquery Scan 阶段：遍历 user_play_counts 的结果，排序取前几名。

整个过程中 plays 和 songs 表都只扫描了一遍。所以选择子查询还是 CTE 时，选让你和团队读起来更清楚的那个。 多数情况下 Postgres 都能高效地把 CTE 折叠起来，你既得到可读性，又不损失性能。

ⓘ 物化（MATERIALIZED）

如果一个 CTE 被主语句或后续 CTE 引用了不止一次，Postgres 会把它物化：只计算一次，把结果存起来供多次引用。 你也可以强制物化：WITH cte_name AS MATERIALIZED (…)； 反过来，NOT MATERIALIZED 要求每次引用都重新计算。

用 CTE 修改数据

CTE 里也可以放 INSERT、UPDATE、DELETE、MERGE，把新增、修改或删除的记录交给主语句继续处理。 比如：用户正在听歌，服务更新播放时长，然后立刻判断这首歌的排名是否该上升： 

WITH updated_play AS (
    UPDATE streaming.plays
    SET play_duration = 200
    WHERE id = 30
    RETURNING song_id, play_duration       -- 把改后的值交给主语句
)
SELECT s.title, s.duration,
       CASE
            WHEN up.play_duration = s.duration THEN 'Moved Up the Rank'
            ELSE 'Rank Not Changed'
       END AS rank_change_status
FROM updated_play up
JOIN streaming.songs s ON s.id = up.song_id;

 title  | duration | rank_change_status
--------+----------+--------------------
 Song A |      200 | Moved Up the Rank
(1 row)
  • CTE 把第 30 次播放的时长改成 200 秒。如果正好是整首歌的时长，说明听完了，排名可能上升。
  • RETURNING 子句把 song_id 和更新后的 play_duration 返回给主语句（要返回所有列，写 RETURNING *）。
  • CASE WHEN … THEN … ELSE … END 是 SQL 里的“if-else”。
⚠ 修改数据的 CTE 两个特别之处
  • 即使主语句没引用它，它也会执行。而 SELECT 型的 CTE 只有被引用时才会计算。
  • 同一查询里的多个 CTE 是“同时”执行的，基于同一份数据快照 —— 一个 CTE 做的修改，其他 CTE 看不到。

验证第二点。先看第 12 次播放的现状：song_id 为 3，已经听了 118 秒。然后在一个 CTE 里改它，另一个 CTE 里读它：

WITH updated_play AS (
    UPDATE streaming.plays
    SET play_duration = 150
    WHERE id = 12
    RETURNING song_id, play_duration
),
current_play_duration AS (
    SELECT song_id, (play_duration = 150) as is_change_visible_to_cte
    FROM streaming.plays           -- 直接读表
    WHERE id = 12
)
SELECT is_change_visible_to_cte,
    (play_duration = 150) as is_change_visible_to_primary
FROM updated_play up
JOIN current_play_duration cp ON up.song_id = cp.song_id;

 is_change_visible_to_cte | is_change_visible_to_primary
--------------------------+------------------------------
 f                        | t
(1 row)

第二个 CTE 看不到修改（f = false），因为两个 CTE 在同一份快照上并发执行。 想让它看到，就让它直接读取 updated_play，而不是读表： 

WITH updated_play AS (
    UPDATE streaming.plays
    SET play_duration = 160
    WHERE id = 12
    RETURNING id, song_id, play_duration
),
current_play_duration AS (
    SELECT song_id, (play_duration = 160) as is_change_visible_to_cte
    FROM updated_play              -- 改成读 CTE 的结果
    WHERE id = 12
)
SELECT is_change_visible_to_cte,
    (play_duration = 160) as is_change_visible_to_primary
FROM updated_play up
JOIN current_play_duration cp ON up.song_id = cp.song_id;

 is_change_visible_to_cte | is_change_visible_to_primary
--------------------------+------------------------------
 t                        | t
(1 row)

递归查询

递归查询是一种特殊的 CTE，在定义时加上 RECURSIVE 关键字。一般形式如下：

WITH RECURSIVE cte_name (column1, column2, columnN)  -- 递归 CTE 定义（列清单可选）
AS (
    SELECT columns FROM table1                      -- 非递归项：只执行一次，提供“起点”
    WHERE condition

    UNION [ALL]

    SELECT columns FROM cte_name                    -- 递归项：引用自己，反复执行
    WHERE recursive_condition
)
SELECT columns FROM cte_name;                       -- 主语句
  • 非递归项只执行一次，把初始数据放进一个临时的工作表，这些数据也会加入最终结果。
  • 递归项以上一步的工作表为输入反复执行，只要还能产出新行（递归条件为真）就继续。
  • UNION 会去掉重复行，UNION ALL 保留所有行。

用伪代码表示执行过程（原书清单 3.7）：

// 第 1 步：执行非递归项（只执行一次）
non_recursive_result = execute(non_recursive_term);

// 第 2 步：如果用的是 UNION，去重；UNION ALL 则跳过
if (using UNION)
    non_recursive_result = remove_duplicates(non_recursive_result);

// 第 3 步：加入最终结果
final_result.add(non_recursive_result);

// 第 4 步：用它初始化工作表
working_table = non_recursive_result;

// 第 5 步：只要工作表不为空，就继续执行递归项
while (working_table is not empty) {
    // 第 6 步：以当前工作表为输入执行递归项
    intermediate_table = execute(recursive_term, using=working_table);

    // 第 7 步：UNION 时，去掉中间表内部、以及与最终结果重复的行
    if (using UNION)
        intermediate_table =
            remove_duplicates(intermediate_table, excluding=final_result);

    // 第 8 步：把这一轮的结果加入最终结果
    final_result.add(intermediate_table);

    // 第 9 步：用这一轮的结果替换工作表，进入下一轮
    working_table = intermediate_table;
}

// 第 10 步：返回最终结果
return final_result;

查询层级数据：连续播放的歌曲序列

如果用户一首接一首不间断地听歌，每次新播放的 played_after 列就记录上一次播放的 id； 序列里的第一首，played_after 是 NULL。这就构成了一条条链表，典型的层级结构。数据集里有 13 个序列： 

SELECT count(*) FROM streaming.plays WHERE played_after IS NULL;
-- 13

写一个递归查询，找出从第 5 次播放开始的整条播放序列：

WITH RECURSIVE play_sequence AS (
    -- 起点：id = 5 的这次播放
    SELECT id, user_id, song_id,
      play_start_time, play_duration, played_after
    FROM streaming.plays
    WHERE id = 5

    UNION ALL

    -- 每一轮：找“紧接在上一轮那次播放之后”的播放
    SELECT p.id, p.user_id, p.song_id, p.play_start_time,
       p.play_duration, p.played_after
    FROM streaming.plays p
    JOIN play_sequence ps ON p.played_after = ps.id
)
SELECT user_id, song_id, play_start_time,
  play_duration as duration, played_after
FROM play_sequence
ORDER BY play_start_time;

       1 |       6 | 2024-09-15 01:37:30 |      139 |            5
       1 |       7 | 2024-09-15 01:42:00 |      104 |            6
       1 |       8 | 2024-09-15 01:45:00 |       99 |            7

稍作修改，还能得到每首歌在序列里的层级：在非递归项里加一列 1 as level，在递归项里写 level + 1：

WITH RECURSIVE play_sequence AS (
    SELECT id, user_id, song_id, play_start_time,
    play_duration, played_after, 1 as level
    FROM streaming.plays
    WHERE id = 5

    UNION ALL

    SELECT p.id, p.user_id, p.song_id, p.play_start_time,
    p.play_duration, p.played_after, level + 1
    FROM streaming.plays p
    JOIN play_sequence ps ON p.played_after = ps.id
)
SELECT user_id, song_id, play_start_time,
  play_duration as duration, played_after, level
FROM play_sequence
ORDER BY play_start_time;

在递归中携带参数

递归 CTE 名字后面可以跟一个列清单：WITH RECURSIVE cte_name (col1, col2, …)。 这些列在每一轮之间传递，既可以是已有列的别名，也可以是在递归过程中生成、累加或更新的值。 比如计算一个序列的总播放时长： 

WITH RECURSIVE play_sequence(parent_id, sequence, total_duration) AS (
    SELECT id, ARRAY[id], play_duration
    FROM streaming.plays
    WHERE id = 5

    UNION ALL

    SELECT p.id, ps.sequence || p.id, total_duration + p.play_duration
    FROM streaming.plays p
    JOIN play_sequence ps ON p.played_after = ps.parent_id
)
SELECT p.song_id, p.play_start_time, p.play_duration,
  ps.sequence, ps.total_duration
FROM play_sequence ps
JOIN streaming.plays p ON ps.parent_id = p.id
ORDER BY ps.sequence, p.play_start_time;
  • 三个携带列：parent_id（当前播放 id）、sequence（走过的路径）、total_duration（累计时长），按定义顺序赋值。
  • 非递归项：sequence 初始化为 ARRAY[id]，total_duration 初始化为本次时长。
  • 递归项：ps.sequence || p.id 把当前 id 追加到数组末尾（|| 是数组/字符串拼接运算符），时长累加。
 song_id |   play_start_time   | play_duration | sequence  | total_duration
---------+---------------------+---------------+-----------+----------------
       5 | 2024-09-15 01:34:00 |            61 | {5}       |             61
       6 | 2024-09-15 01:37:30 |           139 | {5,6}     |            200
       7 | 2024-09-15 01:42:00 |           104 | {5,6,7}   |            304
       8 | 2024-09-15 01:45:00 |            99 | {5,6,7,8} |            403
(4 rows)

最后一行就是整个序列的总时长：403 秒。想一次拿到所有序列？把起点条件 WHERE id = 5 换成 WHERE played_after IS NULL（所有序列的第一首）即可：

WITH RECURSIVE play_sequence(parent_id, sequence, total_duration) AS (
    SELECT id, ARRAY[id], play_duration
    FROM streaming.plays
    WHERE played_after is NULL

    UNION ALL

    SELECT p.id, ps.sequence || p.id, total_duration + p.play_duration
    FROM streaming.plays p
    JOIN play_sequence ps ON p.played_after = ps.parent_id
)
SELECT p.song_id, p.play_start_time, p.play_duration,
  ps.sequence, ps.total_duration
FROM play_sequence ps
JOIN streaming.plays p ON ps.parent_id = p.id
ORDER BY ps.sequence, p.play_start_time;

💡 递归查询的常见用途

组织架构图（员工→上级）、商品分类树、评论的楼中楼回复、文件目录、社交网络里的“朋友的朋友”……凡是“一行指向另一行”的结构，都可以用递归查询遍历。

⚠ 当心死循环

如果数据里有环（A 指向 B，B 又指向 A），UNION ALL 的递归会永远停不下来。可以用 UNION 去重，或者像清单 3.9 那样记录路径数组，并在递归项里加 WHERE NOT p.id = ANY(ps.sequence) 防止重复访问。

窗口函数

窗口函数也是现代 SQL 最有效的能力之一。递归查询主要用在层级和树形结构上，而窗口函数的用途广泛得多： 排名排序、累计求和、移动平均、前后行对比（lag/lead 分析）等等。

窗口函数在一组彼此相关的行上做计算。它用 OVER 子句把数据分成若干子集（窗口），然后对每个窗口应用函数。最基本的形式： 

SELECT function_name(arguments)
OVER (PARTITION BY columnA)
FROM table;

函数可以是普通聚合函数（SUM()、AVG()…），也可以是专用窗口函数（RANK()、ROW_NUMBER()…）。 PARTITION BY columnA 把 columnA 值相同的行放进同一个窗口。

★ 和 GROUP BY 的根本区别

普通聚合配合 GROUP BY，每组只返回一行；窗口函数则保留每一行，只是在每行旁边附上该行所在窗口的计算结果。

从 GROUP BY 到窗口函数

先用普通聚合算每首歌的总播放时长：

SELECT song_id, SUM(play_duration) as total_duration
FROM streaming.plays
GROUP BY song_id ORDER BY total_duration DESC;

 song_id | total_duration
---------+----------------
       4 |           1200
       1 |            800
       7 |            798
       2 |            654
       3 |            467
       9 |            463
       6 |            451
       8 |            430
      10 |            389
       5 |            268
(10 rows)

新需求：除了每首歌的总时长，还要列出每一位听过这首歌的用户。 如果把 user_id 也加进 GROUP BY，SUM 就变成按“歌曲+用户”求和，不是我们要的： 

SELECT song_id, user_id, SUM(play_duration) as total_duration
FROM streaming.plays
GROUP BY (song_id, user_id) ORDER BY song_id;

 song_id | user_id | total_duration
---------+---------+----------------
       1 |       1 |            200
       1 |       2 |            200
       1 |       3 |            400
       2 |       3 |            304
       2 |       1 |            144
       2 |       2 |            206
(truncated output)

不用窗口函数的话，只能用自连接：先算出每首歌的总时长，再连回原表：

SELECT DISTINCT p.song_id,
       p.user_id,
       t.total_duration
FROM streaming.plays p
JOIN (
    SELECT song_id,
           SUM(play_duration) AS total_duration
    FROM streaming.plays
    GROUP BY song_id
) t ON p.song_id = t.song_id
ORDER BY p.song_id;

 song_id | user_id | total_duration
---------+---------+----------------
       1 |       1 |            800
       1 |       2 |            800
       1 |       3 |            800
       2 |       1 |            654
       2 |       2 |            654
       2 |       3 |            654
(truncated output)

结果对了，但每一行都被访问了两次，效率不高，逻辑也不好读。换成窗口函数：

WITH plays_with_total AS (
  SELECT
    song_id, user_id, SUM(play_duration)
    OVER (PARTITION BY song_id) AS total_duration
  FROM streaming.plays
)
SELECT DISTINCT song_id, user_id, total_duration
FROM plays_with_total
ORDER BY song_id, user_id;

CTE 里的窗口函数按 song_id 把每行放进对应的窗口，分别计算每个窗口的总时长； 主语句再用 SELECT DISTINCT 去掉同一用户多次播放产生的重复行。结果和自连接版本一样。

窗口帧与累计值

在 OVER 里再加 ORDER BY，窗口内的行会被排序并进一步划分成帧（frame）。 默认情况下，每一行的帧 = “从窗口第一行到当前行（以及和当前行排序值相同的行）”。这样就能算累计总和（running total）： 

SELECT song_id, user_id, play_duration, SUM(play_duration)
OVER (PARTITION BY song_id ORDER BY user_id) AS total_play_duration
FROM streaming.plays
WHERE song_id = 2;

 song_id | user_id | play_duration | total_play_duration
---------+---------+---------------+---------------------
       2 |       1 |           144 |                 144
       2 |       2 |           206 |                 350
       2 |       3 |           186 |                 654
       2 |       3 |           118 |                 654

第三位用户听了两次（186 秒和 118 秒），这两行 user_id 相同，属于同一帧，所以累计值都显示 654 —— 这正是这首歌所有用户的总时长。 由于 WHERE 已经只保留了 song_id = 2，这里的 PARTITION BY 其实可以省略，结果只会有一个窗口。

排名：RANK()

任何内置聚合函数（AVG()、MIN()、COUNT()…）都能当窗口函数用。 此外 Postgres 还提供了只能在窗口模式（带 OVER）下用的专用函数，比如排名、前后行比较。按总播放时长给歌曲排名： 

SELECT song_id, SUM(play_duration) AS total_play_duration,
RANK() OVER (ORDER BY SUM(play_duration) DESC) AS song_rank
FROM streaming.plays
GROUP BY song_id
ORDER BY song_rank;
  1. GROUP BY song_id：先分组，每首歌一行，算出总时长。
  2. RANK() OVER (ORDER BY SUM(play_duration) DESC)：分组后的数据送进窗口函数，按总时长降序排名。总时长相同的歌在同一帧，排名相同。
  3. ORDER BY song_rank：按名次输出，时长最长的排第 1。
 song_id | total_play_duration | song_rank
---------+---------------------+-----------
       4 |                1200 |         1
       1 |                 800 |         2
       7 |                 798 |         3
       2 |                 654 |         4
       3 |                 467 |         5
       9 |                 463 |         6
       6 |                 451 |         7
       8 |                 430 |         8
      10 |                 389 |         9
       5 |                 268 |        10
(10 rows)
ⓘ 窗口函数在 GROUP BY 之后执行

回忆第 1 章讲的执行顺序：FROM → WHERE → GROUP BY → HAVING → 窗口函数 → SELECT 输出 → ORDER BY → LIMIT。 这就是为什么 OVER 里可以写 SUM(play_duration) 这种聚合结果。 这里 OVER 没有 PARTITION BY，所以整个结果集是一个窗口。

常用的专用窗口函数速查：

函数作用并列时（如 100, 90, 90, 80）
ROW_NUMBER()按顺序编号1, 2, 3, 4（并列也不同号）
RANK()排名，并列同名次，后面跳号1, 2, 2, 4
DENSE_RANK()排名，并列同名次，不跳号1, 2, 2, 3
LAG(col) / LEAD(col)取前一行 / 后一行的值，做环比、间隔计算—
FIRST_VALUE(col) / LAST_VALUE(col)帧内第一个 / 最后一个值—
NTILE(n)把行均分成 n 个桶，返回桶号—

小结

  • SQL 虽然已经 50 多岁，但仍在进化。现代 SQL 指 SQL-92 之后加入的能力，让 Postgres 能超越经典关系模型。
  • CTE（WITH）把大查询拆成小块，可读性好，Postgres 通常能把它们优化得和子查询一样快；修改型 CTE 共享同一快照。
  • 递归查询（WITH RECURSIVE）用“起点 + 反复执行的递归项”处理层级和树形结构。
  • 窗口函数（OVER）把数据分成窗口，在保留每一行的前提下做聚合、累计、排名、前后行分析。
