VACUUM 与表膨胀

第 2 章讲过 MVCC：Postgres 更新一行时不覆盖旧数据，而是写一个新版本（图 2-7）。这让读写互不阻塞，代价是旧版本会留在表里，变成“死元组”。 负责清理它们的就是 VACUUM。理解它，才能看懂“为什么我的表越来越大”“为什么删了数据磁盘没变小”这类问题。

ⓘ 本页的例子都实际运行过

输出均在 Postgres 17.2 上实测。为了让现象可控，演示用的表都关掉了自动清理：WITH (autovacuum_enabled = false)。生产环境千万不要这样做。

本页目标

  • 亲眼看到 UPDATE 产生的死元组，以及表为什么会膨胀
  • 分清 VACUUM 和 VACUUM FULL：一个回收空间供复用，一个把文件缩小
  • 理解 autovacuum 何时触发，以及如何按表调整
  • 知道“长事务”为什么会让 VACUUM 失效
  • 用 HOT 更新和 fillfactor 减少膨胀，了解事务 ID 回卷

死元组从哪来

每一行都有隐藏的版本信息

每一行除了你定义的列，还有几个系统列。ctid 是行在文件里的物理位置（第几页，第几个槽），xmin 是创建这个版本的事务 ID，xmax 是删除（或更新掉）它的事务 ID：

CREATE DATABASE vactopic;
\c vactopic

CREATE TABLE items (id int PRIMARY KEY, qty int, note text)
  WITH (autovacuum_enabled = false);
INSERT INTO items VALUES (1, 10, 'a');

SELECT ctid, xmin, xmax, * FROM items;

 ctid  | xmin | xmax | id | qty | note
-------+------+------+----+-----+------
 (0,1) |  865 |    0 |  1 |  10 | a
(1 row)

UPDATE items SET qty = 11 WHERE id = 1;
SELECT ctid, xmin, xmax, * FROM items;

 ctid  | xmin | xmax | id | qty | note
-------+------+------+----+-----+------
 (0,2) |  866 |    0 |  1 |  11 | a
(1 row)

ctid 从 (0,1) 变成了 (0,2)：更新后的行住进了新的位置。那旧版本呢？用自带的 pageinspect 扩展直接看数据页的内容：

CREATE EXTENSION pageinspect;
SELECT lp, t_xmin, t_xmax, t_ctid FROM heap_page_items(get_raw_page('items', 0));

 lp | t_xmin | t_xmax | t_ctid
----+--------+--------+--------
  1 |    865 |    866 | (0,2)      ← 旧版本还在！被事务 866 “删除”，指向新版本
  2 |    866 |      0 | (0,2)      ← 新版本
(2 rows)

VACUUM items;
SELECT lp, lp_flags, t_xmin, t_xmax, t_ctid FROM heap_page_items(get_raw_page('items', 0));

 lp | lp_flags | t_xmin | t_xmax | t_ctid
----+----------+--------+--------+--------
  1 |        2 |        |        |            ← 内容被清掉了
  2 |        1 |    866 |      0 | (0,2)
(2 rows)

为什么不在 UPDATE 时直接删掉旧版本？因为此时可能还有别的事务正在读它（比如一个可重复读事务，见专题 2）。只有当所有可能看到它的事务都结束了，旧版本才成为真正的“死元组”，才可以被清理。

表膨胀

放大到 10 万行，看看把每一行都更新一遍会发生什么：

TRUNCATE items;
INSERT INTO items SELECT g, 0, repeat('x', 100) FROM generate_series(1, 100000) g;

SELECT pg_size_pretty(pg_relation_size('items')) AS size, n_dead_tup
FROM pg_stat_user_tables WHERE relname = 'items';
--  size  | n_dead_tup
--  13 MB |          0

UPDATE items SET qty = qty + 1;     -- 每行都改一下

SELECT pg_size_pretty(pg_relation_size('items')) AS size, n_dead_tup
FROM pg_stat_user_tables WHERE relname = 'items';
--  size  | n_dead_tup
--  27 MB |     100000         表翻倍了，里面一半是死元组

数据量没变，表却从 13 MB 涨到 27 MB。这就是表膨胀（bloat）。死元组不仅占磁盘，还拖慢查询： 顺序扫描要多读一倍的页，索引里也留着指向死元组的条目。

VACUUM 与 VACUUM FULL

VACUUM (VERBOSE) items;

INFO:  finished vacuuming "vactopic.public.items": index scans: 1
pages: 0 removed, 3449 remain, 3449 scanned (100.00% of total)
tuples: 100000 removed, 100000 remain, 0 are dead but not yet removable
…
index "items_pkey": pages: 551 in total, 0 newly deleted, 0 currently deleted, 0 reusable

SELECT pg_size_pretty(pg_relation_size('items')) AS size, n_dead_tup
FROM pg_stat_user_tables WHERE relname = 'items';
--  size  | n_dead_tup
--  27 MB |          0         死元组没了，但文件还是 27 MB

普通 VACUUM 不会把文件变小。它把死元组的空间记进“空闲空间映射”（Free Space Map），之后的写入优先用这些空位。再更新一遍全表试试：

UPDATE items SET qty = qty + 1;
SELECT pg_size_pretty(pg_relation_size('items'));   -- 27 MB   没再长：新版本填进了上次回收的空间

用 pgstattuple 扩展（同样随 Postgres 自带）可以精确看到表里有多少死元组和空闲空间：

CREATE EXTENSION pgstattuple;

-- 刚 UPDATE 完全表
SELECT tuple_count, dead_tuple_count, round(dead_tuple_percent) AS dead_pct,
       round(free_percent) AS free_pct
FROM pgstattuple('items');
--  tuple_count | dead_tuple_count | dead_pct | free_pct
--       100000 |           100000 |       47 |        1

VACUUM items;
-- 再查一次
--       100000 |                0 |        0 |       50     死元组变成了空闲空间

真要把文件缩小，就要 VACUUM FULL，它把活元组复制到一个全新的文件里：

VACUUM FULL items;
SELECT pg_size_pretty(pg_relation_size('items'));   -- 13 MB
VACUUMVACUUM FULL
做什么标记死元组空间为可复用，更新统计信息和可见性映射把整张表重写到一个新文件，旧文件删除
文件变小吗基本不会（只能截掉表末尾完全空的页）会
锁不阻塞读写，可以随时跑ACCESS EXCLUSIVE 锁：期间表完全不能读写
额外磁盘不需要需要再放得下一份表和索引
什么时候用日常，通常交给 autovacuum一次性删除了大量数据、确实需要还空间，且能接受停机
⚠ 不要把 VACUUM FULL 当日常维护

一张稳定在 27 MB、内部一半空闲的表，其实是健康的：空闲空间会被持续复用。把它 VACUUM FULL 到 13 MB，下一次全表更新它还会长回 27 MB，白白锁表一次。 需要在线缩小大表时，社区常用第三方扩展 pg_repack，它只在最后切换时短暂加锁，但不随 Postgres 自带，需要另外安装。

autovacuum：自动清理

没人会手动给每张表跑 VACUUM。Postgres 有一个后台进程 autovacuum launcher，定期检查每张表，死元组多到一定程度就派一个 worker 去清理：

SELECT name, setting FROM pg_settings WHERE name LIKE 'autovacuum%' ORDER BY name;

                name                |  setting
------------------------------------+-----------
 autovacuum                         | on          总开关
 autovacuum_analyze_scale_factor    | 0.1
 autovacuum_analyze_threshold       | 50
 autovacuum_freeze_max_age          | 200000000
 autovacuum_max_workers             | 3           最多同时 3 个 worker
 autovacuum_naptime                 | 60          每个数据库每 60 秒检查一轮
 autovacuum_vacuum_insert_threshold | 1000
 autovacuum_vacuum_scale_factor     | 0.2
 autovacuum_vacuum_threshold        | 50
…

ALTER TABLE items SET (autovacuum_vacuum_scale_factor = 0.01, autovacuum_enabled = true);
-- 现在 10 万行的表，只要 50 + 1000 = 1050 个死元组就会触发

UPDATE items SET qty = qty + 1 WHERE id <= 5000;

SELECT relname, n_dead_tup, last_autovacuum, autovacuum_count
FROM pg_stat_user_tables WHERE relname = 'items';

 relname | n_dead_tup |        last_autovacuum        | autovacuum_count
---------+------------+-------------------------------+------------------
 items   |          0 | 2026-10-19 15:58:35.804374+00 |                1
(1 row)

autovacuum 在后台自己完成了清理。同一个 worker 还会顺带做 ANALYZE（更新第 4 章讲的统计信息，last_autoanalyze 列），触发规则类似：50 + 10% 的行数发生变化。

💡 只插入不更新的表也需要 VACUUM

日志、时序这类只追加的表没有死元组，但 VACUUM 还负责更新可见性映射（让第 4 章的 Index Only Scan 不用回表）和冻结旧行（见下文）。所以 Postgres 13 起增加了 autovacuum_vacuum_insert_threshold：插入了足够多的行也会触发清理。

长事务：VACUUM 的头号敌人

前面说过，只要还有事务可能看到旧版本，它就不能被清理。一个忘了提交的事务，会让整个数据库的 VACUUM 都无法清理它开始之后产生的死元组。用两个会话实测：

-- 会话 A：开了个事务，读了点东西，然后……一直没提交
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT count(*) FROM items;

-- 会话 B：更新全表，然后 VACUUM
UPDATE items SET qty = qty + 1;
VACUUM (VERBOSE) items;

tuples: 0 removed, 200000 remain, 100000 are dead but not yet removable
removable cutoff: 874, which was 1 XIDs old when operation ended

“100000 are dead but not yet removable”：10 万个死元组，一个也删不掉，因为会话 A 的快照还可能需要它们。 会话 A 提交之后再 VACUUM，就 100000 removed 了。

谁在“拖后腿”？查看 pg_stat_activity 里持有旧快照（backend_xmin 不为空）、事务开始时间最早的连接：

SELECT pid, usename, state, now() - xact_start AS xact_age, backend_xmin, left(query, 40) AS query
FROM pg_stat_activity
WHERE backend_xmin IS NOT NULL AND pid <> pg_backend_pid()
ORDER BY xact_start;

 pid | usename | state  |    xact_age     | backend_xmin | query
-----+---------+--------+-----------------+--------------+------------------------------
 420 | postgres| active | 00:00:01.352946 |          874 | …

常见的罪魁祸首和对策：

  • 应用开了事务却没提交（异常分支漏了 rollback），连接显示为 idle in transaction。设置 idle_in_transaction_session_timeout（默认 0，即不限制），比如 '10min'，超时自动断开。
  • 跑了几个小时的分析查询：放到只读副本上执行，或者拆小。
  • 被遗忘的复制槽（逻辑复制、Debezium 这类变更数据捕获工具会创建它们）：查 pg_replication_slots，删掉不用的。
  • 必要时用 SELECT pg_terminate_backend(pid); 结束那个连接。

HOT 更新与 fillfactor

一次普通的 UPDATE，除了写新版本，还要在每一个索引里插入一条指向新版本的条目。表上索引越多，代价越大，索引膨胀也越快。 如果满足两个条件，Postgres 会走一条捷径，叫 HOT（Heap-Only Tuple）更新：

  1. 更新的列都没有被任何索引用到；
  2. 新版本能放进同一个数据页（页里还有空位）。

第二个条件就是 fillfactor 的用武之地。表默认 fillfactor = 100，插入时把每页填满，更新时页里没有空位，新版本只能去别的页。 设成 90，插入时每页留 10% 的空位给将来的更新。对比两张一模一样的表，各更新 10% 的行（只改没有索引的 note 列）： 

CREATE TABLE ff100 (id int PRIMARY KEY, qty int, note text) WITH (autovacuum_enabled = false);
CREATE TABLE ff90  (id int PRIMARY KEY, qty int, note text) WITH (autovacuum_enabled = false, fillfactor = 90);
INSERT INTO ff100 SELECT g, 0, repeat('x', 100) FROM generate_series(1, 100000) g;
INSERT INTO ff90  SELECT g, 0, repeat('x', 100) FROM generate_series(1, 100000) g;

UPDATE ff100 SET note = 'y' || note WHERE id % 10 = 0;
UPDATE ff90  SET note = 'y' || note WHERE id % 10 = 0;

SELECT relname, n_tup_upd, n_tup_hot_upd FROM pg_stat_user_tables
WHERE relname LIKE 'ff%' ORDER BY 1;

 relname | n_tup_upd | n_tup_hot_upd
---------+-----------+---------------
 ff100   |     10000 |             0     页都满了，一次 HOT 都没有
 ff90    |     10000 |         10000     全部是 HOT 更新
(2 rows)

再给 qty 加个索引，然后更新 qty。被更新的列有索引，第一个条件不满足，fillfactor 再低也没用：

CREATE INDEX ON ff90 (qty);
SELECT pg_stat_reset_single_table_counters('ff90'::regclass);   -- 计数清零
UPDATE ff90 SET qty = 1 WHERE id % 10 = 5;
-- n_tup_upd = 10000, n_tup_hot_upd = 0
★ 经验法则
  • 频繁更新的表（计数器、状态、库存），考虑 fillfactor = 80 ~ 90。只插入不更新的表保持 100。
  • 别给经常被更新的列随手建索引：多一个索引，不只是多一份写入，还可能让所有更新都失去 HOT。
  • 用 n_tup_hot_upd * 100.0 / n_tup_upd 观察每张表的 HOT 比例。
  • 改了 fillfactor 只影响之后写入的页；要让已有数据也留出空位，需要 VACUUM FULL 或重建表。

事务 ID 回卷

xmin、xmax 里的事务 ID 是 32 位的，大约 42 亿个，用完会绕回去重新开始。Postgres 判断“这行是不是过去写的”靠比较事务 ID 的先后， 一个很老的 ID 绕一圈后，可能突然被当成“未来”的，那一行就凭空消失了。

解决办法是冻结（freeze）：VACUUM 会把足够老的行标记为“已冻结”，意思是“对所有事务永远可见”，之后它的事务 ID 就不再参与比较。 当一张表最老的未冻结 ID 的“年龄”超过 autovacuum_freeze_max_age（默认 2 亿），即使表上关了 autovacuum，Postgres 也会强制对它做一次防回卷的 VACUUM。 

-- 每个数据库、每张表距离回卷还有多远（年龄越大越危险）
SELECT datname, age(datfrozenxid) FROM pg_database ORDER BY 2 DESC;
SELECT relname, age(relfrozenxid) FROM pg_class
WHERE relkind = 'r' ORDER BY 2 DESC LIMIT 10;
⚠ 年龄接近 20 亿就要立即处理

如果冻结一直跟不上（通常是因为长事务、被遗忘的复制槽，或者 autovacuum 被关掉），年龄会逼近约 21 亿的上限。 到那一步，Postgres 为了保护数据会拒绝分配新的事务 ID，也就是拒绝一切写入，直到完成 VACUUM。 在监控里给 age(datfrozenxid) 设一个告警（比如超过 5 亿），比事后补救容易得多。

日常监控清单

-- 1. 死元组最多的表，以及它们上次被清理的时间
SELECT relname, n_live_tup, n_dead_tup,
       round(100.0 * n_dead_tup / nullif(n_live_tup + n_dead_tup, 0), 1) AS dead_pct,
       last_vacuum, last_autovacuum, autovacuum_count
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC LIMIT 10;

-- 2. 正在运行的 VACUUM 进度
SELECT pid, relid::regclass, phase, heap_blks_scanned, heap_blks_total
FROM pg_stat_progress_vacuum;

-- 3. 最老的事务（挡住清理的元凶）
SELECT pid, state, now() - xact_start AS age, left(query, 50)
FROM pg_stat_activity WHERE xact_start IS NOT NULL ORDER BY xact_start LIMIT 5;

-- 4. HOT 比例低、更新又多的表：考虑 fillfactor 或删掉多余索引
SELECT relname, n_tup_upd, round(100.0 * n_tup_hot_upd / nullif(n_tup_upd, 0), 1) AS hot_pct
FROM pg_stat_user_tables WHERE n_tup_upd > 1000 ORDER BY hot_pct;

小结

  • UPDATE 和 DELETE 都会留下旧版本；没有事务再需要它时就成了死元组，只有 VACUUM 能回收。
  • 普通 VACUUM 不锁表，把空间留给后续写入复用，文件通常不变小；VACUUM FULL 重写整张表、缩小文件，但全程锁表。
  • autovacuum 在死元组超过 50 + 20% × 行数 时触发；大表应按表调低 autovacuum_vacuum_scale_factor。
  • 长事务（尤其是 idle in transaction）会阻止清理，用 pg_stat_activity 找出来，用 idle_in_transaction_session_timeout 预防。
  • HOT 更新要求被改的列没有索引、且页内有空位；频繁更新的表可以设 fillfactor 80 ~ 90。
  • VACUUM 还负责冻结旧行、防止事务 ID 回卷，监控 age(datfrozenxid)。

    CREATE TABLE half (id int PRIMARY KEY, note text) WITH (autovacuum_enabled = false);

SELECT pg_size_pretty(pg_relation_size('half')) AS size,

FROM pgstattuple('half');

                     size    | tuple_count | dead_tuple_count | dead_pct | free_pct
DELETE 之后     13 MB    |       50000 |            50000 |       46 |        1
VACUUM 之后     13 MB    |       50000 |                0 |        0 |       49
VACUUM FULL 后  6904 kB  |       50000 |                0 |        0 |        1

    DELETE 和 UPDATE 一样只是把行标记为过期；VACUUM 把这一半空间变成可复用的空闲空间，文件不变；VACUUM FULL 重写整张表，文件才缩小到一半左右。

  2. 用 pageinspect 观察同一行连续更新 3 次后，数据页里有几个版本、t_ctid 是怎么串起来的。
    参考答案 
    CREATE TABLE chain (id int PRIMARY KEY, v int) WITH (autovacuum_enabled = false);
INSERT INTO chain VALUES (1, 0);
UPDATE chain SET v = 1;  UPDATE chain SET v = 2;  UPDATE chain SET v = 3;

SELECT lp, t_xmin, t_xmax, t_ctid,
       (t_infomask2 & 16384) > 0 AS hot_updated,     -- 这个版本被 HOT 更新过
       (t_infomask2 & 32768) > 0 AS heap_only        -- 这个版本是 HOT 产生的（索引里没有它）
FROM heap_page_items(get_raw_page('chain', 0));

     lp | t_xmin | t_xmax | t_ctid | hot_updated | heap_only
----+--------+--------+--------+-------------+-----------
  1 |   3761 |   3762 | (0,2)  | t           | f
  2 |   3762 |   3763 | (0,3)  | t           | t
  3 |   3763 |   3764 | (0,4)  | t           | t
  4 |   3764 |      0 | (0,4)  | f           | t
(4 rows)

    4 个版本都在第 0 页上，每个旧版本的 t_ctid 指向下一个版本，形成 (0,1) → (0,2) → (0,3) → (0,4) 的链；最新版本的 t_ctid 指向自己、xmax 为 0。更新的 v 列没有索引，所以都是 HOT 更新：主键索引里始终只有指向 (0,1) 的那一条，查询时顺着链找到最新版本。

  3. 复现“长事务挡住 VACUUM”：会话 A 开事务不提交，会话 B 更新并 VACUUM VERBOSE，然后在会话 B 里用 pg_terminate_backend 结束会话 A。
    参考答案 
    -- 会话 A
SET application_name = 'session_a';
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT count(*) FROM items;
-- ……不提交

-- 会话 B
UPDATE items SET qty = qty + 1 WHERE id <= 1000;
VACUUM (VERBOSE) items;
--  tuples: 0 removed, 101000 remain, 1000 are dead but not yet removable
SELECT pg_terminate_backend(pid) FROM pg_stat_activity WHERE application_name = 'session_a';
--  t
VACUUM (VERBOSE) items;
--  tuples: 1000 removed, 100000 remain, 0 are dead but not yet removable

    会话 A 这边：FATAL:  terminating connection due to administrator command

    结束长事务之后，被它“护着”的死元组立刻就能清理了。给连接设置 application_name，排查时一眼就能认出是谁。

  4. 把 idle_in_transaction_session_timeout 设为 '5s'，开一个事务后等 6 秒再执行查询，观察报错。
    参考答案 
    SET idle_in_transaction_session_timeout = '5s';
BEGIN;
SELECT 1;
-- 什么都不做，等 6 秒（psql 里可以用 \! sleep 6）

    超时后服务器直接断开连接，事务自动回滚。注意计时的是“在事务里空闲”的时间，长时间执行中的查询不受它限制（那是 statement_timeout 的事）。

  5. 对第 2 章的 products.catalog 表，查一下 n_tup_hot_upd。哪些索引会让更新库存数量失去 HOT？
    参考答案 
    \c coffee_chain
SELECT pg_stat_reset_single_table_counters('products.catalog'::regclass);
UPDATE products.catalog SET stock_quantity = stock_quantity - 1 WHERE id = 1;   -- 再对 id 3、4 各做一次
SELECT n_tup_upd, n_tup_hot_upd FROM pg_stat_user_tables WHERE relid = 'products.catalog'::regclass;
--  3 | 3        全部是 HOT：表上只有主键索引，stock_quantity 没有索引

CREATE INDEX catalog_stock_idx ON products.catalog (stock_quantity);
-- 重置计数后：两次改库存 + 一次改价格
--  3 | 1        改库存不再是 HOT，只有改价格那次还是

    任何包含 stock_quantity 的索引（单列、复合、表达式、部分索引的 WHERE 条件里用到它都算）都会让改库存失去 HOT。像库存这种频繁更新的列，建索引前要掂量一下：多一个索引，每次更新都要多写一份索引、表也更容易膨胀。
