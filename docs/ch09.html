第 9 章

时间序列

时间序列是随时间采集的一串数据点，每个点代表系统或对象在某一时刻的状态。通过采集一段时间的数据，我们能看出系统如何演变，从而发现趋势、提前行动、预测未来。 查看服务器上周的 CPU 和内存用量、研究过去三个月的汇率波动、分析病人过去一年的生命体征，都是在和时间序列打交道。 这一章我们开发一个智能手表应用：记录用户心率，在 Postgres 里高效存储和分析，及时提醒用户重要的健康变化。

本章目标

  • 理解时间序列数据的两个特点，以及为什么要分区
  • 会用 Postgres 原生的范围分区
  • 用 TimescaleDB 的超表（hypertable）自动管理分区（chunk），设置数据保留策略
  • 用 time_bucket、time_bucket_gapfill、LOCF、interpolate 分析数据
  • 用连续聚合预计算结果并自动刷新
  • 比较 B-tree 和 BRIN 索引在时序数据上的大小与性能

Postgres 如何处理时间序列数据

没接触过时序数据？只需要知道它有两个鲜明特点：

⏱

每个点都带时间

每条记录都包含测量或事件发生的时间。

➕

只追加，不修改

测量结果一旦记录就不再更新（append-only）。

智能手表持续监测心率，每分钟把数据发给后端（断网时则在恢复后批量补发）。后端把每条记录存进这张表：

CREATE TABLE heart_rate_measurements (
   watch_id INT NOT NULL,              -- 设备 ID
   recorded_at TIMESTAMPTZ NOT NULL,   -- 测量时间
   heart_rate INT NOT NULL,            -- 心率（次/分钟，BPM）
   activity TEXT NOT NULL CHECK (      -- 当时在做什么
       activity IN ('walking', 'sleeping', 'resting', 'workout'))
);
ⓘ 为什么用 TIMESTAMPTZ

TIMESTAMPTZ（带时区的时间戳）把时间点存成“自 2000 年 1 月 1 日 UTC 起的微秒数”。写入时 Postgres 自动转换成 UTC 存储； 读取时再根据数据库服务器、当前连接或用户的时区转换回来。处理跨时区的用户时非常省心（后面会看到东京用户的例子）。

这么简单的表结构正符合时序应用的最佳实践：每条测量只存必要的最少信息。因为时序数据只增不减，表会飞快地膨胀，结构越复杂膨胀越快，存储和处理成本越高。 每分钟一条，一个用户每天就是 1440 条；1000 个用户就是每天 144 万条。（有些系统按秒甚至毫秒采集，每天轻松达到数十亿条。）

表分区

把所有测量放在一张巨大的表里并不现实：用户大多数时候只关心最新的数据（今天或最近几天），每周、每月的趋势只是偶尔看看。 所以近期数据和历史数据应该分开存放：针对近期数据的查询不受总量增长的影响，历史数据也随时能访问、压缩或淘汰。

Postgres 的表分区（partitioning）能把一张大的逻辑表拆成多张更小的物理表，叫分区。 其中范围分区按某列（或几列）的值划分成互不重叠的范围： 

CREATE TABLE heart_rate_measurements (
  watch_id INT NOT NULL,
  recorded_at TIMESTAMPTZ NOT NULL,
  heart_rate INT NOT NULL,
  activity TEXT NOT NULL CHECK (
      activity IN ('walking', 'sleeping', 'resting', 'workout'))
) PARTITION BY RANGE (recorded_at);     -- 按 recorded_at 的范围分区

CREATE TABLE measurements_jan2025
    PARTITION OF heart_rate_measurements
    FOR VALUES FROM ('2025-01-01') TO ('2025-02-01');

CREATE TABLE measurements_feb2025
    PARTITION OF heart_rate_measurements
    FOR VALUES FROM ('2025-02-01') TO ('2025-03-01');
  • 分区就是普通的 Postgres 表，用特殊形式的 CREATE TABLE 创建：PARTITION OF 指定所属的父表，FOR VALUES 指定存储的值范围。
  • 范围包含下界、不包含上界：FROM ('2025-01-01') TO ('2025-02-01') 存的是从 2025-01-01 00:00:00（含）到 2025-02-01 00:00:00（不含）。

应用只管查父表，由 Postgres 决定访问哪些分区。查 1 月 1 日到 3 日：

EXPLAIN
SELECT * FROM heart_rate_measurements
WHERE recorded_at BETWEEN '2025-01-01' AND '2025-01-03';

 Seq Scan on measurements_jan2025 heart_rate_measurements
   (cost=0.00..26.05 rows=5 width=48)
   Filter: ((recorded_at >= '2025-01-01 00:00:00+00'::timestamp with time zone) AND
            (recorded_at <= '2025-01-03 00:00:00+00'::timestamp with time zone))

只扫描了 1 月的分区。查 1 月 30 日到 2 月 2 日呢？

 Append (cost=0.00..52.15 rows=10 width=48)
   -> Seq Scan on measurements_jan2025 heart_rate_measurements_1 ...
   -> Seq Scan on measurements_feb2025 heart_rate_measurements_2 ...

表分区是 Postgres 支撑时序负载的关键能力：既解决了“所有数据挤在一张大表”的问题，又能让查询只访问匹配的分区，显著提升性能。 （深入了解见官方文档。）

分区对应用是透明的，但总得有人管理分区：提前创建未来的分区，决定何时淘汰、清空或压缩历史分区。 可以组合使用 pg_partman（用后台进程自动创建和维护分区）和 pg_cron（在数据库里按 cron 计划定时执行 pg_partman 的维护任务）。 但本书选一个更简单的方案：专为时序场景打造、同样能自动管理分区的 TimescaleDB 扩展。

启动带 TimescaleDB 的 Postgres

TimescaleDB 超表

导入数据的脚本 schema.sql 里有这样一条语句：

SELECT create_hypertable(
   relation => 'watch.heart_rate_measurements',
   dimension => by_range('recorded_at', interval '1 month'),
   create_default_indexes => false
);

它把表变成了 TimescaleDB 的超表（hypertable）：一张会自动创建和管理分区的普通 Postgres 表。

  1. relation：要变成超表的表。
  2. dimension：分区方式。这里按 recorded_at 做范围分区，每个范围一个月。
  3. create_default_indexes：是否创建默认索引。这里关掉，后面专门讲时序数据的索引。
⚠ 分区粒度要随数据量调整

按月分区只是为了简单 —— 我们只有三台设备。当数据来自成千上万甚至上百万台设备时，每个月的分区会非常大，危及数据库和应用的性能，需要按天、按小时，甚至按设备来分区。

用 \d+ watch.heart_rate_measurements 查看，Child tables 部分列出了所有分区：

   Filter: (recorded_at >= '2025-12-08 00:00:00+00'::timestamp with time zone)
 Planning Time: 0.208 ms
 Execution Time: 0.026 ms

不管数据量多大，数据库都自动把新数据分配到各个分区，查询时只访问满足条件的子集，性能可预测。

★ 数据保留策略：自动删除旧数据

只想保留一段时间的数据？在超表上定义保留策略。下面创建 30 天的保留策略：TimescaleDB 会安排一个每天运行的任务，删除只包含 30 天前数据的 chunk。

SELECT add_retention_policy(
  'watch.heart_rate_measurements', INTERVAL '30 days');

-- 也可以指定任务运行频率，比如每 12 小时一次
SELECT add_retention_policy(
  'watch.heart_rate_measurements',
  drop_after => INTERVAL '30 days',
  schedule_interval => INTERVAL '12 hours');

读本章时千万别执行！示例数据是 2024–2025 年的，如果你在 2025 年之后读这本书，所有数据都在 30 天之外，会被全部删掉。删整个 chunk 比逐行 DELETE 高效得多。

分析时间序列数据

TimescaleDB 提供了几十个专门的函数（称为 hyperfunctions），能高效处理和分析海量时序数据。我们用其中几个，让手表用户更好地了解自己的健康状况。

time_bucket：按时间分桶

time_bucket 把时间戳归入指定长度的区间（桶），方便做汇总：最近 30 分钟的平均心率、每次 1 小时锻炼的最高心率、睡眠中每 15 分钟的最低心率……

time_bucket(bucket_width, ts, [origin, timezone, offset])
参数含义
bucket_width桶的长度，比如 '5 minutes'、'3 days'、'1 week'
ts要分桶的时间戳
origin（可选）桶的对齐起点。默认：按月/年/世纪分桶时对齐到 2000 年 1 月 1 日零点，其他情况对齐到 2000 年 1 月 3 日零点（一个星期一）
timezone（可选）计算桶边界用的时区，默认 UTC
offset（可选）把所有桶整体偏移一段时间

用户 1 在 2025-04-23 锻炼了，结束后打开 App，想看锻炼期间每 10 分钟的平均和最高心率图表：

  time_bucket('10 minutes', recorded_at) AS period, activity,
  AVG(heart_rate)::int AS avg_rate, MAX (heart_rate)::int AS max_rate
FROM watch.heart_rate_measurements
WHERE watch_id = 1 AND activity = 'workout'
  AND recorded_at >= '2025-04-23' AND recorded_at < '2025-04-24'
GROUP BY period, activity ORDER BY period;

按用户的时区计算

time_bucket 默认用 UTC 计算桶边界，这也是我们服务器和连接的默认时区（SHOW time zone; 返回 UTC）。第二位用户住在日本，戴着 2 号手表。可以显式把 timezone 参数设为 Asia/Tokyo，让桶按他的本地时间对齐：

BEGIN;

SET LOCAL time zone 'Asia/Tokyo';

SELECT time_bucket('1 week', recorded_at, 'Asia/Tokyo',
  '2025-04-01'::timestamptz) AS period, activity,
  AVG(heart_rate)::int AS avg_rate,
  MAX (heart_rate)::int AS max_rate, MIN (heart_rate)::int AS min_rate
FROM watch.heart_rate_measurements
WHERE watch_id = 2 AND recorded_at >= '2025-04-01' AND
  recorded_at < '2025-04-15'
GROUP BY period, activity ORDER BY period, activity;

COMMIT;

         period         | activity | avg_rate | max_rate | min_rate
------------------------+----------+----------+----------+----------
 2025-04-01 00:00:00+09 | resting  |       77 |       79 |       75
 2025-04-01 00:00:00+09 | sleeping |       67 |       69 |       65
 2025-04-01 00:00:00+09 | walking  |       90 |       94 |       85
 2025-04-01 00:00:00+09 | workout  |      142 |      199 |      130
 2025-04-08 00:00:00+09 | resting  |       77 |       79 |       75
 ...
(8 rows)
  • SET LOCAL 在显式事务里把时区从 UTC 改成 Asia/Tokyo，只在这个事务内有效，COMMIT 后自动恢复。
  • 事务内的所有操作都用东京时区：WHERE 里比较的日期范围、time_bucket 计算的桶边界，以及输出的 period —— 因为 recorded_at 和 period 都是 timestamptz，Postgres 会按当前连接（这里是当前事务）的时区解释和显示它们。
  • period 末尾的 +09 表示 UTC+9，正是东京时间。
ⓘ 另一种做法

这是完全依靠 Postgres 内置能力支持多时区用户的做法。另一种常见做法是在应用层把用户的本地时间转换成 UTC 再发给 Postgres，数据库里全程用 UTC 计算。

time_bucket_gapfill：填补空缺

手表虽然定时测量，但不一定每次都能把数据送到后端：用户可能摘了手表，设备可能断网。于是某些时间段会缺数据。time_bucket 遇到空缺会直接跳过那个桶：

SELECT watch_id, time_bucket('1 minute', recorded_at) AS minute,
  AVG(heart_rate)::int AS avg_rate
FROM watch.heart_rate_measurements
WHERE watch_id=1 AND recorded_at BETWEEN '2025-03-02 07:25'
  AND '2025-03-02 07:36'
GROUP BY watch_id, minute ORDER BY minute;

结果只有 9 行：07:30、07:31、07:35 没有数据。用户想看连续的心率图，这样的缺口体验不好。换成 time_bucket_gapfill，它会生成连续的桶，包括空缺的：

SELECT watch_id, time_bucket_gapfill('1 minute', recorded_at) AS minute,
  AVG(heart_rate)::int AS avg_rate
FROM watch.heart_rate_measurements
WHERE watch_id=1 AND recorded_at BETWEEN '2025-03-02 07:25'
  AND '2025-03-02 07:36'
GROUP BY watch_id, minute ORDER BY minute;

现在有 12 行了，但 07:30、07:31、07:35 的 avg_rate 还是空的 —— gapfill 只补桶，不补值。TimescaleDB 提供了两个配套函数来填值：

  • LOCF（last observation carried forward，沿用上一次观测值）：用最近一个已知值填补。适合值往往保持不变或变化很小的场景。
  • interpolate（线性插值）：在前后两个已知值之间做线性插值。适合值随时间平滑变化的场景。
SELECT watch_id, time_bucket_gapfill('1 minute', recorded_at) AS minute,
  LOCF(AVG(heart_rate)::int) AS avg_rate
FROM watch.heart_rate_measurements
WHERE watch_id=1 AND recorded_at BETWEEN '2025-03-02 07:25'
  AND '2025-03-02 07:36'
GROUP BY watch_id, minute ORDER BY minute;

SELECT watch_id, time_bucket_gapfill('1 minute', recorded_at) AS minute,
  interpolate(AVG(heart_rate)::int) AS avg_rate
FROM watch.heart_rate_measurements
WHERE watch_id=1 AND recorded_at BETWEEN '2025-03-02 07:25'
  AND '2025-03-02 07:36'
GROUP BY watch_id, minute ORDER BY minute;

连续聚合

除了各种分析函数，TimescaleDB 还提供连续聚合（continuous aggregates）：存储预先计算好的查询结果，并按预定策略在后台刷新。 适合在大量历史数据上跑分析查询，或者查询频率远高于数据更新频率的场景。

设想手表在后台持续监测心率，如果最近 5 分钟里心率一直低于 50 BPM 就发出警报 —— 这可能是心动过缓（bradycardia，心跳比正常慢）的症状，经常收到警报的用户应该去看医生。 这个监测可以在手表本地做，也可以交给本来就定时收到数据的后端。我们用连续聚合在后端实现。

创建和使用连续聚合

连续聚合是一种特殊的 Postgres 物化视图（第 2 章讲过），它把预计算的结果存在一个超表里：可以像普通表一样查询，而且结果也是自动分区的。

CREATE MATERIALIZED VIEW watch.low_heart_rate_count_per_5min
WITH (timescaledb.continuous) AS
SELECT
  watch_id,
  time_bucket('5 minutes', recorded_at) AS bucket,
  MIN(heart_rate) as min_rate,
  COUNT(*) FILTER (WHERE heart_rate < 50) AS low_rate_count,
  COUNT(*) AS total_measurements
FROM watch.heart_rate_measurements
GROUP BY watch_id, bucket;
  • WITH (timescaledb.continuous) 把物化视图声明为连续聚合。
  • 按 recorded_at 分成 5 分钟的桶，存在 bucket 列。
  • 每个桶算出：最低心率 min_rate、低于 50 BPM 的次数 low_rate_count、测量总数 total_measurements。
  • COUNT(*) FILTER (WHERE …) 只统计满足条件的行，是标准 SQL 的聚合过滤写法。
  • 每台设备分别聚合（GROUP BY watch_id, bucket）。

创建后它已经填好了数据：288577 行，存在 3 个 chunk 里（show_chunks('watch.low_heart_rate_count_per_5min') 可查）。

假设现在是 2025 年 11 月 30 日深夜，用户戴着手表睡觉，后端收到数据并分析。手表收到一条推送：2:35 开始的 5 分钟内心率偏低。推送内容来自这条查询：

SELECT bucket, low_rate_count,
  (low_rate_count >= 5) AS bradycardia_detected
FROM watch.low_heart_rate_count_per_5min
WHERE bucket = '2025-11-30 02:35' AND watch_id = 3;

         bucket         | low_rate_count | bradycardia_detected
------------------------+----------------+----------------------
 2025-11-30 02:35:00+00 |              5 | t
(1 row)

手表至少每分钟上报一次，所以 5 分钟里低心率出现 ≥ 5 次，很可能每一分钟心率都偏低。手表确认通知后设一个定时器，10 分钟后再查 2:35 到 2:45 这三个连续的 5 分钟窗口：

SELECT bucket, low_rate_count,
  (low_rate_count >= 5) AS bradycardia_detected
FROM watch.low_heart_rate_count_per_5min
WHERE bucket BETWEEN '2025-11-30 02:35' AND
  '2025-11-30 02:45' AND watch_id = 3
ORDER BY bucket;

         bucket         | low_rate_count | bradycardia_detected
------------------------+----------------+----------------------
 2025-11-30 02:35:00+00 |              5 | t
 2025-11-30 02:40:00+00 |              5 | t
 2025-11-30 02:45:00+00 |              5 | t
(3 rows)

低心率持续了整整 15 分钟。手表轻轻振动几秒并显示警报，确保用户醒来后注意到。

刷新连续聚合

接着是 12 月 1 日深夜，同一位用户的手表又上报了一批测量：

INSERT INTO watch.heart_rate_measurements
(watch_id, recorded_at, heart_rate, activity) VALUES
(3, '2025-12-01 00:45:00+00', 48, 'sleeping'),
(3, '2025-12-01 00:46:00+00', 46, 'sleeping'),
(3, '2025-12-01 00:47:00+00', 44, 'sleeping'),
(3, '2025-12-01 00:47:30+00', 47, 'sleeping'),
(3, '2025-12-01 00:48:00+00', 48, 'sleeping'),
(3, '2025-12-01 00:48:30+00', 45, 'sleeping'),
(3, '2025-12-01 00:49:00+00', 43, 'sleeping');

数据进了表，但不会自动更新连续聚合。查 00:45 这个桶，结果是空的。TimescaleDB 可以定义刷新策略：

SELECT add_continuous_aggregate_policy
  ('watch.low_heart_rate_count_per_5min',
  start_offset => INTERVAL '15 minutes',
  end_offset => INTERVAL '1 minute',
  schedule_interval => INTERVAL '1 minute');
  • start_offset：从当前时间往前多久开始刷新 —— 这里是 15 分钟前。
  • end_offset：刷新到离当前时间多远为止 —— 这里停在 1 分钟前，避免和正在进行的写入冲突。
  • schedule_interval：策略多久运行一次 —— 每分钟。

但策略是相对当前时间工作的，而示例数据的时间戳是固定的（2025 年 12 月），所以策略多半刷新不到它们。这时可以手动刷新指定的时间范围：

CALL refresh_continuous_aggregate('watch.low_heart_rate_count_per_5min',
    '2025-12-01 00:45:00+00', '2025-12-01 00:50:00+00');

         bucket         | low_rate_count | bradycardia_detected
------------------------+----------------+----------------------
 2025-12-01 00:45:00+00 |              7 | t
(1 row)
💡 连续聚合也能设保留策略
SELECT add_retention_policy(
   'watch.low_heart_rate_count_per_5min', INTERVAL '7 days');

扩展会安排每天运行的任务，删除只包含 7 天前数据的聚合 chunk。原始数据和聚合可以有不同的保留期，比如原始数据留 30 天、5 分钟汇总留 1 年。

B-tree 索引

B-tree 完全支持 date、time、timestamp 等日期时间类型。recorded_at 上的单列索引是时序查询的通用方案。 但我们的应用通常同时按 watch_id 和 recorded_at 过滤，所以建一个复合索引： 

CREATE INDEX heart_rate_btree_idx
ON watch.heart_rate_measurements (recorded_at, watch_id);

它能优化只按 recorded_at，或同时按 recorded_at 和 watch_id 过滤的查询（pg_indexes 可以确认是 USING btree）。表被分成了多个分区，Postgres 会为每个分区创建本地索引：

SELECT indexname, indexdef
FROM pg_indexes
WHERE schemaname = '_timescaledb_internal'
  AND tablename LIKE '_hyper_1\_%_chunk' ESCAPE '\';

                                       |   ON _timescaledb_internal._hyper_1_1_chunk

 _hyper_1_3_chunk_heart_rate_btree_idx | ...

ⓘ 复合索引的列顺序

(recorded_at, watch_id) 能用于只有 recorded_at，或两者都有的条件；如果查询跳过第一列、只按 watch_id 过滤，Postgres 17 及更早的版本用不上这个索引（Postgres 18 起支持 skip scan）。复习见第 4 章。

BRIN 索引

BRIN（Block Range Index，块范围索引）是一种特别适合时序数据的索引，尤其在看重索引大小时可以替代 B-tree。 它为这样的大表设计：某些列的值和行在表中的物理位置高度相关。这是什么意思？以 recorded_at 为例：

  • 每条新测量的 recorded_at 都是当前时间，比上一条更晚 —— 时钟只会向前走。
  • 新行被追加到表里，Postgres 把它放进一个页（page）。页大小是 8 KB，远大于一条测量记录，所以每页能存几十条。
  • 时序数据只追加、不更新，行按顺序填满一页又一页。同一页里的行，时间都很接近（即使来自不同设备，偏差也不大）；后面的页存的是更晚的时间。

建 BRIN 索引时，Postgres 扫描表，为每个页范围记录 recorded_at 的最小值和最大值。搜索时，BRIN 用这些范围信息决定访问哪些页、跳过哪些页。 因为它只存每个范围的 min/max，而不像 B-tree 那样索引每一个实际值，所以体积小得多： 

CREATE INDEX heart_rate_brin_idx
ON watch.heart_rate_measurements
USING brin (recorded_at);

和 B-tree 一样，它也会在每个分区上建本地索引。比较一下大小：

  AND recorded_at >= '2025-03-15 00:00'
  AND recorded_at < '2025-03-16 00:00'

数据量还不大（总共约 140 万行、每个分区约 12.5 万行），只查一天，Postgres 选择了 B-tree，耗时约 2.3 ms：

   -> HashAggregate (actual time=8.368..8.389 rows=10 loops=1)
         -> Result (actual time=0.482..8.077 rows=1510 loops=1)

  1. Bitmap Index Scan：用 BRIN 找出 min/max 满足条件的页范围，生成要访问的页位图（全是 lossy 的，见第 4 章）。

  3. HashAggregate：对剩下的 1510 行做聚合、排序。

如果应用开始分析好几个月甚至几年的数据，B-tree 和 BRIN 可能都不再被使用 —— 对相关分区做全表扫描反而更高效。 这时可以利用 TimescaleDB 的列式存储能力，把特定分区的数据以为分析优化的列式格式存储。 比如最近三个月的测量留在行存储里并建索引，三个月前的数据转到列存储、不建索引。 这超出了本书的范围，可以阅读 TimescaleDB 列存储 Hypercore 的文档。

小结

  • Postgres 能轻松处理持续写入、或不定期批量写入的时序负载。
  • 表分区把大表拆成多个分区，查询只访问满足条件的分区。
  • TimescaleDB 把 Postgres 变成时序数据库：自动分区（超表 / chunk）、专门的分析函数、列式存储引擎等。
  • time_bucket 把时间戳分桶，便于汇总；time_bucket_gapfill 生成连续的桶，配合 LOCF 或 interpolate 填补空缺。
  • 连续聚合存储预计算的结果，按策略在后台刷新。
  • 超表和连续聚合都可以设置保留策略，自动删除过期数据。
  • B-tree 和 BRIN 索引都能优化时序查询，需要在索引大小和性能之间权衡。

  5. 把清单 9.26 的时间范围改成整个 3 月，分别只保留 B-tree 或只保留 BRIN，比较执行计划和耗时。
    参考答案 
    EXPLAIN (analyze, costs off)
SELECT time_bucket('1 hour', recorded_at) AS period, AVG(heart_rate)::int
FROM watch.heart_rate_measurements
WHERE activity = 'sleeping'
  AND recorded_at >= '2025-03-01' AND recorded_at < '2025-04-01'
GROUP BY period ORDER BY period;
    只保留的索引执行计划耗时
    B-tree (recorded_at, watch_id)两个 chunk 上各一次 Index Scan约 34 ms
    BRIN (recorded_at)两个 chunk 上各一次 Seq Scan（没用 BRIN）约 24 ms
    都不要同上，Seq Scan约 25 ms

    范围扩大到整个月，结论就变了：TimescaleDB 先做 chunk 排除，只剩下覆盖 3 月的两个 chunk，而查询要读的正是这两个 chunk 里的大部分数据。 这时顺序扫描比按索引逐行读更快，规划器连 BRIN 都不用。索引的价值在“窄”的时间范围（比如清单 9.26 的一天）；宽范围的分析查询，靠分区裁剪就够了。
