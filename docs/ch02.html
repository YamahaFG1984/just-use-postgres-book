标准关系型数据库能力

这一章快速巡览所有关系型数据库都具备、Postgres 当然也具备的那些“标准能力”： 建库建表、增删改查、约束、事务、连接查询、函数与触发器、视图、角色权限。 我们会围绕一个贯穿全章的例子来学：一个服务成千上万商家的多租户电商 SaaS 平台。

本章目标

  • 理解“服务器 → 数据库 → 模式（schema）→ 表”这四层结构，以及多租户的三种做法
  • 熟练使用 SELECT / INSERT / UPDATE / DELETE
  • 用约束和外键在数据库层面守住数据的正确性
  • 理解隐式事务、显式事务，以及 MVCC 如何让读写互不阻塞
  • 会写内连接和左连接
  • 用 PL/pgSQL 函数实现购物车，用触发器自动维护订单总额
  • 会用普通视图和物化视图，会用角色限制访问
ⓘ 前置知识

本书假设你懂一点关系型数据库和 SQL 的基础：知道怎么建表、插数据、查数据。 如果这些对你来说还很陌生也没关系，先跟着本章把例子跑一遍，看看这些功能长什么样，遇到不懂的再去查资料。

创建数据库结构

Postgres 把应用数据存在表（table）里。表是行（row）的命名集合，每一行都有同一组列（column）。 除了表，Postgres 还提供了两层更高的抽象来组织结构：

  • 模式（schema）：数据库对象的命名集合，可以理解成编程语言里的命名空间或包。 用来把表、视图、函数等归到一个逻辑名下。默认情况下，你创建的所有对象都放在 Postgres 自动创建的 public 模式里。
  • 数据库（database）：最顶层的命名集合，里面包含模式，模式里再包含表等对象。 同一个数据库里不同模式的表可以在一条 SQL 里一起查；但跨数据库的表就不行了（除非借助第三方方案）。
ⓘ 什么是“数据库对象”

在 Postgres 里，数据库对象指用来存储或操作数据的命名 SQL 对象。表、视图、函数、触发器都是数据库对象。

故事背景：咖啡店和精酿酒馆

Jake 在美国东海岸开了一家小有名气的连锁咖啡店，想在网上卖咖啡豆和周边，但完全不知道从何下手。 他的朋友 Susannah 在西海岸开了一家很火的精酿酒馆，靠我们的电商平台一周就上线了网店 —— 注册、建商品目录、开店，支付、物流跟踪、会员管理都是现成的。于是 Jake 也决定用我们的平台。

我们的电商平台是一个典型的多租户（multitenant）SaaS 应用： 多个客户（租户）共享 CPU、存储等资源，从而降低成本； 同时又必须保证数据隔离 —— Jake 和 Susannah 虽然是朋友，但彼此的商业数据不能互相看到。

多租户的三种做法

我们选择数据库级多租户：每个商家一个专属数据库，通过角色和权限（本章最后一节）确保商家只能连自己的库。 如果平台规模扩大，还可以轻松地把不同租户的数据库分配到不同的 Postgres 服务器上。

这样做的好处：数据库结构和应用架构对齐；不同模块里同名的表不会冲突；而且因为都在同一个数据库里， 一条 SELECT 就能跨模式联合查询（如果每个模块各用一个数据库，就做不到了）。

💡 自动化

如果每个租户都要建同样的库、模式和表，就应该把这个过程自动化：新商家注册时，平台自动为他建好数据库和全部对象。

当前模式与 search_path

有了多个模式，就要理解当前模式：当 SQL 里没写模式名时，Postgres 去哪里找表？ 答案由 search_path 决定： 

SHOW search_path;

   search_path
-----------------
 "$user", public
(1 row)

意思是：先找和当前用户同名的模式，没有就找 public。可以随时改： 

SET search_path TO products;
-- 之后不写模式名的语句，都会在 products 模式里执行
SELECT id FROM catalog;   -- 等价于 SELECT id FROM products.catalog

创建表

数据库和模式都有默认值（postgres 库、public 模式），可以跳过；但表必须你自己设计和创建，没有捷径。 Jake 准备上架商品，先建商品目录表： 

CREATE TABLE products.catalog (
    id SERIAL PRIMARY KEY,
    name VARCHAR (100) NOT NULL,
    description TEXT NOT NULL,
    category TEXT CHECK (category IN ('coffee', 'mug', 't-shirt')),
    price NUMERIC(10, 2),
    stock_quantity INT CHECK (stock_quantity >= 0)
);
  • products.catalog：表放在 products 模式下。模式名可以省略，省略就用当前模式。
  • SERIAL：自增整数。Postgres 会在背后创建一个序列（sequence）对象来自动生成 ID， 生成 32 位整数，最大 2,147,483,647（2³¹−1）。
  • NOT NULL、CHECK：约束，2.3 节详细讲。

再建一张商品评论表：

CREATE TABLE products.reviews (
    id BIGSERIAL PRIMARY KEY,
    product_id INT,
    customer_id INT,
    review TEXT,
    rank SMALLINT
);

这次 ID 用了 BIGSERIAL：生成 64 位整数，最大约 922 亿亿（2⁶³−1）。 因为评论数量预计会远超商品数量，所以选了更大的类型。 这张表故意没加任何约束 —— 约束不是必须的，而且以后随时可以用 ALTER TABLE 补上（2.3 节会演示）。

类型位数范围适合
SMALLINT16 位−32768 ~ 32767评分、小枚举
INT / SERIAL32 位约 ±21 亿大多数 ID 和计数
BIGINT / BIGSERIAL64 位约 ±922 亿亿海量数据的 ID
NUMERIC(10,2)可变共 10 位，2 位小数金额（精确，不会有浮点误差）
UUID128 位全局唯一分布式 ID（2.4 节）
ⓘ 数据类型

Postgres 的数据类型非常丰富。为列挑选和应用层最匹配的类型时，官方文档是最好的参考：postgresql.org/docs/current/datatype.html。

查询和修改数据

SQL 标准定义了四个最核心的数据操作命令：SELECT、INSERT、UPDATE、DELETE， 它们属于 DML（Data Manipulation Language，数据操作语言）。 （而 CREATE、ALTER、DROP 这些改结构的命令属于 DDL，数据定义语言。）

Jake 在网店后台添加了前五件商品，平台后端收到请求后执行：

  ('Sunrise Brew Co. T-Shirt',

三种口味的咖啡豆、一个品牌马克杯、一件品牌 T 恤。注意我们没有提供 id —— 它由序列自动生成：

⚠ 千万别忘了 WHERE

UPDATE 和 DELETE 不带 WHERE 会作用于整张表的所有行。这是新手（和老手）最经典的事故之一。执行前多看一眼。

SELECT id, name, price, stock_quantity FROM products.catalog;

 id |           name           | price | stock_quantity
----+--------------------------+-------+----------------
  3 | Morning Glory            | 13.99 |             30
  4 | Sunrise Brew Co. Mug     |  9.99 |            100
  5 | Sunrise Brew Co. T-Shirt | 19.99 |             25
  1 | Sunrise Blend            | 16.54 |             50
(4 rows)
ⓘ 为什么 id=1 跑到最后去了

没有 ORDER BY 时，Postgres 不保证返回顺序。这里 id=1 被更新过 —— Postgres 的更新实际上是写入一个新版本的行（下面讲 MVCC 时会细说），新版本存到了表的后面，所以扫描时最后出现。 需要固定顺序时，一定要写 ORDER BY。

数据完整性

数据完整性指数据在整个生命周期中的准确、一致和完整。 关系型数据库就是为“任何时候数据都必须正确”的事务型应用设计的。Postgres 提供了事务和各种约束来保证这一点 —— 但这些能力需要我们开发者主动、及时地用起来。

约束：写入前的“安检门”

第一道防线是数据类型：价格列是 NUMERIC，你就不可能写进去一段文本或一个布尔值。 第二道防线是约束（constraint）：每次写入时都会检查的规则。

约束作用
非空 NOT NULL该列不能为 null
唯一 UNIQUE该列（或列组合）不能有重复值
主键 PRIMARY KEY行的唯一标识，相当于“非空 + 唯一”
外键 FOREIGN KEY该列的值必须在另一张表的某行里存在
检查 CHECK值必须满足自定义条件
排他 EXCLUDE任意两行在指定列上用指定运算符比较，至少有一个比较结果为 false 或 null（2.6 节有实例）

设想我们平台为了赶进度，原本打算让后端在写库前做所有校验，结果手快改坏了好几处检查，库里已经出现了脏数据。 为了防止再发生，我们决定在数据库层面补上约束。先看看商品表现有哪些约束： 

\d products.catalog

                 Table "products.catalog"
     Column     |          Type          | Nullable |
----------------+------------------------+----------+
 id             | integer                | not null |
 name           | character varying(100) | not null |
 description    | text                   | not null |
 category       | text                   |          |
 price          | numeric(10,2)          |          |
 stock_quantity | integer                |          |
Indexes:
    "catalog_pkey" PRIMARY KEY, btree (id)
Check constraints:
    "catalog_category_check" CHECK (category = ANY (ARRAY['coffee'::text,
         'mug'::text, 't-shirt'::text]))
    "catalog_stock_quantity_check" CHECK (stock_quantity >= 0)
  • id 是主键。主键依赖一个名为 catalog_pkey 的索引来快速检查唯一性 —— 在索引里查找是对数复杂度，远快于把整张表从头扫到尾（全表扫描）。
  • name 和 description 都是 NOT NULL。
  • category 只能是 coffee、mug、t-shirt 之一。
  • stock_quantity 不能小于 0。

唯独 price 什么约束都没有。商家手滑输了个负价格怎么办？用 ALTER TABLE 补一个：

ALTER TABLE products.catalog
    ADD CONSTRAINT catalog_price_check CHECK (price > 0);

现在就算后端漏检，Postgres 也会拦住：

UPDATE products.catalog SET price = -16 WHERE name = 'Morning Glory';

ERROR: new row for relation "catalog" violates
check constraint "catalog_price_check"
DETAIL: Failing row contains (3, Morning Glory, A light roast with
  bright acidity and floral notes., coffee, -16.00, 30).
⚠ 已有数据违反新约束时

如果表里已经有一行价格是负数，清单 2.4 的 ALTER TABLE 本身就会失败： ERROR: check constraint "catalog_price_check" of relation "catalog" is violated by some row。 这时要先把违规的行修正，再加约束。

评论表也补上约束：评论内容不能为空，评分必须在 1 到 5 之间：

ALTER TABLE products.reviews
    ALTER COLUMN review SET NOT NULL,
    ADD CONSTRAINT review_rank_check CHECK (rank BETWEEN 1 AND 5);
💡 能早加就早加

如果你一开始就知道需要哪些约束，直接写在 CREATE TABLE 里。这里分开加只是为了演示 ALTER TABLE 的用法。

外键：表与表之间的“引用必须存在”

评论表的 product_id 和 customer_id 应该指向真实存在的商品和客户。 如果指向了一个根本不存在的商品呢？这就是外键约束要解决的问题。 

ALTER TABLE products.reviews
    ADD CONSTRAINT products_review_product_id_fk
    FOREIGN KEY (product_id) REFERENCES products.catalog(id);
ⓘ 被引用的列必须唯一

外键引用的列必须有唯一约束（主键天然满足）。否则会报错 there is no unique constraint matching given keys for referenced table。 原因是 Postgres 需要快速确认“这个 product_id 真的存在”，最快的办法就是去查唯一列上自带的索引。

再建客户账户表，并给评论表的 customer_id 也加上外键：

CREATE TABLE customers.accounts (
    id SERIAL PRIMARY KEY,
    name TEXT NOT NULL,
    email TEXT NOT NULL,
    passwd_hash TEXT NOT NULL
);

ALTER TABLE products.reviews
    ADD CONSTRAINT products_review_customer_id_fk
    FOREIGN KEY (customer_id) REFERENCES customers.accounts(id);

三位老顾客发现 Jake 开了网店，纷纷注册：

INSERT INTO customers.accounts (name, email, passwd_hash)
VALUES
('Alice Johnson', 'alice.johnson@example.com',
    '5f4dcc3b5aa765d61d8327deb882cf99'),
('Bob Smith', 'bob.smith@example.com', 'd8578edf8458ce06fbc5bb76a58c5ca4'),
('Charlie Brown', 'charlie.brown@example.com',
     '5f4dcc3b5aa765d61d8327deb882cf99');

他们的 ID 依次是 1、2、3。Alice 看到了她已经拥有并且很喜欢的马克杯（id=4），忍不住要写好评。 可她点“发送”后却报错了。我们查后端日志，发现过去五分钟里很多商家的顾客都发不了评论，Postgres 报的是外键冲突： 

ERROR: insert or update on table "reviews" violates
foreign key constraint "products_review_product_id_fk"
DETAIL: Key (product_id)=(1004) is not present in table "catalog".

马克杯的 ID 应该是 4，后端却传了 1004 —— 我们的应用代码里有个 bug。几分钟内修好上线后，Alice 的评论成功提交： 

INSERT INTO products.reviews (product_id, customer_id, review, rank)
VALUES (4, 1, 'This mug is perfect — sturdy, stylish, and keeps
   my coffee warm for a good while.', 5);

虽然 bug 影响了一些用户，但如果没有外键，后果会严重得多：我们得花大量时间清理那些挂在错误商品、甚至不存在的商品下面的评论。

外键是双向守护的

如果 Alice 想注销账户，后端直接删除她的记录：

DELETE FROM customers.accounts WHERE id = 1;

ERROR: update or delete on table "accounts" violates foreign key
   constraint "products_review_customer_id_fk" on table "reviews"
DETAIL: Key (id)=(1) is still referenced from table "reviews".

Postgres 提醒我们：Alice 还有一条评论，删掉她这条评论就成了“孤儿”。我们不希望这样， 于是改用软删除：加一个 deleted 标志列，注销时只把它设为 true，记录本身保留。 

ALTER TABLE customers.accounts
    ADD COLUMN deleted boolean DEFAULT false;

-- 注销时：
UPDATE customers.accounts SET deleted = true WHERE id = 1;
💡 ON DELETE CASCADE

如果你希望删除客户时连同其评论一起删掉，在外键定义里加上 ON DELETE CASCADE。之后删除 accounts 里的客户，Postgres 会自动删除 reviews 里关联的所有评论。

事务

不论是更新一行，还是跨几张表更新很多行，Postgres 都会按照 ACID 原则以事务方式处理：

A · 原子性 Atomicity

要么全部成功，要么全部撤销，不会只做一半。

C · 一致性 Consistency

事务前后，数据都满足所有约束和规则。

I · 隔离性 Isolation

并发执行的事务互不干扰，像是排队执行一样。

D · 持久性 Durability

一旦提交，就算服务器马上断电，数据也不会丢。

隐式事务

Jake 的仓库到了一批咖啡豆。他先给 Sunrise Blend 加 100 袋库存，又发现 Sunrise Blend 和 Morning Glory 各还有 50 袋：

UPDATE products.catalog
SET stock_quantity = stock_quantity + 100
WHERE id = 1;

UPDATE products.catalog
SET stock_quantity = stock_quantity + 50
WHERE id = 1 or id = 3;

这两条语句都是隐式事务：Postgres 给每条语句分配一个内部事务 ID，读出当前库存、加上数量、写回、提交。 中途出任何问题都会回滚到语句执行之前的状态。INSERT 和 DELETE 也一样。 也就是说，哪怕你从没写过 BEGIN，Postgres 也一直在背后帮你保证一致性。

显式事务

当你需要把多条 SQL 当作一个整体来执行时，就要用显式事务：以 BEGIN 开始，以 COMMIT 提交。 先建订单相关的两张表： 

CREATE TABLE sales.orders (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    customer_id INT REFERENCES customers.accounts(id),
    order_date TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP,
    total_amount DECIMAL(10, 2)
);

CREATE TABLE sales.order_items (
    order_id UUID REFERENCES sales.orders(id),
    product_id INT REFERENCES products.catalog(id),
    quantity INT CHECK (quantity > 0),
    price DECIMAL (10, 2),
    PRIMARY KEY (order_id, product_id)
);
  • orders.id 是 UUID 主键，应用没传值时由 gen_random_uuid() 生成随机的 UUIDv4。 UUID 主键不依赖序列，通常扩展性更好。
  • order_items.price 记录的是下单时的价格，因为商品价格以后可能会变。
  • PRIMARY KEY (order_id, product_id) 是复合主键：一个订单里可以有多种商品，但每种商品只出现一次。
ⓘ Postgres 18 的 UUIDv7

Postgres 18 开始支持 uuidv7()。UUIDv7 的值里包含 Unix 时间戳，时间相近生成的 UUID 在索引里也挨得近， 因此对索引更友好、访问更快。gen_random_uuid() 是 uuidv4() 的别名。

一位顾客买了一袋 Sunrise Blend 和一个马克杯。后端用一个显式事务记录这笔订单：

BEGIN;

INSERT INTO sales.orders (id, customer_id, total_amount)
VALUES ('19a0cffc-8757-453c-a4d2-b554fdc08954', 1, 26.53);

INSERT INTO sales.order_items (order_id, product_id, quantity, price)
VALUES ('19a0cffc-8757-453c-a4d2-b554fdc08954', 1, 1, 16.54),
 ('19a0cffc-8757-453c-a4d2-b554fdc08954', 4, 1, 9.99);

UPDATE products.catalog
SET stock_quantity = stock_quantity - 1
WHERE id IN (1, 4);

COMMIT;

（这里显式写出 UUID 只是为了让你看看它长什么样，实际可以交给 gen_random_uuid() 自动生成。）

◆ 回滚的数据去哪了

被回滚的修改并不会立刻从磁盘上消失。Postgres 的 MVCC（多版本并发控制）引擎保证后续的请求再也看不到它们； 这些“死掉”的行版本会在一段时间后被垃圾回收清理掉，这个过程叫 vacuum（清理）。

多版本并发控制（MVCC）

在一些顾客下单的同时，另一些顾客还在浏览商品目录，产生大量 SELECT。 Postgres 实现了 MVCC，默认使用读已提交（read committed）隔离级别。 这意味着：一个顾客在 SELECT * FROM products.catalog，另一个在执行清单 2.15 的 UPDATE，两者互不阻塞。

读已提交隔离级别保证两件事：

  • 不会脏读（dirty read）：任何事务都看不到别的事务还没提交的修改。
  • 不会脏写（dirty write）：两个事务同时改同一行时，后来的会被阻塞，直到先来的提交，避免覆盖别人未提交的值。

亲手验证一下。下面这个事务要在两个 psql 会话里并发执行（先别急着运行）：

BEGIN;

SELECT stock_quantity FROM products.catalog
WHERE id = 1;

UPDATE products.catalog
SET stock_quantity = stock_quantity - 1
WHERE id = 1;

COMMIT;

再开一个终端窗口，建立第二个连接：docker exec -it postgres psql -U postgres -d coffee_chain，然后按下图的时间顺序交替执行：

两个事务都完成后确认结果：

SELECT name, stock_quantity FROM products.catalog WHERE id = 1;

     name      | stock_quantity
---------------+----------------
 Sunrise Blend |            197
(1 row)
ⓘ 更强的隔离级别

读已提交在一致性和并发性能之间取得了很好的平衡，所以是默认值。 但 SQL 标准还定义了不可重复读、幻读等现象，Postgres 提供了更强的 REPEATABLE READ（可重复读）和 SERIALIZABLE（可串行化）隔离级别来应对。 什么时候需要它们，官方文档讲得很清楚：Transaction Isolation。

清单 2.16 里的 SELECT 对结果没有影响，实际应用里可以去掉，这里只是为了演示读已提交的行为。

连接查询（JOIN）

到目前为止，每个 SELECT 都只查一张表。连接（join）能一次从多张表取数据： 选好表，再用连接条件把它们的行配对起来。

Jake 开店一小时后打开销售看板。要显示“下单最多的三位顾客”，后端执行：

SELECT c.name, c.id, count(*) as total_orders
FROM customers.accounts c
JOIN sales.orders s ON c.id = s.customer_id
GROUP BY c.id
ORDER BY total_orders DESC
LIMIT 3;

     name      | id | total_orders
---------------+----+--------------
 Alice Johnson |  1 |            1
(1 row)

c 和 s 是表的别名，省得每次都写全名。ON c.id = s.customer_id 是连接条件。 这是内连接（inner join）：只返回两边都能配对上的行。开店才一小时，只有一笔订单，聊胜于无！

看板上还有一份“还没下过单的顾客”报表，这要用左连接（left join）：

SELECT c.name
FROM customers.accounts c
LEFT JOIN sales.orders s ON c.id = s.customer_id
WHERE s.customer_id IS NULL;

     name
---------------
 Bob Smith
 Charlie Brown
(2 rows)

最后一份报表是商品受欢迎程度，同样用左连接 —— 这样一件都没卖出的商品也会出现在列表里：

SELECT c.name, c.category, c.price, SUM(oi.quantity) AS total_sold
FROM products.catalog c
LEFT JOIN sales.order_items oi ON c.id = oi.product_id
GROUP BY c.id
ORDER BY total_sold DESC NULLS LAST, price DESC;

           name           | category | price | total_sold

没卖出的商品 SUM 结果是 NULL。NULLS LAST 让它们排在最后； 销量相同时再按价格从高到低排（price DESC）。

函数与触发器

关系型数据库不只是放数据的容器，它还能运行相当复杂的逻辑。 你可以用 PL/pgSQL（Postgres 专属的过程式语言）写函数和触发器， 也可以借助扩展用 Java、JavaScript、Python 等语言来写。先看一个纯 SQL 的简单函数： 

CREATE OR REPLACE FUNCTION products.get_product_price(product_id INT)
RETURNS NUMERIC(10, 2) AS $$
    SELECT price
    FROM products.catalog
    WHERE id = product_id;
$$ LANGUAGE sql;

SELECT products.get_product_price(5);

 get_product_price
-------------------
             19.99
(1 row)
ⓘ $$ 是什么

$$ … $$ 是 Postgres 的“美元引号”，用来包住函数体。好处是函数体里的单引号不用转义。 需要修改函数时，改好代码后重新执行完整的 CREATE OR REPLACE FUNCTION 即可。

这个函数本身没什么实际价值。那什么时候值得把逻辑放进数据库函数呢？至少有两种场景：

  • 和数据紧密耦合的复杂业务逻辑，每个客户端或微服务都要各自实现一遍。不如写成一个数据库函数，大家共用。
  • 多步骤逻辑需要在应用和数据库之间来回很多次。比如银行给几千个储蓄账户计息： 一种做法是把所有账户读到应用层、算好利息、再写回去；另一种是一个数据库函数在内部全部做完，省掉来回传输，网络延迟高、数据量大时尤其划算。
ⓘ 函数 vs 存储过程

在很多数据库里“函数”和“存储过程”是同义词，但 Postgres 里不是。 Postgres 的存储过程用 CREATE PROCEDURE 创建、不返回值，是 Postgres 11 才引入的独立 API； 而函数从一开始就有。

触发器（trigger）是一种特殊的函数，在数据变化之前或之后由 Postgres 自动执行。 适合审计（记录谁改了什么）和事件驱动架构（数据库里的变化触发别处的动作）。

实战：用函数实现购物车

你一定有过这种体验：在家用电脑逛网店，往购物车里加了两件商品，还没付款就出门了； 几小时后用手机打开同一家店，购物车里那两件还在。我们用数据库函数来实现一个简化版。

先引入待处理订单（pending order）的概念：顾客正在挑选、还没结账的订单就是“购物车”。 复用 sales.orders 表，加一个状态列： 

ALTER TABLE sales.orders
ADD COLUMN status TEXT DEFAULT 'pending'
  CHECK (status in ('pending','ordered'));

UPDATE sales.orders SET status = 'ordered';

ALTER TABLE sales.orders
ADD CONSTRAINT one_pending_order_per_customer
EXCLUDE USING btree (customer_id WITH =)
WHERE (status = 'pending');
  1. 第一句加 status 列，只能是 pending（待处理）或 ordered（已下单），默认 pending。
  2. 第二句把已有订单都改成 ordered —— 因为上一句让它们默认成了 pending。
  3. 第三句是排他约束：(customer_id WITH =) 的意思是“customer_id 相等的两行不能同时存在”， 但只在 WHERE status = 'pending' 的行之间检查。也就是说，每个顾客最多只能有一个购物车，已完成的订单则不受限。 USING btree 表示用 B-tree 索引来高效检查。

接着用 PL/pgSQL 实现“加入购物车”函数，它覆盖了大部分边界情况：

CREATE OR REPLACE FUNCTION sales.order_add_item(customer_id_param INT,
  product_id_param INT, quantity_param INT)
RETURNS TABLE (order_id UUID, prod_id INT,
  quantity INT, prod_price DECIMAL) AS $$
DECLARE
    pending_order_id UUID;               -- 变量：该顾客的购物车 ID
BEGIN
    -- ① 找这个顾客现有的购物车
    SELECT id INTO pending_order_id
    FROM sales.orders
    WHERE customer_id = customer_id_param
      AND status = 'pending'
    LIMIT 1;

    -- ② 没有就新建一个，并用 RETURNING 拿到自动生成的 UUID
    IF pending_order_id IS NULL THEN
        INSERT INTO sales.orders (customer_id, status)
        VALUES (customer_id_param, 'pending')
        RETURNING id INTO pending_order_id;
    END IF;

    -- ③ 商品已在购物车里就改数量，不在就插入
    MERGE INTO sales.order_items AS oi
    USING (SELECT id, price FROM products.catalog
      WHERE id = product_id_param) AS prod
    ON oi.product_id = prod.id AND oi.order_id = pending_order_id
    WHEN MATCHED THEN
        UPDATE SET quantity = quantity_param
    WHEN NOT MATCHED THEN
        INSERT (order_id, product_id, quantity, price)
        VALUES (pending_order_id, prod.id, quantity_param, prod.price);

    -- ④ 返回购物车里的全部商品
    RETURN QUERY
    SELECT oi.order_id, oi.product_id, oi.quantity, oi.price as prod_price
    FROM sales.order_items as oi
    WHERE oi.order_id = pending_order_id;
END;
$$ LANGUAGE plpgsql;
ⓘ MERGE 是什么

MERGE（Postgres 15 起支持）把“存在就更新，不存在就插入”合成一条语句：USING 指定数据来源，ON 是匹配条件，WHEN MATCHED / WHEN NOT MATCHED 分别处理两种情况。

老顾客 Charlie Brown（id=3）登录后，往购物车里放了两袋 Morning Glory（id=3）：

SELECT * FROM sales.order_add_item(
    customer_id_param => 3,
    product_id_param => 3,
    quantity_param => 2
    );

               order_id               | prod_id | quantity | prod_price
--------------------------------------+---------+----------+------------
 e900fb15-aa65-4eea-bd52-1abe8d5832b6 |       3 |        2 |      13.99
(1 row)
ⓘ 命名参数

参数名 => 值 是命名参数写法，只为可读性，可以省略：SELECT * FROM sales.order_add_item(3, 3, 2) 效果一样。

结账前他又加了一件 T 恤（id=5）。函数找到已有的购物车，把 T 恤加进去，返回完整清单：

    product_id_param => 5,
    quantity_param => 1
    );

               order_id               | prod_id | quantity | prod_price
--------------------------------------+---------+----------+------------
 e900fb15-aa65-4eea-bd52-1abe8d5832b6 |       3 |        2 |      13.99

(2 rows)
★ 函数是原子执行的

Postgres 以事务方式执行函数：函数执行中任何一步失败，它之前做的所有修改都会回滚。这一点对保证数据一致性非常重要。

接下来实现结账函数：

CREATE OR REPLACE FUNCTION sales.order_checkout(customer_id_param INT)
RETURNS TABLE (order_id UUID, customer_id INT, total_amount DECIMAL) AS $$
DECLARE
    pending_order_id UUID;
    final_total_amount DECIMAL := 0;
BEGIN
    SELECT id INTO pending_order_id
    FROM sales.orders as o
    WHERE o.customer_id = customer_id_param
      AND status = 'pending'
    LIMIT 1;

    IF pending_order_id IS NULL THEN
        RAISE EXCEPTION 'No pending order found for customer %',
          customer_id_param;
    END IF;

    SELECT SUM(oi.quantity * oi.price) INTO final_total_amount
    FROM sales.order_items oi
    WHERE oi.order_id = pending_order_id;

    UPDATE sales.orders
    SET status = 'ordered',
        total_amount = final_total_amount,
        order_date = CURRENT_TIMESTAMP
    WHERE id = pending_order_id;

    UPDATE products.catalog
    SET stock_quantity = stock_quantity - oi.quantity
    FROM sales.order_items oi
    WHERE products.catalog.id = oi.product_id
      AND oi.order_id = pending_order_id;

    RETURN QUERY
    SELECT o.id, o.customer_id, o.total_amount
    FROM sales.orders as o
    WHERE o.id = pending_order_id;
END;
$$ LANGUAGE plpgsql;
  1. 找到顾客的购物车，找不到就 RAISE EXCEPTION 抛出异常（% 是占位符）。
  2. 算出订单总额。
  3. 把订单状态改为 ordered，写入总额和下单时间。
  4. 扣减库存。热门商品可能库存不够 —— 这时 stock_quantity >= 0 的 CHECK 约束会让这一步失败，整个函数回滚。
  5. 返回订单摘要。
SELECT * FROM sales.order_checkout(customer_id_param => 3);

               order_id               | customer_id | total_amount
--------------------------------------+-------------+--------------
 e900fb15-aa65-4eea-bd52-1abe8d5832b6 |           3 |        47.97
(1 row)
💡 SELECT * FROM 函数

用 SELECT * FROM 函数名(…) 调用，psql 会把返回的列名一起显示；不需要列名的话可以简写成 SELECT sales.order_checkout(3)。

实战：用触发器自动维护订单总额

现在有个小问题：顾客往购物车里加东西时，订单的 total_amount 并不会更新，要等到结账时才计算。 比如 Bob（id=2）加了一袋 Sunrise Blend： 

SELECT * FROM sales.order_add_item(
    customer_id_param => 2,
    product_id_param => 1,
    quantity_param => 1);

SELECT id, status, total_amount FROM sales.orders
WHERE id = '34221a65-df20-4396-b9f4-3e3cf328f9d2';  -- 换成你自己的 order_id

                  id                  | status  | total_amount
--------------------------------------+---------+--------------
 34221a65-df20-4396-b9f4-3e3cf328f9d2 | pending |
(1 row)

总额是空的。我们写一个触发器：每当购物车明细被增、改、删，就自动重算订单总额。先写触发器函数：

CREATE OR REPLACE FUNCTION sales.update_order_total()
RETURNS TRIGGER AS $$
BEGIN
    UPDATE sales.orders
    SET total_amount = (
        SELECT COALESCE(SUM(oi.quantity * oi.price), 0)
        FROM sales.order_items oi
        WHERE oi.order_id = COALESCE(NEW.order_id, OLD.order_id)
    )
    WHERE id = COALESCE(NEW.order_id, OLD.order_id) AND status = 'pending';

    RETURN NEW;
END;
$$ LANGUAGE plpgsql;
  • 触发器执行时，Postgres 会传入两个特殊变量：NEW 是行的新版本，OLD 是旧版本。
  • COALESCE(a, b) 返回第一个非 NULL 的参数。INSERT/UPDATE 时 NEW 不为空，DELETE 时只有 OLD 不为空，所以 COALESCE(NEW.order_id, OLD.order_id) 三种情况都能拿到订单 ID。
  • 购物车被清空时 SUM 结果是 NULL，外层 COALESCE(…, 0) 把它变成 0。
  • 最后 RETURN NEW，让 Postgres 原样保存新版本的行。

再创建触发器本身，把函数“挂”到 order_items 表上：

CREATE TRIGGER trigger_update_order_total
AFTER INSERT OR UPDATE OR DELETE ON sales.order_items
FOR EACH ROW
EXECUTE FUNCTION sales.update_order_total();

    product_id_param => 1, quantity_param => 2);
-- 订单总额自动变成 33.08（16.54 × 2）

SELECT * FROM sales.order_add_item(customer_id_param => 2,
    product_id_param => 1, quantity_param => 4);
-- 订单总额自动变成 66.16（16.54 × 4）

--------------------------------------+---------+--------------
 34221a65-df20-4396-b9f4-3e3cf328f9d2 | pending |        66.16
(1 row)

物化视图

用 CREATE VIEW 创建的普通视图不保存结果，每次调用都重新执行底层查询。 如果查询很耗资源，或者数据不需要实时，可以用物化视图（materialized view）： 它执行一次查询并把结果存下来，所有人看到的都是这份结果，直到你显式刷新。 

CREATE MATERIALIZED VIEW sales.monthly_sales_summary AS
SELECT
    date_trunc('month', o.order_date) AS sales_month,
    SUM(oi.quantity * oi.price) AS total_revenue,
    COUNT(DISTINCT(o.id)) AS total_orders
FROM sales.orders o
JOIN sales.order_items oi ON o.id = oi.order_id
GROUP BY sales_month
ORDER BY sales_month;

date_trunc('month', …) 把时间截断到当月 1 日零点，于是同一个月的订单被分到一组。查询它：

     sales_month     | total_revenue | total_orders
---------------------+---------------+--------------
 2024-09-01 00:00:00 |        140.66 |            3
(1 row)

角色与访问控制

写代码时我们常常沉浸在功能里，忽略了安全。我们熟练使用应用层的安全框架做认证和授权，但只做应用层安全是不够的： 用户登录后，应用会以某个数据库角色打开连接、替用户执行 SQL。 如果这个角色的权限远大于应用允许用户做的事，一旦某个用户账号被盗，攻击者就可能借此在数据库里为所欲为。

Postgres 用角色（role）管理数据库层面的权限。角色可以是一个用户，也可以是一组用户，取决于怎么配置。 所以当有人说“用用户 X 连 Postgres”，技术上指的是“用角色 X 连接”。用 \du 看看现有角色： 

                             List of roles
 Role name |                         Attributes
-----------+------------------------------------------------------------
 postgres  | Superuser, Create role, Create DB, Replication, Bypass RLS

目前只有 Postgres 初始化时创建的 postgres 超级用户，它什么都能做。 做实验和早期开发用它没问题，但应用成形后就应该为不同类型的用户建专门的角色。 我们来给 Jake 建一个：能管理商品、看销售数据，但不能改数据库结构（那是平台的职责），也不能碰别人的数据库。 

CREATE ROLE coffee_chain_admin WITH LOGIN PASSWORD 'password';

GRANT CONNECT ON DATABASE coffee_chain TO coffee_chain_admin;

REVOKE CONNECT ON DATABASE coffee_chain FROM PUBLIC;
  • CREATE ROLE … WITH LOGIN：带 LOGIN 属性的角色可以用来登录，通常就叫“数据库用户”。
  • GRANT CONNECT：允许它连接 coffee_chain 数据库。
  • REVOKE CONNECT … FROM PUBLIC：PUBLIC 是一个包含所有角色的默认角色。撤销它的连接权限 = 默认谁都不能连。 coffee_chain_admin 虽然也属于 PUBLIC，但上一句已经显式授权给它，所以不受影响。

再允许它读写各个模式里的所有表，并能使用序列生成 ID：

GRANT USAGE ON SCHEMA public TO coffee_chain_admin;
GRANT USAGE ON SCHEMA products TO coffee_chain_admin;
GRANT USAGE ON SCHEMA customers TO coffee_chain_admin;
GRANT USAGE ON SCHEMA sales TO coffee_chain_admin;

GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES
  IN SCHEMA public TO coffee_chain_admin;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES
  IN SCHEMA products TO coffee_chain_admin;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES
  IN SCHEMA customers TO coffee_chain_admin;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES
  IN SCHEMA sales TO coffee_chain_admin;

GRANT USAGE, SELECT ON ALL SEQUENCES
  IN SCHEMA products TO coffee_chain_admin;
GRANT USAGE, SELECT ON ALL SEQUENCES
  IN SCHEMA customers TO coffee_chain_admin;
GRANT USAGE, SELECT ON ALL SEQUENCES
  IN SCHEMA sales TO coffee_chain_admin;

最后，确保默认谁都连不上 Susannah 的库和默认的 postgres 库：

REVOKE CONNECT ON DATABASE brewery FROM PUBLIC;
REVOKE CONNECT ON DATABASE postgres FROM PUBLIC;
ⓘ 命令有点多？

只为 Jake 一个人配角色就写了这么多条，而且可能还没覆盖所有边界情况。别担心，深入了解后会发现很直观。 比如可以创建一个组角色，把所有商家通用的 GRANT/REVOKE 定义在它上面，再把每个商家的角色加入这个组，自动继承权限。

因为 coffee_chain_admin 不是数据库及其对象的所有者 —— 所有者是创建它们的 postgres 角色（\l 可以看到）。 postgres 权限太大，只应该给有管理员权限的人，或者需要初始化、修改数据库结构的应用组件使用。 Jake 的角色也可以给协助他打理店铺的经理使用；而面向顾客，还可以再建一个权限更小的角色。

小结

  • Postgres 具备你对关系型数据库期待的所有标准能力。
  • 数据库、模式、表是基础构件，可以把数据库结构和应用架构对应起来；多租户可以在表、模式、数据库三个层级实现。
  • SQL 非常灵活：既能操作单表，也能用 JOIN 联合多表。
  • 约束和外键在数据库层面守住数据正确性；事务（ACID）和 MVCC 让并发读写既安全又高效。
  • 函数和触发器让你直接在数据库里执行应用逻辑，减少网络往返。
  • 视图封装复杂查询；物化视图缓存结果，需要手动或定时刷新。
  • 角色让你细粒度地控制数据库访问，遵循“最小权限”原则。
