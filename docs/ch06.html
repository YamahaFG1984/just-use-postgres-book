第 6 章

全文搜索

Postgres 一直支持各种文本类型和搜索运算符：=、LIKE/ILIKE 模式匹配、~/~* 正则匹配…… 它们对付简单文本够用，但面对大段文档、需要理解“词的变形”和“相关度排序”时就力不从心了。 全文搜索是 Postgres 的另一项核心能力：用语言学技术对文本做分词、规范化、排序和索引，让搜索更快、更准。 这一章我们为一个电影推荐服务开发搜索模块。

本章目标

  • 理解全文搜索的四步流程：分词 → 规范化 → 存储与索引 → 搜索
  • 认识 词素（lexeme）、tsvector、tsquery、全文搜索配置
  • 用生成列自动维护 tsvector
  • 用 @@、plainto_tsquery、to_tsquery 搜索，用 ts_rank + 权重排序，用 ts_headline 高亮
  • 用 GIN 和 GiST 索引加速，并知道两者的取舍

Postgres 全文搜索基础

先看看为什么 LIKE 不够用。假设用户想找“explorers traveling to a galaxy”的电影：

Postgres 的全文搜索大致分四步：

  1. 分词（tokenization）：原始文本（通常叫文档）被解析成一个个词元（token），比如单词或短语。“5 explorers are traveling”被切成 “5”、“explorers”、“are”、“traveling”。
  2. 规范化（normalization）：把词元转换成词素（lexeme）——语言中有意义的基本单位。这一步会去掉大小写差异、把词还原成词干（stemming）、去掉冠词介词这类停用词（stop word）。上面四个词元变成三个词素：“5”、“explor”、“travel”。“are”是停用词被去掉了。
  3. 存储和索引：把词素存进数据库，避免每次重复分词和规范化。Postgres 有专门的 tsvector 类型来存词素，还能对它建索引。
  4. 搜索：应用对存储的词素执行全文搜索查询。
ⓘ 为什么 explorers 变成 explor 而不是 explore

Postgres 默认的英文词干提取器会去掉 “-er”、“-s” 这类常见后缀，所以 explorers → explor。词干不一定是一个真实的单词，只要同一个词的各种变形都能还原成同一个词干就行。

分词与规范化

用 ts_debug（测试和调试全文搜索配置的函数）看看一句话是怎么被处理的：

SELECT token, description, lexemes, dictionary
FROM ts_debug('5 explorers are traveling to a distant galaxy');

   token   |   description    |  lexemes  |  dictionary
-----------+------------------+-----------+--------------
 5         | Unsigned integer | {5}       | simple
           | Space symbols    |           |
 explorers | Word, all ASCII  | {explor}  | english_stem
           | Space symbols    |           |
 are       | Word, all ASCII  | {}        | english_stem
           | Space symbols    |           |
 traveling | Word, all ASCII  | {travel}  | english_stem
           | Space symbols    |           |
 to        | Word, all ASCII  | {}        | english_stem
           | Space symbols    |           |
 a         | Word, all ASCII  | {}        | english_stem
           | Space symbols    |           |
 distant   | Word, all ASCII  | {distant} | english_stem
           | Space symbols    |           |
 galaxy    | Word, all ASCII  | {galaxi}  | english_stem
(15 rows)
  • token 列是切出来的词元，description 是词元类型：“5”是 Unsigned integer（无符号整数），七个单词是 Word, all ASCII，还有七个空格（Space symbols）。
  • 切分由 Postgres 内置的解析器 pg_catalog.default 完成（SELECT prsname FROM pg_ts_parser; 可以看到它）。
  • lexemes 是规范化后的词素，dictionary 是用了哪个字典：
    • simple 字典原样处理词元，不做词干提取或去停用词，所以“5”还是 {5}。
    • english_stem 字典按英语规则提取词干、去停用词。停用词被映射为空词素 {} 而不是彻底删除，是为了保留它们的位置信息，供 <->（紧跟）运算符使用。
    • 空格不对应任何词素，dictionary 列为空。

全文搜索配置

Postgres 只有一个预定义的解析器，但内置了很多字典。用哪个字典处理哪类词元，由全文搜索配置决定。 Postgres 为很多种人类语言预定义了配置，默认配置在安装时设定，存在 default_text_search_config 参数里。按第 1 章的方式启动的容器，默认是 english：

⚠ 关于中文

Postgres 内置配置里没有中文。中文词与词之间没有空格，默认解析器无法正确分词（整句会被当成一个词元）。 处理中文全文搜索需要安装 zhparser、pg_jieba 等第三方分词扩展，或者用第 8 章的向量搜索。本章的例子都是英文，中文的完整做法见专题 1：中文全文搜索。

为文本搜索准备数据

我们负责电影推荐服务的搜索模块：用户或其他组件来要推荐，它要返回最相关的结果。第一步是把电影数据准备成可以全文搜索的样子。

用 to_tsvector 生成词素

to_tsvector([ config regconfig, ] document text) returns tsvector

它把原始文本转换成 tsvector 类型的词素列表。用户搜索“The explorers must save the fragile peace between Earth and the aliens.”：

SELECT * FROM to_tsvector(
    'The explorers must save the fragile peace between Earth and the aliens.');

                              to_tsvector
-----------------------------------------------------------------------
 'alien':12 'earth':9 'explor':2 'fragil':6 'must':3 'peac':7 'save':4
(1 row)

搜索模块允许用户同时提供标题和描述。用字符串拼接运算符 || 把它们合成一个字符串再传进去（中间加个空格）：

SELECT * FROM to_tsvector(
'Space Explorers' ||
' ' ||                    -- 加一个空格
'The explorers must save the fragile peace between Earth and the aliens.');

                               to_tsvector
-------------------------------------------------------------------------
 'alien':14 'earth':11 'explor':2,4 'fragil':8 'must':5 'peac':9
 'save':6 'space':1
(1 row)

“explorers”在标题和描述里各出现一次，所以 'explor':2,4 记录了两个位置。也可以分别生成：

SELECT title_lexemes, description_lexemes FROM
 to_tsvector('Space Explorers') as title_lexemes,
 to_tsvector(
 'The explorers must save the fragile peace between Earth and the aliens.'
 ) as description_lexemes;

    title_lexemes     |                description_lexemes
----------------------+---------------------------------------------------
 'explor':2 'space':1 | 'alien':12 'earth':9 'explor':2 'fragil':6 'must':3
                      | 'peac':7 'save':4
(1 row)

在 movies 表里存储词素

搜索模块要对 name 和 description 两列做全文搜索。先看看《2001 太空漫游》：

💡 \x 扩展显示

psql 的 \x on 开启扩展显示模式：每一行竖着显示，列多或值很长时更好读。\x off 恢复成表格模式。

用 ALTER TABLE 加一个 tsvector 类型的 lexemes 列：

ALTER TABLE omdb.movies
ADD COLUMN lexemes tsvector
GENERATED ALWAYS AS (
  to_tsvector(
    'english', coalesce(name, '') ||
    ' ' ||
    coalesce(description, ''))) STORED;
  • GENERATED ALWAYS AS (…) STORED 定义了一个存储型生成列：它的值由表达式自动计算并保存。片名或简介一改，词素自动重新生成，应用不用操心。
  • 必须显式传入 'english'：生成列的表达式必须是不可变的（immutable）。不传配置的话，to_tsvector 会依赖 default_text_search_config，而这个设置可以在会话或数据库级别修改，结果就不确定了，所以语句会报错。
  • coalesce(column, '') 处理 NULL：to_tsvector(NULL) 返回 NULL，而 NULL 和任何字符串拼接的结果也是 NULL。（这里两列都有 NOT NULL 约束，其实用不着，但值得了解。）

执行全文搜索

用户的查询也要经过同样的规范化：去停用词、转词素。转换结果是 tsquery 类型，词素之间用特殊运算符连接，比如 &（与）、|（或）。 然后用匹配运算符 @@ 比较 tsvector 和 tsquery：匹配返回 true，否则 false。

plainto_tsquery：简单查询

plainto_tsquery([ config regconfig, ] querytext text) returns tsquery

用户想看动画片，在搜索框里输入“a computer animated film”：

SELECT plainto_tsquery('a computer animated film');

      plainto_tsquery
----------------------------
 'comput' & 'anim' & 'film'
(1 row)

冠词 a 被去掉，其余规范化成词干，中间插入 &（AND）：三个词素都必须出现才算匹配。

ⓘ 拼写错误怎么办？

“computer animated”严格说应该写成“computer-animated”，但用户就是这么输入的，应用要能容忍小错误和拼写错误。 想识别拼写错误或做自动补全，可以用 pg_trgm 扩展提供的三元组（trigram）匹配 —— 把字符串拆成连续三个字符的组合来比较相似度。详见文档。

to_tsquery：高级过滤

plainto_tsquery 要求所有词都出现。需要更复杂的逻辑时，用 to_tsquery，它的输入必须用运算符把词连起来，还可以用括号分组：

用户看了上面的推荐，进一步要求：电脑动画，并且有狮子、小丑鱼或驴子：

SELECT id, name
FROM omdb.movies
WHERE lexemes @@ to_tsquery('computer & animated
      & (lion | clownfish | donkey)');

   id   |     name
--------+---------------
     12 | Finding Nemo
    808 | Shrek
 120862 | The Lion King
(3 rows)

用户又说：要有狮子的电影，但排除《狮子王》：

SELECT id, name
FROM omdb.movies
WHERE lexemes @@ to_tsquery('lion & !''The Lion King''');

   id   |                              name
--------+----------------------------------------------------------------
    411 | The Chronicles of Narnia: The Lion, the Witch and the Wardrobe
    630 | The Wizard of Oz
   9904 | The Wild
  35066 | Four Lions
  99216 | Lion
 130325 | Les misérables
(6 rows)

短语要用两个单引号包起来（SQL 字符串里的单引号要写两次来转义），才会被当作一个整体。它是怎么被理解的？

SELECT * FROM to_tsquery('lion & !''The Lion King''');

           to_tsquery
---------------------------------
 'lion' & !( 'lion' <-> 'king' )
(1 row)

短语被拆成 lion 和 king（the 是停用词），中间插入 <->：king 必须紧跟在 lion 后面。 <N> 可以指定距离。比如找“return”之后第 3 个位置是“king”的电影： 

SELECT id, name
FROM omdb.movies
WHERE lexemes @@ to_tsquery('return <3> king');

 id  |                     name
-----+-----------------------------------------------
 122 | The Lord of the Rings: The Return of the King
(1 row)

“return”后面依次是 of、the、king —— king 正好在第 3 个位置。这也说明了为什么停用词要保留位置编号。

💡 另外两个转换函数
  • phraseto_tsquery：和 plainto_tsquery 类似，但词素之间插入 <-> 而不是 &（按短语匹配），遇到停用词时会插入 <N>。
  • websearch_to_tsquery：最适合直接处理用户的原始输入。用户可以像用搜索引擎一样写 or、引号短语、- 排除，格式写错也不会报语法错误。

Postgres 提供了两个计算相关度的函数：

  • ts_rank：根据词出现的频率和位置打分。
  • ts_rank_cd：ts_rank 的变体，还考虑词的密度（cover density）—— 查询词彼此靠得越近，分越高。

用 ts_rank 排序

ts_rank([ weights float4[], ] vector tsvector,
  query tsquery [, normalization integer ]) returns float4
参数含义
weights（可选）按标签给词加权。共四个标签 A、B、C、D，A 通常给文档最重要的部分。格式是 {D权重, C权重, B权重, A权重}，默认 {0.1, 0.2, 0.4, 1.0}，越接近 1 越重要
vector文档的 tsvector
querytsquery 查询
normalization（可选）文档长度如何影响得分，是个位掩码：0（默认）不考虑长度；1 除以文档长度；2 除以平均词频……可组合
SELECT id, name, vote_average,
  ts_rank(lexemes, to_tsquery('ghosts')) AS search_rank
FROM omdb.movies
WHERE lexemes @@ to_tsquery('ghosts')
ORDER BY search_rank DESC, vote_average DESC NULLS LAST LIMIT 10;

用权重区分标题和简介

现在 ts_rank 还分不清 ghost 是出现在片名里还是简介里 —— 词素是从“片名 + 简介”拼接后的文本生成的，只有位置信息。 用 setweight 函数可以给 tsvector 里的词素打上权重标签： 

SELECT id, name, description,
  (setweight(to_tsvector('english', coalesce(name, '')), 'A') ||
   setweight(to_tsvector('english', coalesce(description, '')), 'B'))
     as lexemes_with_weight
FROM omdb.movies
WHERE id = 251;

lexemes_with_weight | 'award':6B 'chaotic':19B 'contact':24B 'demi':29B
                      'ghost':1A,2B,15B 'help':22B 'love':8B 'moor':30B ...

片名部分标 A（最高），简介部分标 B，两个 tsvector 用 || 拼起来。'ghost':1A,2B,15B：一次在片名，两次在简介。重建 lexemes 列：

ALTER TABLE omdb.movies
DROP COLUMN lexemes;

ALTER TABLE omdb.movies
ADD COLUMN lexemes tsvector
GENERATED ALWAYS AS (
    setweight(to_tsvector('english', coalesce(name, '')), 'A') ||
    setweight(to_tsvector('english', coalesce(description, '')), 'B')
) STORED;

💡 在 tsquery 里限定权重

可以在查询词后面加 :A，只匹配带 A 标签的词素 —— 也就是只搜片名：

SELECT id, name, vote_average,
  ts_rank(lexemes, to_tsquery('ghosts')) AS search_rank
FROM omdb.movies
WHERE lexemes @@ to_tsquery('ghosts:A')
ORDER BY search_rank DESC, vote_average DESC NULLS LAST LIMIT 10;
-- 只返回 7 部片名里有 ghost 的电影

高亮搜索结果

搜索模块还想支持高亮：把简介里匹配的词标出来，供其他组件进一步处理。Postgres 的 ts_headline 函数返回文档中的片段，并把搜索词高亮： 

ts_headline([ config regconfig, ] document text,
  query tsquery [, options text ]) returns text

找出最相关的海盗电影，并高亮简介：

SELECT id, name,description,
    ts_headline(description, to_tsquery('pirates')) AS fragments,
    ts_rank(lexemes, to_tsquery('pirates')) AS rank
FROM omdb.movies
WHERE lexemes @@ to_tsquery('pirates:B')
ORDER BY rank DESC LIMIT 1;
  1. to_tsquery('pirates:B') 只在简介（B 标签）里搜。
  2. ts_headline 处理的是原始的 description 文本（它会自己现场生成不带权重的词素），所以这里的查询不加 :B。
  3. ts_rank 的查询也不加 :B，这样片名（A 标签）里的 pirates 也计入得分。最后取得分最高的一部。
id          | 58
name        | Pirates of the Caribbean: Dead Man's Chest
description | Captain Jack is back! The bizarre and infamous pirate
              Captain Jack is in a battle with the ocean itself. Jack knows
              it won't be easy and gathers friends to help him on his mission to
              find the heart of Davy Jones in this second and more slapstick
              film from the pirate trilogy.
fragments   | <b>pirate</b> Captain Jack is in a battle with the ocean
              itself. Jack knows it won't be easy
rank        | 0.6957388

匹配的词被包在 <b> 和 </b> 里，这是默认的高亮标记。但简介末尾还有一个 pirate（“the pirate trilogy”）没被高亮 —— 因为 ts_headline 默认只返回一个片段。可以通过选项调整： 

SELECT id, name, description,
  ts_headline(description, to_tsquery('pirates'),
    'MaxFragments=3, MinWords=5, MaxWords=10,
     FragmentDelimiter=<ft_end>') AS fragments,
  ts_rank(lexemes, to_tsquery('pirates')) AS rank
FROM omdb.movies
WHERE lexemes @@ to_tsquery('pirates:B')
ORDER BY rank DESC LIMIT 1;
选项含义
MaxFragments=3最多返回 3 个包含搜索词的不同片段
MinWords=5, MaxWords=10每个片段最少 5 个、最多 10 个词（默认 15 和 35）
FragmentDelimiter=<ft_end>片段之间的分隔符，默认是 ...
fragments | bizarre and infamous <b>pirate</b> Captain Jack is
            in a battle<ft_end>slapstick film from the <b>pirate</b> trilogy
⚠ 当心 XSS

ts_headline 的输出不保证可以直接放进网页：处理不可信的输入时可能被用来发动跨站脚本攻击（XSS）。 我们的 name 和 description 都是纯文本，没有这个问题；但如果你存储、搜索的是带 HTML 标记的文档，要么先去掉所有 HTML 标签，要么用 HTML 清理器（sanitizer）处理输出。 更多选项见官方文档。

为词素建索引

用户想看一部“人们为真正重要的东西而战”的历史片：

SELECT id, name FROM omdb.movies
WHERE lexemes @@ to_tsquery('historical & fight');
-- Gladiator · Saints and Soldiers · Braveheart

找到这三部电影花了多大力气？

 Seq Scan on movies (actual time=0.226..15.301 rows=3 loops=1)
   Filter: (lexemes @@ to_tsquery('historical & fight'::text))
   Rows Removed by Filter: 4222
 Planning Time: 0.179 ms
 Execution Time: 15.328 ms

全表扫描，对每一行都做了一次匹配，丢掉了 4222 行。来试试 GIN 和 GiST 索引。

GIN 索引

GIN 是全文搜索的首选索引。第 5 章用它索引 JSON 的键和值；这里它索引的是 tsvector 的词素：每个不同的词素一个条目，条目指向包含该词素的所有行。

ⓘ GIN 不存位置和权重

GIN 只存词素本身，不存位置信息和权重标签。查询如果需要这些信息（比如 <->、:A），Postgres 要回表去取。如果大量查询依赖位置，可以考虑 RUM 索引：原理类似 GIN，但条目里还存了词素位置。它以扩展的形式提供。

CREATE INDEX idx_movie_lexemes_gin
ON omdb.movies
USING GIN (lexemes);

 Bitmap Heap Scan on movies (actual time=0.088..0.099 rows=3 loops=1)
   Recheck Cond: (lexemes @@ to_tsquery('historical & fight'::text))
   Heap Blocks: exact=3
   -> Bitmap Index Scan on idx_movie_lexemes_gin (actual time=0.067..0.067 rows=3 loops=1)
         Index Cond: (lexemes @@ to_tsquery('historical & fight'::text))
 Planning Time: 0.283 ms
 Execution Time: 0.150 ms

从 15.3 ms 降到 0.15 ms，快了一百倍。先 Bitmap Index Scan 在索引里找出匹配的行、生成位图，再 Bitmap Heap Scan 回表取 id 和 name。

GiST 索引

GiST（Generalized Search Tree，通用搜索树）是一种灵活的平衡树，常用于支持“包含、邻近、相似”这类运算的复杂类型：几何形状、全文词素、网络地址、范围类型等。 它怎么工作取决于被索引的类型。比如索引二维点时，它先用大的外接矩形把点分组放在根页，再逐层拆成更小的矩形，直到叶子存真正的点（第 10 章会细讲）。

索引 tsvector 时，GiST 构建的是一棵签名树（signature tree）：每个条目存一个代表文档的签名——一串 0/1 位。 单个词素的签名只有一位是 1；文档的签名是它所有词素签名的按位或（OR）。假设签名长 8 位：

词素 / 文档签名
“histor”00000001
“film”10000000
“gladiat”01000000
文档 “Gladiator is a historical film”11000001（三者按位或）
ⓘ 签名长度

默认签名长度是 124 字节，建索引时可以修改，最大 2024 字节。签名越长，扫描索引时误判（false positive）越少，但索引也越大。

CREATE INDEX idx_movie_lexemes_gist
ON omdb.movies
USING GIST (lexemes);

-- 删掉 GIN 索引，确保实验时 Postgres 选择 GiST
DROP INDEX omdb.idx_movie_lexemes_gin;

 Index Scan using idx_movie_lexemes_gist on movies
   (actual time=0.077..0.363 rows=3 loops=1)
   Index Cond: (lexemes @@ to_tsquery('historical & fight'::text))
 Planning Time: 0.985 ms
 Execution Time: 0.395 ms

GiST 的执行计划看起来比 GIN 简单（直接 Index Scan），但 GIN 反而快了一倍多（0.150 ms vs 0.395 ms）。 原因之一：GiST 找到签名匹配的文档后，还得回表确认词素真的存在 —— 不同词素可能在同一位上为 1，造成签名碰撞。把签名长度从默认的 124 字节加大，可以减少碰撞。

💡 需要更强的搜索？

如果 Postgres 核心的全文搜索还不够，可以看看 pg_search 扩展，它提供了现代搜索引擎广泛使用的 BM25 相关度评分算法等高级功能。第 8 章还会用生成式 AI 进一步提升这个电影推荐服务的搜索能力。

小结

  • Postgres 内置了全文搜索，适合需要分析、查询文本内容的应用。
  • 和其他全文搜索引擎一样，它对文档做分词和规范化，生成 tsvector 词素；查询也被规范化成 tsquery，用 @@ 匹配。
  • 全文搜索配置决定用哪个字典；生成列要显式指定配置。
  • plainto_tsquery / to_tsquery / websearch_to_tsquery 构造查询；ts_rank + setweight 排序；ts_headline 高亮。
  • GIN 和 GiST 是加速全文搜索的两种主要索引：GIN 查得快，GiST 小而易维护。
